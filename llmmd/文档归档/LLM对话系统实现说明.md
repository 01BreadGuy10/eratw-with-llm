## 1. 一句话概括

用**插件**把游戏里的"自由对话"接到大模型上：角色用**游戏自带的口上剧本当 persona**，
按性格和你自由聊天；对话**能增减游戏数值**（好感度/情緒/愤怒），
**她被惹毛了会拒绝继续聊**；全程**立绘跟随显示**。

**对游戏本体零侵入**：不改任何既有脚本的逻辑，只新增文件 + 一个自定义指令。
插件删掉即完全恢复原状。

## 3. 文件构成

### 3.1 ⚠️「接口返回了空内容」的真正原因：**思考过程吃光了 max_tokens**

**症状**：偶尔出现 `[CHAT-FAIL] InvalidOperationException: 接口返回了空内容`，
**尤其容易发生在开场白那一轮**。

**诊断**（从 `debug.log` 里捞真实响应体，这是关键一步）：

```json
"message": {
  "content": "",                          ← 空
  "reasoning": "用户希望我开始自由对话…我是映姬…我需要用映姬的说话方式：礼貌体…"
}
```

**根因**：这个接口的 **`thinking:{"type":"disabled"}` 不生效** —— 模型仍然会先输出一段
`reasoning`（思考过程）。而 `max_tokens = 400` 时，**思考过程就把额度吃光了，
正文（`content`）没地方放，于是返回空**。

**为什么偏偏是开场白**：那一轮的 prompt 最复杂（要她主动开口 + 遵守一堆格式规则）→
模型思考得最多 → 最容易撑爆额度。

**修法**：`plugins/LLMBridge/apis.txt` 里把 `max_tokens` 提到 **2000**
（reasoning 本身可能有 500~1000 字）。改完**点 `[1]` 重载即可，不用重启**。

> ⚠️ **不要试图用 `reasoning` 当回复**（插件里原来那句兜底找的是 `reasoning_content`，
> 而且字段名还不对）—— 那是**思考过程不是台词**，拿来当回复只会得到一段
> 像是在自言自语的分析文字。**正确做法是给足额度，让它把正文写出来。**
>
> **教训**：`max_tokens` 是"思考 + 正文"的**总预算**，不是"正文长度"。
> 只要接口会返回 `reasoning`，额度就得按"两者之和"来配。
```
plugins/
  LLMBridge.dll              ← 插件本体（必须直接放 plugins/ 根目录，引擎不递归子目录）
  LLMBridge/
    apis.txt                 ← 接口配置（自己填 key）
    config.txt               ← 每角色的自由对话/自由亲密开关
    debug.log                ← 运行日志（排查问题看这里）
    src/                     ← 源码 + build.ps1

ERB/魔改内容/
  LLM_CONVERSATION.ERB       ← 对话主逻辑（14 个函数）
  LLM_CHAT_BRIDGE.ERB        ← 菜单 + 自定义指令入口
  LLM_KOJO.ERH               ← 跨函数共享变量（.ERH 头文件，不是 .ERB）
  LLM_ERB语法避坑.md          ← 语法坑清单
```

> **关于 `.ERH`**：本作里 `#DIM/#DIMS` **不能**直接写在 `.ERB` 文件级
> （会报 Lv1「#行只能在函数声明后立刻使用」），跨函数共享变量必须放 `.ERH`。
>
> `LLM_KOJO.ERH` 现在只承担两件事：
> - **`LLM_PERSONA*`** —— persona 快照（`@LLM_PERSONA_SNAPSHOT` 写入，
>   `@LLM_BUILD_SYSTEM_PROMPT` 读取）。**这部分是必需的。**
> - **`LLM_DBG_*`** —— `@LLM_POLL` 用的轮询状态码中转变量。
>
> 另有 7 个 `LLM_BTN_*`（早期菜单按钮值）**已无人引用** —— 菜单改用字面量后
> 就废弃了，留着无害，可随时删。
>
> 除此之外，**跨函数传值一律走 `REF` 参数、跨轮次状态一律用函数内局部变量**
> （见 §9.4 的设计理由）。

## 4. 配置

### 4.1 接口配置 `plugins/LLMBridge/apis.txt`

最小的可用配置（复制粘贴改值即可）：

```
key   = sk-你的密钥
model = 模型名
url   = https://api.服务商.com
```

- `url` **很宽松**：`https://api.deepseek.com` 或带 `/v1` 或直接写完整
  `.../v1/chat/completions` 都能识别，会自动补全
- 多个接口用 `[名字]` 分段，加 `; [*]` 或 `active = 名字` 指定当前用哪条
- 本地 Ollama 无需密钥：`key = none` / `url = http://127.0.0.1:11434`
- **模型名会随服务商更新而变化**，报 `Model Not Exist` 就去服务商文档确认

### 4.2 每角色开关 `plugins/LLMBridge/config.txt`

```ini
[默认]
enable_free_talk     = 1
enable_free_intimate = 0

[1]
enable_free_talk = 0
```

- `[1]` 是角色编号（`TARGET`）
- 未列出的角色走 `[默认]`

### 4.3 游戏内临时开关

菜单里的 `[0] 切换本角色的临时开关` —— 存在 `CFLAG:角色:1100`，
**只影响当前这次游戏**，不改 `config.txt`。用于"临时不想让某个角色接 LLM"。

## 5. 使用

### 5.1 入口

指令列表里的 **`自由对话 ★[9030]`**（`ADD_CUSTOM_COM30`）。
进去后是菜单：

| 键 | 功能 |
|---|---|
| `[4]` | **开始自由对话** |
| `[1]` | 接口列表 / 重载 `apis.txt`（改完配置不用重启游戏） |
| `[2]` | 清空与该角色的对话记忆 |
| `[0]` | 切换本角色的临时开关 |
| `[3]` | 打印插件调试信息 |
| `[5]` | **自检**（确认各函数是否真的被引擎注册） |
| `[9]` | 返回 |

### 5.2 自由对话流程

```
点 [4]
  ├─ 她拒绝？（本地判定，见 §8）
  │    └─ 是 → 说一句拒绝台词 → 退出界面（台词留在画面上）
  └─ 否 → 她先开口（开场白）
           ↓
        你输入一句话 → 她回复 + 立绘 + 数值提示
           ↑                    ↓
           └──── 循环（上限 20 轮，输入空行结束）────┘
                每轮你发言后都会**重新判定一次是否被激怒**
```

### 5.3 数值联动

模型在台词后附一个结算块：

```
「哼，又来烦我。有事快说。」
###DELTA###
1,40,-60,0
       │  │   │ └─ t = 这句话的**性质**（0普通 / 1亲昵调情 / 2性骚扰越界）
       │  │   └─── 愤怒  c
       │  └─────── 情緒  b
       └────────── 好感度 a
```

**`t` 是"性质"而不是数值** —— 它决定 ERB 用哪套效果（见 §7.2）。
`t` 可以省略（模型没跟上格式时按 0 处理，只是没有分级效果）。

ERB 侧解析后**在台词下方打印一行**：

| 显示 | 含义 |
|---|---|
| `好感度＋1　情緒＋2` | 数值真的动了 |
| `（本轮数值无变化）` | 模型给了块、但判定为 0（平淡对话的正常结果） |
| `（本次回复未包含结算块 · 数值未变动）` | 模型没按格式来 |

**模型只提供建议值，最终裁决在 ERB**（见 §7），所以模型输出 `999` 也只能拿到 `+3`。

### 5.4 陪她一起做事（会消耗游戏时间）

如果**她手头正好有事在做**（吃饭 / 看书 / 钓鱼…），你可以直接说
「我陪你一起吃吧」「要帮忙吗」—— 她不只是回一句话，**这件事真的会推进**。

**结算方式完全照抄官方的「陪同行動」指令**（`COMF368 自由行動に付き合う.ERB:17-32`）：

```erb
LLM_ELAPSE = MIN(Activity_Duration:(CID), 30)     ; 投入时间 = min(她的剩余时间, 30 分钟)
LLM_FACTOR = MAX(LLM_ELAPSE / 10, 1)              ; 收益倍率 = 投入时间 / 10（至少 1）
TRYCALLFORM 自由行動内容_{Activity_Type:(CID)}(CID, "ソース", LLM_FACTOR)
TIME += LLM_ELAPSE                                 ; ★ 推进游戏时间
```

- 收益走该行动的 **`"ソース"` 分支** —— 每个 `FREE_ACT_*.ERB` 都有一个，
  按倍率结算 `SOURCE:歓楽` / `受動` / `征服` 与体力恢复（吃饭还会填饱肚子）
- 进度**不手动递减** —— `@自由行動処理` 会在时间推进后按 `TIME_PROGRESS` 自己减
  （`MOVEMENT_自由行動.ERB:13`）。手动再减一次就成了**双重递减**
- 时间推进后若已到点，`@自由行動処理` 会正确走 `"完了"` 分支（收尾 + 效果）

> ⚠️ **这是唯一会改变游戏时间的功能。** 也是它存在的意义 ——
> 自由对话原本不花时间（可以无限聊），"陪她做"让对话第一次有了时长成本：
> **每陪一次推进 10~30 分钟**（取决于她还剩多少）。
>
> 触发条件要**三条同时满足**：
> ① 她**手头确实有事**在做（`Activity_Duration` 非 0）；
> ② 玩家**明确表示要一起做 / 帮忙** —— 单纯"加油"不算；
> ③ **关系达到该动作要求的档位** —— 吃饭/看书要「思慕」，其余公开活动不设门槛（见下）。
>
> 判定由模型给出（结算块的 `t=3`），但**执行与钳制在 ERB 侧**：
> 即使模型乱填 `t=3`，只要她手头没做事，`IF LLM_D4 == 3 && Activity_Duration:(CID)` 就不会命中。

#### 动作专属处理

| 动作 | 处理 |
|---|---|
| **0 发呆** | **完全不走官方** —— 改为气力 +5、信赖度档位 2（见上） |
| **1 玩 / 2 吃饭 / 3 偷吃零食** | 官方结算之外**额外加成**：好感度 +2、`TFLAG:信頼度管理 += 1` |
| 其余 | 一律走官方 `"ソース"` 分支 |

**额外加成只在这三件事上给**（"纯粹愉快的相处"），且**只在第一次建立陪伴时给一次** ——
陪伴模式跨轮保持，每轮都给的话好感度会连着刷。

两个实现细节：

- **好感度直接加 `CFLAG:2`，不走 `SOURCE:歓楽`** —— 官方刚才已经在 `"ソース"` 里写过
  `SOURCE:歓楽` 了，再写一次等于把它翻倍，量级就失控
- **信赖度用 `TFLAG:信頼度管理 += 1`（加一档）而不是直接赋值** ——
  官方在 `"ソース"` 里已按**大成功 / 成功**设过档位，`+=` 是在它的基础上再补，
  不会覆盖掉官方对成败的判断

#### ⚠️ LLM 看不到道具 —— 所以要主动告诉它

模型**读不到** `ITEM:` / `MUSIC_ABLE` 这类游戏变量。但有些动作**玩家参与不了**：

| 动作 | 前置条件 | 不满足时官方怎么判 |
|---|---|---|
| **10 钓鱼** | `ITEM:釣魚竿` | `TFLAG:193 = -1`（没钓竿只能看着） |
| **8 演奏** | `MUSIC_ABLE(30~35)` 任一为 1 | `TFLAG:193 = -2`（没乐器只能看着） |

不告诉它，她就会说出「**来，你也甩一杆**」这种**与事实不符**的台词。

所以这两项会检查后注入：

```
【注意】玩家没有钓竿，只能在一旁看着你钓
（所以别邀请他一起做，也别假设他正在做 —— 按「他在旁边陪着你」来演。）
```

> ⚠️⚠️ **人称别写反**：这两项检查的都是**玩家（MASTER）**的持有物 ——
> `ITEM:` 是玩家的道具栏，`MUSIC_ABLE` 内部用的也是 `ITEM:ARG` 与
> `ABL:MASTER:音楽技能`。但这段文字是写给**角色**看的（第二人称"你" = 角色），
> 所以说成「**你**没有钓竿」会被理解成「**她自己**没钓竿」，**意思正好反了**。
> 必须写成「**玩家**没有○○，只能看着**你**做」。
>
> （这个错误我第一版就写反了，是使用者看出来的。）

`MUSIC_ABLE(ARG)` 的参数是**物品编号**（30~35），它内部已经检查了
"玩家有没有这件乐器、现在能不能用"（钢琴看地点、小提琴看音楽技能），
所以直接照抄官方 `FREE_ACT_8.ERB:169` 的写法即可。

#### ★ 特例：她在发呆时，「一起发呆」是**恢复**不是消耗

`Activity_Type == 0`（发呆想事情）时，"陪她一起"走一条**独立路径**：

```erb
ELSEIF Activity_Type:(LLM_CID) == 0
	LLM_ELAPSE = MIN(Activity_Duration:(LLM_CID), 30)
	BASE:MASTER:気力 = MIN(BASE:MASTER:気力 + 5, MAXBASE:MASTER:気力)   ; ★ 恢复
	TFLAG:信頼度管理 = 2                                                  ; ★ 信赖度
	TIME += LLM_ELAPSE
```

| 项目 | 数值 | 理由 |
|---|---|---|
| **气力** | **+5** | 正好抵消一轮自由对话的消耗（每轮双方各 −5），等于"这一轮白聊" |
| **信赖度** | 档位 **2** | 走官方结算；官方"会话"成功给 1、"膝枕"给 5，陪发呆介于两者之间 |
| 时间 | 照旧 +10~30 分钟 | 陪伴总是要花时间的 |

**⚠️ 为什么刻意不走 `FREE_ACT_0` 的 `"ソース"` 分支**：

那个分支是「**找她搭话聊天**」的结算 —— 它会**扣**双方 20~40 气力
（`FREE_ACT_0.ERB:113-120`），跟"安静地一起待着"的语义**正相反**。
一起发呆应该是休息，所以这里反过来给气力。

**信赖度用 `TFLAG:信頼度管理` 而不是直接改 `CFLAG:信赖度`** ——
因为官方结算链路（`@TRACHECK_信頼度上昇処理`）会按**愤怒 / 态度 / 献身**等
做修正后再写进 `CFLAG:角色:信赖度`（`TRACHECK_信頼度上昇処理.ERB:266`），
绕过去就丢掉了这些修正。

**界面提示**：

```
（你陪她一起发了会儿呆，气力恢复，过了 30 分钟）
```

```erb
LLM_TG_GATE = 0
IF GROUPMATCH(Activity_Type:(LLM_CID), 2, 3, 6)      ; 吃饭 / 偷吃零食 / 看书
	LLM_TG_GATE = REQUIRED_FAVOR_思慕                  ; = 1500，要思慕档
ENDIF
IF CFLAG:(LLM_CID):2 < LLM_TG_GATE
	; ── 她婉拒 ──
	LLM_D1 = -1      ; 好感度 −1（象征性的"这人有点没分寸"）
	LLM_D2 = -20     ; 情緒 −20
	LLM_D3 = 30      ; 愤怒 +30
	; 提示按档位给不同说法
	LLM_MSG += (亲密类 ? "（这件事太亲密了，关系还不够）" : "（关系还不够近，她没答应）")
```

**为什么要分档**：

| 类型 | 动作 | 门槛 | 道理 |
|---|---|---|---|
| **公开的社交活动** | 玩 / 运动 / 打扫 / 钓鱼 / 采集 / 演奏… | **不设门槛** | 不熟的人凑一局很自然，硬要"关系够近"反而不合理 |
| **安静私密的共处** | **吃饭 / 偷吃零食 / 看书** | **思慕（1500）** | 共享食物、并肩沉默 —— 关系不到位会显得唐突 |

（`REQUIRED_FAVOR_思慕 = 1500`、`恋慕 = 3000`，见 `DIM.ERH:11-15`）

**两级保险**（避免"她嘴上答应了、系统却判失败"的前后矛盾）：

1. **prompt 里告诉模型分档规则** —— 并且给了一对**对比例子**，这是关键：
   - 示例⑥：正在**吃饭** + 只是「认识的人」→ **婉拒**
   - 示例⑦：正在**运动** + **不太熟** → **爽快答应**
   
   > prompt 里明写了这条对比：**同一句「我陪你」，吃饭会被婉拒、运动却答应**
   > —— 因为这俩事的亲密程度不一样。只讲规则不给例子，模型很容易一刀切。
2. **ERB 侧仍然做门槛检查** —— 模型乱答应也没用

prompt 里还专门给了一个"被婉拒"的示例（示例⑥），让模型知道那种情形该怎么演：

```
【正确示例⑥】你正在吃饭，但你们还只是「认识的人」，玩家说「我陪你一起吃吧」：
……不用了。我一个人吃就行，你有事就去忙吧。
###DELTA###
-1,-20,30,3
```

**你在界面上会看到一行提示**：

```
（陪她吃饭，过了 30 分钟）
```

（`FreeAct_Name` 取行动名；取不到时退化成「陪了她 30 分钟」。）

#### ⚠️ 别忘了：**她自己也在干活**

这是本项目一个很容易漏的点 —— 游戏里角色**自己**就会推进工作量，
在 `@BASE自然変動(ARG)` 里（`BASE自然変動.ERB:104-106`）：

```erb
IF CFLAG:ARG:行動 == 5
	BASE:ARG:工作量 = MAX(BASE:ARG:工作量 - Lapse * 10, 0)   ; 每分钟 10 点
```

而它由 `MOVEMENT_SUB.ERB:24` **每回合**为每个角色调用一次。

**自由对话不是游戏回合**，所以这个函数根本不会跑 —— 结果就是
「**只有玩家帮忙才有进度**」，玩家会误以为自己必须一直帮，
最后把体力耗光（实测就累晕在门口了）。

**修法**：在 ④c 按**本轮实际推进的分钟数**补上那一份：

```erb
LLM_DT = TIME - LLM_T0          ; LLM_T0 在函数开头记下
SIF CFLAG:(LLM_CID):行動 == 5 && BASE:(LLM_CID):工作量 > 0 && LLM_DT > 0
	BASE:(LLM_CID):工作量 = MAX(BASE:(LLM_CID):工作量 - LLM_DT * 10, 0)
```

`TIME - LLM_T0` 同时覆盖**对话本身的 3 分钟**和**陪伴/帮忙额外推进的时间**，
所以一处就够了。

> ⚠️ 刻意**不直接 `CALL BASE自然変動`** —— 那会连带触发情绪衰减、
> 理性恢复、发情判定、宴会酒气等一大堆**本回合之外的**副作用，
> 在对话中途跑不合适。这里只补"她在干活"这一条。

**单轮的手感**（这才是该看的数 —— 玩家随时可以退出，见下）：

| 来源 | 每轮 |
|---|---|
| 她自己干（3 分钟 × 10） | **约 30** |
| 玩家帮忙（份额 3） | **约 33** |
| **合计** | **约 63 / 轮** |

⇒ **帮忙是"加速"，不是"唯一来源"** —— 这正是应该有的比例。

> ⚠️⚠️ **不要把"一场对话"当设计单位。**
> `LLM_ROUND >= 20` 那个上限只是**防止无限聊**，
> **玩家随时可以输入空行退出**。所以配平要看**单轮**：
> 一轮的消耗与收益自己就该说得过去，而不是"聊满 20 轮刚好如何"。
> （本项目早期的文档里多处用"一场 20 轮 = 一小时"来论证，那是**错误的基准**，
>   已全部改掉。）

#### ⚠️ 官方结算是**两步**，缺第二步等于白干

这是本项目**第三个同类 bug**（前两个：`DOWNBASE` 没结算、她自己干活没推进）——
共同点都是「**写了累积量，但没有结算入口**」。

官方「帮忙干活」的完整流程：

```
① @COM304 干活
     → 写 SOURCE:歓楽 / SOURCE:受動   （好感度 / 情绪的"源"）
     → TFLAG:信頼度管理 += 5          （信赖度的"档位"）
     → DOWNBASE                        （体力 / 气力）
② @SOURCE_CHECK（eraTW 的指令统合函数）统一结算
     → CALL FAVOR_CALC(TARGET)   SOURCE → 好感度 / 情緒 / 憤怒
     → CALL TRUST_CALC(TARGET)   TFLAG:信頼度管理 → 信赖度（末尾清 0）
```

出处：`SOURCE.ERB:1219`（`FAVOR_CALC`）与 `:1224-1225`（`TRUST_CALC`）。

**自由对话不是指令，`@SOURCE_CHECK` 根本不会跑** —— 所以只做 ① 的话，
她的**好感度、信赖度一动不动**（这就是"感觉对她的数值没影响"的根因）。

**修法**：在 ④e 手动补上第二步：

```erb
IF LLM_SRC_ANY || LLM_TRST_ANY
	LLM_TF102 = TFLAG:102
	TFLAG:102 = 1                    ; ← 闸门
	SIF LLM_SRC_ANY
		CALL FAVOR_CALC(LLM_CID)
	SIF LLM_TRST_ANY
		CALL TRUST_CALC(LLM_CID)
	TFLAG:102 = LLM_TF102
ENDIF
```

**两个关键细节**：

1. **`TFLAG:102` 是指令类型**（`1`=日常 / `2`=性行为 / `3`=逆推，见 `COUNTER_TYPE.ERB:4`），
   而 `FAVOR_CALC` / `TRUST_CALC` 开头都有 `SIF !TFLAG:102 / RETURN 0` ——
   自由对话里要**手动设成 1**（等同日常指令），否则它们直接返回、白调。**设完恢复原值。**
2. **两个标志分开判**（`LLM_SRC_ANY` / `LLM_TRST_ANY`）——
   像"陪发呆"这种**只写信赖、不写 SOURCE** 的情形不该跑 `FAVOR_CALC`，
   因为它开头有基线计算（`TFLAG:97 += (ABL:従順 + ABL:親密) / 2`），
   会让**每轮闲聊都白涨好感度**。

#### 工作量的两条贡献规则（都照抄官方）

工作进度有**两个来源**，缺一不可 —— 早期只实现了后者，导致玩家以为"必须一直帮"：

| 来源 | 公式 | 出处 |
|---|---|---|
| **她自己干** | `工作量 -= Lapse × 10` —— **每分钟 10 点** | `BASE自然変動.ERB:106` |
| **玩家帮忙** | `工作量 -= L_帮忙`，`L_帮忙 = WorkP + RAND:80 + RAND:80 + 10` | `COMF304:394,419` |

其中 `Lapse = TIME_PROGRESS(TIME:時間進行管理)` = **这一回合经过的分钟数**
（`MOVEMENT2.ERB:8`）。所以"陪她 15 分钟"时她自己就推进 **150 点**，
比玩家的贡献还多。

**量纲核对**：`600 = 1 小时的工作量`（`JOB_仕事内容.ERB:299` 注释 `=2400=4時間`），
美铃门番 `600 × 6 = 3600 = 6 小时` —— 她每分钟 10 点，正好 6 小时干完。**规则自洽。**

> ⚠️ 我一度以为"她自己只推进 30 太少了"，其实那是**没把她的贡献显示出来**：
> 明细里只有玩家的那份，看起来就像她几乎没动。
> 现在明细会**分开列**：
> ```
> （体力－150　气力－30　工作量＋126　信赖度＋2　她自己推进＋150　时间－15分钟）
> ```

#### ⚠️「工作量份额」不能拿去乘「好感度源」

帮忙干活会写两样东西，它们**必须分开控制**：

| 项目 | 跟什么走 | 理由 |
|---|---|---|
| **工作量推进** | `LLM_STEP`（随口 9 / 认真 30） | 使用者要"一场对话内能把活干完"，所以给足 |
| **好感度源 `SOURCE`** | **官方基准**（随口 300 / 认真 450） | 描述的是"**这次相处本身的质量**"，不是"干完了多少活" |

**踩过的坑**：早期写成

```erb
SOURCE:(LLM_CID):歓楽 += MAX(300 * LLM_STEP / 10, 1)
```

份额 30 时 `歓楽 += 900` —— 官方基准（`COMF304:138` 的 `300`）的 **3 倍**，
经 `@FAVOR_CALC` 换算后**一次帮忙就 +40~50 好感度**。

**现在的写法**：

```erb
LLM_SRC = 300
SIF LLM_COSTSTEP > 0
	LLM_SRC = 450        ; 认真帮忙 1.5 倍（作为"更投入"的奖励）
SOURCE:(LLM_CID):歓楽 += LLM_SRC
SOURCE:(LLM_CID):歓楽 += 70 + ABL:(LLM_CID):親密 * 50     ; 基准值，不乘份额
SOURCE:(LLM_CID):受動 += 230 + 80 * ABL:(LLM_CID):従順
```

> **教训**：一个份额参数被"复用"到多个语义不同的地方时，
> 只要其中一处的量级被调过，另一处就会跟着失控。
> **数值快慢**和**关系收益**是两件事，参数要分开。

#### ⚠️⚠️ 她"婉拒"时必须填 `t=0` —— 否则进度照涨

**踩过的坑**：模型台词说「不太行呢……我一个人看书才能静得下来」，
**却仍然填了 `t=3`** → 系统认为"她答应了" → **进度照涨、得失照算**，
玩家看到的是「她明明拒绝了，怎么还在帮她读书」。

**根因是我自己教错的**。早期 prompt 里写着：

> ~~t 这里仍然照填 3 或 4 —— t 只表示「玩家想陪你」这个意图；
> 答不答应、系统怎么判，由你的台词和你们的关系共同决定。~~

而**示例⑥（婉拒场景）示范的正是 `t=3`**：

```
【正确示例⑥】你正在吃饭，但你们还只是「认识的人」，玩家说「我陪你一起吃吧」：
……不用了。我一个人吃就行，你有事就去忙吧。
###DELTA###
-1,-20,30,3        ← ❌ 婉拒却填 3（模型就是照这个学的）
```

**修法**（prompt 两处）：

1. **明确规则**：
   > **如果你在台词里婉拒了，就必须填 `t=0`，不能填 3 / 4！**
   > 因为 `t=3/4` 的含义是「**你答应了、这件事真的发生了**」。
   > ⇒ 答应 → 填 3 或 4；婉拒 → 填 **0**。
2. **修正示例⑥**：`-1,-20,30,3` → **`-1,-20,30,0`**，并就地加注说明为什么。

> **教训**：prompt 里的**示例比规则更有说服力**。
> 规则写对了、示例写反了，模型一定跟示例走。
> **改规则时，务必把示例一起过一遍。**

#### ⚠️⚠️ `#DIMS REF` 的引用参数：**比较和赋值都不可靠**

这是本项目**踩得最惨的一类坑**，出现三次、症状各不相同：

| 症状 | 出错写法 | 真因 |
|---|---|---|
| 界面显示 `（"工作"停下来了）`（带引号） | `IF REF_TOGETHER == "工作"` | 引用参数的值带引号，直接比不相等 |
| **「（停下来了）」反复出现、且没名字** | `ELSEIF REF_TOGETHER != ""` | **模式其实已空，这个判断却仍为真** → 走进"自由行动"分支 → 用空的副本拼出无名字的提示 |
| 陪伴门槛判断失效 | `SIF ... REF_TOGETHER != "工作" ...` | 同上 |

**统一解法：进函数就复制一份干净副本，之后一切比较/显示都用它。**

```erb
#DIMS LLM_TGKIND
LLM_TGKIND = %REF_TOGETHER%
LLM_TGKIND '= REPLACE(LLM_TGKIND, "\"", "")   ; 顺手去掉可能带的引号
...
ELSEIF LLM_TGKIND != ""        ; ✅ 用副本
IF LLM_TGKIND == "工作"        ; ✅ 用副本
```

> **教训**：`#DIMS REF` 只适合"**传进来看一眼**"和"**赋值传出**"，
> **不适合做判断依据**。凡是拿它做 `==` / `!=` 的地方，先落到局部变量再比。
>
> ⚠️ 而且这类 bug 极难自查 —— 语法、括号、引号全对，
> 只有跑起来才表现为"逻辑偶尔不对"，且症状像是**别的**问题。

#### ⚠️ 晕倒判定：**`体力 <= 500` 就会出事，不是 `<= 0`**

查 `EVENTCOMEND.ERB:63-94`（回合末的体力检查）：

```erb
IF BASE:MASTER:体力 <= 500 && ITEM:リバースフェザー
	...                                ; 不死鸟之羽自动救一次
ELSEIF (BASE:MASTER:体力 <= 500 && !GETBIT(TCVAR:TARGET:随便,0)) || BASE:MASTER:体力 <= 0
	PRINTL （体力濒临极限）
	PRINTW 　一天过去了                  ; ← 强制结束当天
	IF BASE:MASTER:体力 <= 0 && !CHK_DATENOW(CFLAG:MASTER:约会中)
		PRINTFORMW %CALLNAME:MASTER%体力不支晕过去了…
		FLAG:気絶中断 = 100 + GET_MAPID(CFLAG:MASTER:現在位置)
	ENDIF
```

| 体力 | 后果 |
|---|---|
| **`<= 500`** | 「（**体力濒临极限**）」→「**一天过去了**」（强制结束当天） |
| **`<= 0`** | 追加「**体力不支晕过去了…**」+ `FLAG:気絶中断`（回地图） |
| `<= 500` 且有**不死鸟之羽** | 自动恢复 300/200，消耗羽毛，不中断 |

**⚠️⚠️ 教训：我们的"太累"阈值原本用的是「上限的 20%」，和游戏的固定 `500` 对不上。**

上限 1000 时 20% = **200**，于是：

> **体力 350** → 我们判"还行、继续陪" → 但游戏判 `350 <= 500` → **濒临极限 + 一天过去了**
> ⇒ 玩家视角就是"我明明还有 350 体力，怎么一退出就倒了"。

**修法**：阈值取 **`MAX(800, 上限/5)`** ——

- **必须能盖住「最大的一次扣减」**：
  `500`（游戏硬线）+ `250`（认真帮忙最大消耗）= **750** → 取整 **800**。
  否则玩家可能在 **499 时被放行、结算完直接跌破 0 晕倒**。
- **上限高时按比例取更保守的值**（`上限/5`）。

```erb
LLM_TIRED_TH = 800
SIF MAXBASE:MASTER:体力 / 5 > LLM_TIRED_TH
	LLM_TIRED_TH = MAXBASE:MASTER:体力 / 5
SIF MAXBASE:MASTER:気力 / 5 > LLM_TIRED_TH
	LLM_TIRED_TH = MAXBASE:MASTER:気力 / 5
```

> **调参轨迹**：最初用"上限的 20%"（上限 1000 时是 200，**体力 350 落在空档里** ——
> 游戏判濒临极限、我们却放行）→ 对齐游戏的 **500** → **700**（看着有余量，
> 其实 `700 - 250 = 450 < 500`，**恰好踩线，等于没留**）→ **800**。
>
> **教训**：留余量不能凭"感觉够"，要**照着最大那次扣减去算**：
> 阈值 ≥ 判罚线 + 单次最大消耗。

> ⚠️ 这个阈值**必须每轮重算**（放在函数开头的初始化段）——
> 陪伴模式下的普通轮次走的是另一个分支，不经过 `t=3/4` 的档位翻译段，
> 放在那里的话读到的是**残留值或 0**。

#### ⚠️ 玩家"累趴"的判断：**统一入口 `@LLM_TOO_TIRED`**

帮忙 / 陪她做事会**在对话中**扣体力气力，而官方的"体力不支"判定在**回合末**
（`EVENTCOMEND.ERB:91-94`：`体力 <= 0` → 「体力不支晕过去了…」+ `FLAG:気絶中断`）。
也就是说**不管的话，你能一边掉体力一边无限互动，直到退出对话才突然晕倒**。

判定抽成**一个函数**，所有 LLM 交互入口共用 —— 避免"这里拦了那里没拦"：

```erb
@LLM_TOO_TIRED
#FUNCTIONS
SIF BASE:MASTER:体力 <= 0
	RETURNF 1        ; 体力见底（比气力严重 —— 会直接触发官方晕倒判定）
SIF BASE:MASTER:気力 <= 0
	RETURNF 2        ; 气力见底
RETURNF 0
```

**覆盖情况**（会发 LLM 请求的路径已全部接入）：

| 入口 | 调用点 | 累趴时的行为 |
|---|---|---|
| `@LLM_CHAT_LOOP` 开场 | 入口检查 | 不开始对话（「你连站都快站不稳了…」/「你已经累得说不出话了…」） |
| `@LLM_CHAT_LOOP` 主循环 | **每轮末尾** | 就地收场 + **清掉陪伴模式**（「你眼前一阵发黑…只能先跟她道别」） |
| `@LLM_REFUSE_TALK` | 函数开头 | **不发请求**，直接用她的口吻给一句保底台词 |
| `@LLM_TOGETHER_TALK` | 函数开头 | **不发请求**，安静跳过（那句只是锦上添花） |

另外两处"软刹车"（阈值是**上限的 20%**，属于**她的体贴**而不是硬拦）：

| 时机 | 行为 |
|---|---|
| **邀请陪伴时** | 「她看你一脸疲惫，让你先去歇会儿」（吃饭/偷吃零食例外 —— 那会回复体力） |
| **陪伴中每轮** | 「她看你实在撑不住了，让你先去歇会儿」+ 结束陪伴 |

> **为什么只拦气力不够**：官方 `COM_ABLE` 清一色只查气力
> （`SIF BASE:MASTER:気力 <= 0 / RETURN 0`），但**帮忙干活扣的是体力** ——
> 所以"帮到体力 0 还在原地聊天"这种情况原来完全没人管。

**她的工作进度会保留**（已推进的部分照常记账），下次再来接着帮即可；
`LLM_TOGETHER` 本身是 `@LLM_CHAT_LOOP` 的局部变量，退出对话自动消失。

#### 帮忙干活的两档：**由模型判断态度**（`t=3` / `t=4`）

陪伴分两档，**由模型按玩家的投入程度判定** —— 不是按"第几次"：

| 档位 | `t` | 时长 | 玩家体力 | 玩家气力 | 信赖 | 进度份额 |
|---|---|---|---|---|---|---|
| **随口陪着**（边聊边搭手） | `3` | **15 分钟** | **−150** | **−30** | **+2** | **9**（约一份） |
| **认真帮忙**（撸起袖子干） | `4` | **30 分钟** | 按職種 | 按職種 | **+5** | **30**（三份） |

> **份额的调参过程**（目标是"**一场对话内真能把她的活干完**"）：
> 最初 `3 / 10` → 翻倍 `6 / 20` → 再 ×1.5 成 **`9 / 30`**。
> 陪伴模式里的普通轮次也用 **9**（相当于"继续随口陪着"），不与邀请那次脱节。
>
> **粗估效果**（技能 0、美铃门番总工作量 3600）：
> - 随口陪着：约 **156 / 轮** → 20 轮约 3100（接近完成）
> - 认真帮忙：约 **450 / 轮** → **约 8 轮就能干完**

prompt 里教模型区分：

```
t=3  玩家要陪着你做手头的事，口气比较随意（「我陪你坐会儿」「边聊边弄吧」）
t=4  玩家要认真帮你做这件事（「我来帮你干」「交给我吧」「我搭把手」）
     ⚠️ 3 和 4 的区别是「投入程度」，不是「要不要陪」——
        口气随意、主要想聊天 → 3；明确说要动手一起做 → 4。
```

**⚠️ 这套档位对「所有陪伴内容」生效** —— 工作、吃饭、看书、发呆…
全部读同一组档位参数（`LLM_STEP` / `LLM_COSTSTEP` / `LLM_ELAPSE` / `LLM_FIX_T` / `LLM_FIX_K` / `LLM_TRUST`），
在进分支前由 `t` 翻译好，所以不会出现"只对工作分档、吃饭不分"的情况。

#### ⚠️ 玩家太累时，她会**拒绝 / 结束陪伴**

两条保护，阈值都是"体力或气力**低于上限的 20%**"：

| 时机 | 行为 |
|---|---|
| **邀请时**（`t=3/4`） | 她会说「**她看你一脸疲惫，让你先去歇会儿**」，不答应 |
| **陪伴中**（每轮） | 她会「**她看你实在撑不住了，让你先去歇会儿**」并**结束陪伴模式** |

**两者都加了「吃饭例外」**：自由行动的 **2 吃饭 / 3 偷吃零食** 本身会恢复体力气力，
所以"累了还继续吃"才是对的，不该被拦。

> 动机：实测玩家会**一路陪着帮到自己昏过去**（因为陪伴没有自动刹车）。
> 加上这两条之后，她会替玩家踩刹车 —— 也符合"角色会关心你"的设定。
> **两种情况都不加负面数值** —— 她是关心，不是生气。

#### 得失明细：所有陪伴都要有

早期只有「帮忙干活」有明细，其他陪伴只有一句「过了 N 分钟」。
现在**统一**：

```
（陪她吃饭，过了 15 分钟）
（体力－40　气力－65　好感度＋2　信赖度＋2　时间－15分钟）
```

能显示的项：**体力 / 气力 / 工作量（你帮的）/ 她自己推进 / 额外好感度 / 信赖度 / 时间经过**。

> ⚠️ 官方的 `SOURCE:歓楽` / `SOURCE:受動` 要等**回合末**才由 `FAVOR_CALC`
> 换算成好感度，对话里算不出来，所以明细里只显示**能立刻确定**的部分。
> 那部分收益会在退出对话后的回合结算时由游戏自己显示。

#### 帮忙干活的效率：为什么是「份额 3」
持续帮忙每轮调用 `@LLM_WORK_DO(角色, 3, 0)`，也就是**约 0.3 次「完整帮忙」**。
这个值是权衡出来的：

| 依据 | 说明 |
|---|---|
| **官方「帮忙干活」其实不花时间** | `@COM304` 里**没有** `TIME +=`，而 `@TRACHECK_TIME` 只给 `SELECTCOM < 200` 加 5 分钟 —— 它定位是"**顺手帮一把**"。所以"每轮都算一次帮忙"本身不离谱 |
| **但不能按"每轮 = 完整一次"** | 份额 10 时，进度会推得太猛，帮忙变成一键通关 |
| **份额 3 的手感** | 每轮推进**约 33**（技能 0 时），配合她自己干的约 30 —— **单轮就能看出进度在动** |

> ⚠️ **基准是单轮，不是"一场"。** 玩家随时能退出，所以判据是
> "**聊一轮有没有感觉**"，而不是"聊满 20 轮能帮掉几成"。
>
> ⚠️ 我最初按「一次帮忙 = 30 分钟」折算成 **1/10**，结果每轮只减少个位数
> （美铃门番总工作量 3600，每轮才 5~10），玩家体感就是"**进度极慢**"。
> **教训：折算前先确认官方那次操作到底花不花时间。**

**进度用百分比显示**，而不是绝对数字：

```
（你继续帮她看门，进度 12%）
```

门番总工作量是 3600，光看「还剩 3161」根本判断不出算多算少；**百分比一眼就懂**。

#### 陪伴之后，她还会**补一句台词**

只有数值提示（「陪她吃饭，过了 30 分钟」）是系统口吻，很干巴。
所以她本人对"有人陪"这件事的反应才是重点 —— 陪伴真的发生时会**追加一次请求**：

```
（你陪她一起发了会儿呆，气力恢复，过了 30 分钟）
灵梦：「……嗯。难得你肯安静一会儿。」
```

**怎么串起来的**（`@LLM_APPLY_DELTA` → `@LLM_CHAT_LOOP` → `@LLM_TOGETHER_TALK`）：

1. `@LLM_APPLY_DELTA` 多了一个**输出参数** `REF_TOGETHER`
   （`#DIMS REF`，**空串 = 没发生**；非空 = 她手头那件事的名字，如「吃饭」）
2. `@LLM_CHAT_LOOP` 在调用后检查它：非空就调 `@LLM_TOGETHER_TALK(角色, 行动名)`
3. 那个函数用**独立的 prompt**（`@LLM_BUILD_TOGETHER_PROMPT`）再要一句话，然后显示

**两个设计上的取舍**：

| 决定 | 理由 |
|---|---|
| **另写一个 prompt，而不是复用主 prompt** | 主 prompt **强制要求**输出 `###DELTA###` 数值块；这次只是补一句反应，**不该再结算一次**（否则同一轮算两遍） |
| **`REF_TOGETHER` 直接传"行动名"而不是"布尔值"** | 调用方事后再取名字会取错 —— 时间推进后她的行动可能**已经结束了**，`FreeAct_Name` 会返回别的（比如刚结束时的"在思考什么"） |

**容错**：

- 请求发不出去（接口问题）→ **安静跳过**。陪伴效果和数值提示都已生效，这一句只是锦上添花
- 模型仍带回了 `###DELTA###` → 用 `@LLM_PARSE_DELTA` **把块抠掉**（保持台词干净），
  但**不应用**其中的数值
- 这一句**记入对话记忆**（第 4 参数传 1）—— 与「拒绝」相反（拒绝不算聊过，那边传 0）

**只在真的发生陪伴时才多花一次请求**（一场对话最多几次），不会明显拖慢节奏。

#### 本次结算明细：把「得了什么、花了什么」也写出来

陪伴/帮忙之后，除了那句提示，还会多打一行**明细**：

```
（陪她吃饭，过了 33 分钟）
（体力－40　气力－65　好感度＋2　信赖度＋1）
```

```
（你帮她干了一会儿活，过了 30 分钟）
（体力－150　气力－5　工作量＋320　信赖度＋5）
```

**怎么算出这些数**：

| 项目 | 来源 | 读法 |
|---|---|---|
| **体力 / 气力** | `DOWNBASE:MASTER:体力/気力` | **调用前后取快照，算差值** |
| **工作量** | `BASE:角色:工作量` | 同上（帮忙时取差值） |
| **好感度** | `CFLAG:角色:2` | 我们直接改的额外加成（+2） |
| **信赖度** | `TFLAG:信頼度管理` | 档位值（+1 / +2 / +5） |
| **时间** | `TIME` | 陪伴推进的 + 对话本身的 3 分钟 |

**两个技术点**：

1. **`DOWNBASE` 是"累积待扣"的，所以差值法成立**
   —— 它由 `@SOURCE_CHECK` 在回合末消费并清零（`SOURCE.ERB:1044-1066`），
   在对话中调用 `"ソース"` 后只是累积、还没真正扣。所以前后差值就是本次的量。
2. **符号方向相反，所以有两个格式化函数**
   - `@LLM_GAIN_COST` —— 消耗类（体力/气力）：`DOWNBASE` **正数=消耗** → 显示「－N」
     （与官方 `SOURCE.ERB` 的显示规则一致：`体力-{DOWNBASE}` / 负数才显示 `体力+`）
   - `@LLM_GAIN_GET` —— 获得类（好感度/工作量）：正数=得到 → 显示「＋N」

**0 值一律跳过**，不显示没变化的项。

**而且每轮都会带上时间经过**：

```
（陪她吃饭，过了 33 分钟）
（体力－40　气力－65　好感度＋2　信赖度＋1　时间－33分钟）
```

普通轮次（没陪伴/帮忙）也会有一行，让人清楚时间确实在走：

```
（好感度＋2　情緒＋20　时间－3分钟）
```

`LLM_DT`（= `TIME - LLM_T0`）就是**这一轮的总时间开销** ——
它同时含"对话本身的 3 分钟"和"陪伴/帮忙额外推进的时间"，
所以一个数就够，也不会漏算。

> ⚠️ **陪伴那一次的总时间 = `LLM_ELAPSE`（如 30 分钟），不是 33。**
>
> 每轮对话本身在 ④b 会固定 `TIME += 3`，所以陪伴分支**只补差额**：
> ```erb
> TIME += MAX(LLM_ELAPSE - 3, 0)     ; 而不是 TIME += LLM_ELAPSE
> ```
> 不补差额的话，"陪她吃饭"会变成 3 + 30 = **33 分钟** ——
> 界面会显示这个别扭的数字，而且和"一次陪伴 = 30 分钟"的直觉对不上。
> （`MAX(…, 0)` 是防她只剩 2 分钟时把时间倒推。）
>
> 时间用的是 `@LLM_GAIN_COST`（消耗版，正数显示成「－N」）——
> 时间流逝算**消耗**，不是收益。

##### ⚠️⚠️ `DOWNBASE` 只是"待扣"，必须**立刻结算** —— 否则等于没扣

这是本项目最隐蔽的一个坑之一：

`DOWNBASE` **不是**"已经扣掉的值"，而是**累积待扣**的暂存量。
真正的减法发生在 `@SOURCE_DOWNBASE`（`SOURCE_EXTRA.ERB:580-581`）：

```erb
BASE:ARG:体力 = LIMIT(BASE:ARG:体力 - DOWNBASE:ARG:体力, 0, MAXBASE:ARG:体力)
BASE:ARG:気力 = LIMIT(BASE:ARG:気力 - DOWNBASE:ARG:気力, 0, MAXBASE:ARG:気力)
```

**而它只在回合结束时由 `@SOURCE_CHECK` 调用**（`SOURCE.ERB:532`）。

**自由对话不是一个回合** —— 所以：

- 界面会显示「体力－75」，但**实际数值一点没少**
- 那笔消耗要等你退出对话、执行下一条指令时才补扣

**修法**：每次往 `DOWNBASE` 里加完，立刻结算 + 清零：

```erb
DOWNBASE:MASTER:体力 += N
DOWNBASE:MASTER:気力 += K
CALL SOURCE_DOWNBASE(MASTER)      ; ← 立刻应用（含限幅 / 酒气 / 疲劳累积）
DOWNBASE:MASTER:体力 = 0          ; ← 必须手动清零！
DOWNBASE:MASTER:気力 = 0
```

> ⚠️ `@SOURCE_DOWNBASE` **不清零** `DOWNBASE`（清零由 `@SOURCE_CHECK` 负责），
> 所以不手动清零的话，**下一轮会把同一笔消耗再扣一次**。
>
> 用官方函数而不是直接改 `BASE:体力`，是因为它还负责：恋人时的打折、
> 酒气减少、以及 `ADD_TIRED` 疲劳累积。

> ⚠️ `LLM_GAIN` **必须每轮清空** —— 陪伴模式跨轮保持，第二轮不会重新结算，
> 不清空就会把**上一轮**的明细原样再显示一遍。

#### ★ 陪伴模式：建立一次，之后一直有效

玩家一旦说了「陪你一起××」，这场对话就**进入陪伴模式**：

- **后续轮次即便不再说「陪你」，也仍然算在陪着**，话题自然围绕这件事展开
- prompt 里会持续出现：
  ```
  【你们正在一起做的事】吃饭
  （你现在正和玩家一起吃饭，这件事还没结束。
    接下来的对话自然围绕它展开就好 —— 边做边聊、随口搭话，
    不用每次都重新确认「要不要一起」，也不用反复道谢。）
  ```
- **直到**：① 玩家退出自由对话 ② 这件事做完了（`Activity_Duration` 归零，会提示「××的事告一段落」）

**状态存在 `LLM_TOGETHER`** —— 它是 `@LLM_CHAT_LOOP` 的**局部变量**，
所以"玩家退出对话"时**自动消失**，不需要任何清理逻辑。

**`REF_TOGETHER` 兼作输入与输出**：

| 进来时 | 出去时 | 含义 |
|---|---|---|
| 空 | 非空 | **刚建立**陪伴模式 → 做完整结算 + 追加一句台词 |
| 非空 | 非空 | 模式续着（玩家又说了"陪你"，但**不重复结算**） |
| 非空 | 空 | 事情做完了 → 退出模式 |
| 空 | 空 | 没在陪 |

> ⚠️ **结算只在第一次建立时做**。否则每轮都跑一次 `"ソース"` 分支，
> 好感度会以"一次完整互动"的量级**连刷**，几轮就爆了。

> ⚠️ **追加台词也只在"刚建立"那一轮发**。判断靠 `LLM_TG_BEFORE`
> （调用 `@LLM_APPLY_DELTA` **之前**记下模式值）——
> 否则模式跨轮保持，会变成**每轮都多发一次请求**。

### 5.5 拒绝对话

**两种时机**：

1. **进门就拒绝** —— 点 `[4]` 后她说一句拒绝台词就走，不进入对话
2. **聊到一半赶人** —— 每轮你发言后判定；命中则**针对你刚说的那句话**拒绝，然后退出

**累积机制**：模型每轮给的愤怒增量会累加到一个"不快计数器"，
攒到 **300** 就触发（按 ±60/轮 约 **5 轮**明显冒犯）。
**说软话可以让它降回去** —— 也就是能被哄好，不是一次激怒就永久拉黑。

阈值在 `@LLM_REFUSE_REASON` 里（`LLM_ANGER_LIMIT = 300`），完整条件见 §8。

### 5.6 对话本身的时长与消耗

自由对话原本**完全不花时间和气力**（可以无限刷）。现在每轮扣一点：

```erb
TIME += 3                                             ; 时间 +3 分钟
BASE:MASTER:気力 = MAX(BASE:MASTER:気力 - 5, 0)       ; 玩家气力 −5
BASE:(LLM_CID):気力 = MAX(BASE:(LLM_CID):気力 - 5, 0) ; 她气力 −5
```

#### 数值是怎么定的

| 参照 | 时间 | 气力（双方各） | 出处 |
|---|---|---|---|
| **官方「一次会话」** | **+10 分钟** | **20** | `COMF300 会話.ERB:105-106` |
| 会话失败 / 尴尬 | +10 分钟 | 100 | `同文件:19-26` |
| 官方「肌肤接触」 | +10 分钟 | 30 | `COMF302 スキンシップ.ERB:80,164` |
| 官方日常指令的时间**众数** | **5 分钟** | — | 统计 `COMF/**` 的 `TIME +=`：5 分钟出现 56 处（最多），其次 10 / 30 / 60 |
| 官方统一计时 | `SELECTCOM < 200` 时 **+5 分钟** | — | `@TRACHECK_TIME`（`TRACHECK.ERB:8-21`），由 `SOURCE_CHECK` 每次调用 |
| **我们的自由对话（每轮）** | **+3 分钟** | **5** | **单轮就比官方日常指令还轻** |

#### 为什么是 3 分钟 / 5 气力 —— **看单轮，不看一场**

> ⚠️⚠️ **设计基准是「单轮」，不是「一场」。**
>
> `@LLM_CHAT_LOOP` 里那个 `SIF LLM_ROUND >= 20` 只是**防止无限聊的上限**，
> **玩家随时可以输入空行退出**。所以配平必须按"**聊一轮**"来：
> 一轮的消耗自己就该说得过去，而不是"聊满 20 轮刚好等于一小时"。
>
> （本项目早期文档多处用"一场 20 轮 = 一小时"论证，那是**错误的基准**，已全部改掉。）

依据：

| 对照 | 结果 |
|---|---|
| 官方日常指令一次 | **5 分钟**（`TRACHECK_TIME` 对 `SELECTCOM < 200`）→ 我们取 **3 分钟**，比它还轻 |
| 官方一次完整会话 | 双方各 **−20 气力**（`COMF300:105-106`）→ 我们只取 **1/4（−5）** |
| 手感 | 聊一轮几乎无感；多聊几轮才累积成可观的开销 —— 这样玩家才**敢开口**，也不会觉得"说句话就掉一大截" |

#### ⚠️ 不消耗体力

官方会话**也只扣气力**（`COMF300` 里没有任何体力的 `DOWNBASE`）。
体力是战斗/性行为的资源，闲聊不该动它。
（**帮忙干活**才是体力活，那是另一套数值，见 §5.4。）

#### 气力耗尽就聊不动了

```erb
IF BASE:MASTER:気力 <= 0
	PRINTFORML 　你已经累得说不出话了。先去休息一下再来吧。
	RETURN 1
ENDIF
```

对齐官方 `@COM_ABLE300`（`SIF BASE:MASTER:気力 <= 0 / RETURN 0`）。

> 刻意**不走** `@LLM_REFUSE_TALK` —— 那是"**她**拒绝你"的台词，
> 用在这里会变成她在嫌弃你累。这里是"你太累了"，该用旁白口吻。

## 6. 架构

### 6.1 两侧分工

| 侧 | 负责 |
|---|---|
| **插件（C#）** | 发 HTTP 请求、维护每角色对话历史、管理接口列表 |
| **ERB** | 组装 prompt、解析回复、显示立绘、裁决数值、判定拒绝 |

**刻意的分工**：所有"要影响游戏"的判断都放在 ERB 侧 —— 插件只做网络与存储，
这样行为可预测，也便于排查。

### 6.2 通信协议（这是要害）

Emuera 的 `CALLSHARP` 有两条硬约束：

1. **同步阻塞，没有 async**
2. **只回填最后一个参数**（中间的参数会被引擎丢掉）

所以：

```
CALLSHARP LLM_CHAT_SEND(角色, system, user, [是否记入历史], 回填)   → 立刻返回请求 id
CALLSHARP LLM_CHAT_POLL(请求id, 回填)
CALLSHARP LLM_CHAT_CANCEL(请求id, 回填)
```

**为什么必须轮询**：ERB 侧不能 `await`。插件收到 `CHAT_SEND` 后
**开后台 Task 发请求并立刻返回**，ERB 侧循环 `CHAT_POLL` 直到有结果或超时。

`CHAT_POLL` 的回填格式（状态码 + 文本拼在**同一个**参数里）：

| 回填 | 含义 |
|---|---|
| `"0"` | 还在等 |
| `"1" + 文本` | 成功 |
| `"-1" + 原因` | 失败 |

> 状态码**不能单独占一个参数** —— 那正是"秒超时"那个 bug 的成因（见避坑清单 5d）。

### 6.3 插件方法一览（18 个）

```
LLM_IS_READY            插件是否就绪
LLM_HAS_FREE_TALK       该角色是否允许自由对话
LLM_HAS_FREE_INTIMATE   该角色是否允许自由亲密（尚未使用）
LLM_CHAT_SEND           发起请求 → 返回 id
LLM_CHAT_POLL           查询结果
LLM_CHAT_CANCEL         取消
LLM_HISTORY_COUNT       该角色的历史条数
LLM_HISTORY_CLEAR       清空该角色的历史
LLM_API_COUNT / TOTAL   可用 / 全部接口条目数
LLM_API_ACTIVE_NAME     当前接口名
LLM_API_INFO / LIST     接口详情
LLM_API_RELOAD          重载 apis.txt
LLM_RELOAD / DEBUG / RAW / DUMP   调试用
```

## 7. 数值映射

| 名称 | 游戏变量 | 单轮幅度 | 其它约束 |
|---|---|---|---|
| **好感度** | `CFLAG:2` | **±3**（分级反应时可到 −5） | **单场累计 ±10**；游戏上限 `0 ~ 1000000` |
| **情緒** | `BASE:情緒` | **±40** | **单场累计 ±200**；上限 `MAXBASE:情緒` |
| **愤怒** | `BASE:憤怒` | **±60**（分级反应时可到 +150） | 上限 `MAXBASE:憤怒` |
| **欲情** | `PALAM:欲情` | **+`PALAMLV:3`**（仅"关系深 + 性骚扰"时） | 无上限变量；**必须用 `PALAMLV` 档位**，见下 |

### 7.1 为什么欲情必须写成 `PALAMLV:N`

`PALAM:欲情` **没有上限变量**（全项目搜不到 `LIMIT`/`MAXPALAM`），
它的"大小"完全由等级阈值数组 `PALAMLV` 表达 ——
**而 `PALAMLV` 有两套完全不同的阈值表**（`初期設定.ERB:63-101`，
取决于 DLC 开关 `MAGIC_DLC_好感亲密重做`）：

| 档 | 默认版 | 重做版 |
|---|---|---|
| 3 | **3000** | **500** |
| 5 | 30000 | 2000 |
| 7 | 100000 | 10000 |
| 9 | 250000 | 50000 |

**⇒ 写死 `+= 3000` 在重做版里是 6 档的量、默认版里只是 3 档，差 6 倍。**
**一律写 `PALAM:角色:欲情 += PALAMLV:3`**（语义是"加 3 档"），两套配置下体感一致。

### 7.2 关系分级反应（`t` 字段）

**原则：模型判断「性质」，ERB 决定「效果」。**
模型不知道也不该知道 `REQUIRED_FAVOR_恋慕 = 3000` 这种门槛
（否则它会在台词里报数字），所以它只输出 `t`，效果由游戏状态决定。

`t=2`（露骨的性骚扰 / 越界）时，`@LLM_APPLY_DELTA` 会**覆盖**模型给的 a/b/c：

| 关系（按优先级） | 效果 | 体感 |
|---|---|---|
| `TALENT:恋慕` / `TALENT:愛欲` | 好感 +1、情緒 **+40**、愤怒 **−30**、**欲情 +`PALAMLV:3`** | **害羞** |
| `TALENT:思慕` 或 好感 ≥ `REQUIRED_FAVOR_思慕`(1500) | 好感 −1、情緒 −20、愤怒 +40 | 尴尬嗔怪 |
| 其余（关系尚浅） | 好感 **−5**、情緒 −40、愤怒 **+150** | **讨厌 + 明显愤怒** |

> 愤怒 +150 ⇒ 两轮就够到拒绝阈值 300（陌生人被骚扰直接翻脸）；
> 思慕档 +40 ⇒ 约 8 轮；恋慕档 −30 ⇒ 不累积反而消解。

**设计依据**：照抄官方的「陥落素質」（`SOURCE_EXTRA.ERB:107-140`）——
官方让 恋慕 ×0.2 / 愛欲 ×0.3 / 思慕 ×0.5 地**消解**累积的负面，
即"行为本身产生的反感一样，但关系深的人不记仇"。我们换成分档效果表。

### 7.3 跨对话「真实记录」：`TCVAR:角色:336`

"不快"存在角色的 `TCVAR` 里，**关掉对话也不会忘**：

```
每次重新搭话 → 先按关系消解一次（恋慕 ×0.2 / 愛欲 ×0.3 / 思慕 ×0.5）
              → 再自然消退 50
累积到 300   → 本场拒绝（沿用原阈值）
```

**⇒ 关系越深越容易消气**：恋人几天就翻篇，陌生人会把上次的不愉快带进下一次。

- **编号 336 的选法**：335=「打西瓜参加」、341 起是特殊 Buff、
  **350~399 是「口上用確保領域」不能占** ⇒ 336~340 空闲；容量 `TCVAR,1000`
- **刻意不写 `MARK:反発刻印`** —— 那个在官方设定里几乎不可逆
  （刻印 2/3 连道歉都消不掉），一旦写进去等于永久拉黑

**这些数字不是拍脑袋定的**，是对齐游戏自己尺度的结果（详见 `LLM对话数值设计调研.md`）：

| 对照 | 好感度 | 情緒 | 愤怒 |
|---|---|---|---|
| 官方一次「会話」 | +4 ~ +10 | +30 ~ +200 | 0 |
| 官方一次轻冒犯（捏脸/戳脸） | — | — | +139 ~ +231 |
| 官方「被无视」 | 中断 | — | **+347** |
| **我们的对话（单轮）** | **±3** | **±40** | **±60** |
| **自然衰减（每 10 分钟）** | — | **40 ~ 120** | **50** |

> 最后一行是关键：**旧值 ±2 只有自然衰减的 1/20 ~ 1/60** ——
> 聊 20 轮攒的那点情绪，玩家走一趟路就掉光了，等于没给。
> （2026-09 依据调研调整过一次，旧值见文档历史。）

- 上限全部取自**游戏自己的界**：`MAXBASE:角色:*`（从 `CSV\Chara\Chara*.csv` 读，
  **各角色不同**，所以绝不硬编码 1500/1000）；好感度的 `LIMIT(x,0,1000000)`
  抄自 `TRACHECK_好感度上昇処理.ERB:415`
- `PALAM:欲情` **刻意不碰**（它没有官方上限变量，风险高）
- 数值一改，**立绘表情会自动跟着变** —— 因为立绘用的正是这些量（见 §9）

## 8. 拒绝判定条件

顺序即优先级（`@LLM_REFUSE_REASON`）：

| # | 条件 | 含义 |
|---|---|---|
| 1 | `CFLAG:角色:睡眠` | 睡着了，被吵醒很烦 |
| 2 | `CFLAG:角色:ブチギレ` | 暴怒（游戏里最强的愤怒态） |
| 3 | `MARK:角色:反発刻印 >= 3` | 对玩家有反感刻印 —— **只在刻印 3 时拒绝**（对齐官方 `COMF300:31`） |
| 4 | `BASE:角色:憤怒 >= 500` | 正在气头上（500 是游戏自己的阈值，见 `QOL_IMAGE.ERB:1494`） |
| 5 | 本场累积不快 `>= 300` | **聊到一半被激怒**（≈ 官方一次「被无视」+347 的量；按 ±60/轮 约 5 轮明显冒犯） |
| 6 | `心情 == -1` **且** `情緒 < MAXBASE/10` **且** `好感 < REQUIRED_FAVOR_思慕` | 真的没心情（**三个条件必须同时满足**） |

### 8.1 ⚠️ 这条判定踩过两次「阈值过严」，都会让玩家觉得"每个角色都不理我"

| 问题 | 原来 | 现在 | 为什么原来看起来"合理" |
|---|---|---|---|
| 反感刻印 | `MARK:反発刻印`（**任意非 0**） | `>= 3` | 官方只挡刻印 3；写"非 0"会把刚有 1 级刻印的也一起挡掉 |
| 情绪阈值 | `情緒 < MAXBASE/3`（=500） | `< MAXBASE/10` + 加两个条件 | **500 几乎总是成立** —— 官方自己保底才 `MAX(情緒, 300)`（`情事発覚.ERB:392`），而自然衰减**每次行动掉 40~120**、一次会话才涨 30~200 |

**教训**：这几条都是我们**自己加的**（官方「会話」指令只判反感刻印和会话累积值），
所以尺度得自己拿捏。**宁可宽松，也别挡住正常对话** —— 拒绝功能太严的代价
是玩家直接不想用这个系统了。

> 想调松/调紧就改 `@LLM_REFUSE_REASON` 里那几个判断，注释里写清了每个阈值的来历。

**判定完全在本地** —— 不看模型脸色，行为可预测。
模型只能通过"愤怒增减"间接影响第 5 条，最终裁决仍在这里。

## 9. 关键设计决策（都是踩坑换来的）

### 9.1 persona 用游戏自己的口上，不另写人设

调用游戏现成的口上调度接口拿到该角色**当前生效**的剧本标签与说明，
塞进 prompt。好处：

- 不需要为几十个角色各写一份人设
- **和游戏内表现天然一致** —— 玩家在别处看到的口上风格，就是对话里的风格
- 换服装/换剧本时会自动跟着变

### 9.2 数值裁决权在 ERB，不在模型

模型给的只是"建议值"。所有钳制、上限、单场累计都在 ERB 侧做。
**理由**：模型会漂移、会给出离谱数字，绝不能让它直接写游戏变量。

### 9.3 拒绝判据本地化

"愿不愿意说话"由游戏状态决定，不由模型决定。**理由**：可预测、可复现、
不受模型心情影响；模型只负责**把拒绝说得像她本人**。

### 9.4 尽量不用 `.ERH` 全局变量

本项目遇到过"`.ERH` 全局值莫名失效"的现象（未完全查明），
而其症状极其难查。因此当前实现：

- 跨函数传值一律走 **`REF` 参数**
- 需要跨轮次保留的量（好感度累计、不快累积）做成**函数内局部变量**
- 只有确实需要全局的才放 `.ERH`

### 9.5 立绘交给游戏的显示层

`@PRINT_FACE` / `@PRINT_FIGURE` 内部已经处理了资源名解析、设置开关检查、
各种回退。**不要在外面重复判断** —— 我曾加过一层 `GET_BASE_RESOURCE`
资源校验，结果它误判成"没有图"，整个立绘被跳过（表现：立绘位置什么都没有）。

> **教训：不要替游戏的显示层做它已经做好的判断。**

### 9.6 数值提示改为"始终显示"

最初设计成"全 0 时静默"。结果玩家无法区分
「模型给了 0,0,0」/「模型没给块」/「联动根本没在跑」—— 三种情况界面上一模一样。
现在始终给一行反馈。

## 10. Prompt 结构

```
你正在扮演 eraTW 中的角色…
【角色】<名字>
你的名字就是「<名字>」…
【本作对该角色的既定诠释（persona 来源）】<口上剧本标签 + 说明>
【与玩家的关系】<初次见面 / 认识 / 思慕 / 恋慕 / 恋人>
【当前态度】<合意状态>
【当前状态】<情绪描述：心情很好 / 情绪低落 / 有点烦躁 / 正在气头上 / 醉醺醺…>
【现在所在的地方】<大地图名>的<房间名>        ← 位置感知
（可以自然地提到所处环境，但不要生硬地报地名。）

【回复格式（最重要 · 每次都必须严格遵守）】
  第 1 段：台词
  第 2 段：另起一行写数值块
  ###DELTA###
  a,b,c          a=好感度(-3~+3) b=情緒(-40~+40) c=愤怒(-60~+60)
  【正确示例①】平淡 0,0,0
  【正确示例②】愉快 2,40,0
  【正确示例③】冒犯 -2,0,60
  数值判定规则（含"b/c 别缩手缩脚"的强调）

【硬性要求】1~6（只写台词 / 中文 / 把握亲密度 / 不声称状态变化 /
            不提 AI / 不要省略数值块）
```

**⚠️ 格式要求刻意放在【硬性要求】之前，并且给了三个完整示例（含一个负面例子）。**
最初只写在末尾、没有例子，实测模型**完全忽略**（日志里回复连 `###DELTA###` 都没有）。
对"必须附带额外格式"这类要求，**位置靠前 + 完整示例 + 明确禁止省略** 三样一起上才管用。

### 10.1 位置感知 + 行动感知 + 同场角色：她知道现在在哪、在做什么、身边有谁

**位置**（用游戏自己的接口取，不自己拼位置编号）：

```erb
LLM_MP        = GET_MAPID(CFLAG:(CID):現在位置)              ; #FUNCTION，数值
LLM_MAPNAME   = %GET_MAPNAME(LLM_MP)%                        ; #FUNCTIONS → "博麗神社"
LLM_PLACENAME = %GET_PLACENAME(CFLAG:(CID):現在位置, 0)%     ; #FUNCTIONS → 房间名
LLM_PLACE     = %LLM_MAPNAME%
SIF LLM_PLACENAME != "" && LLM_PLACENAME != LLM_MAPNAME
	LLM_PLACE += @"的%LLM_PLACENAME%"
```

- `GET_MAPID(位置)` = `位置 / 100`；`GET_MAPNAME(地图ID)` 给大地图名
- `GET_PLACENAME(位置, 0)` 内部**已经处理**了隙间空间、据点、其它地图等情况 —— 直接信它
- 房间名与地图名重复时不重复啰嗦（有些地点名就等于地图名）

**行动** —— ⚠️ **有两个不同来源，容易只找到其中一个**：

| 来源 | 含义 | 声明位置 |
|---|---|---|
| **① `Activity_Type:角色`**（配 `Activity_Duration:角色` > 0） | **她自己正在做的"自由行动"** —— 吃饭、看书、钓鱼、喝酒… | `DIM.ERH:415-416` |
| **② `CFLAG:角色:行動 == 5` + `CFLAG:角色:職種`** | **"工作"**（打工/被安排做的事） | `CFLAG.csv`（行動=325、職種=350） |

- **两者互斥**：`@自由行動条件` 要求 `CFLAG:ARG:行動 == 0` 才可能发生自由行动（`MOVEMENT_自由行動.ERB:91`）
- **① 优先级更高** —— 它才是"当下"最准的（正在看的书、正在吃的饭）
- `CFLAG:行動` **只有两个值**：`0` = 空闲、`5` = 在做事

**① 自由行动编号 → 描述**（来源：各 `FREE_ACT_*.ERB` 的头注释；

| 1 | 正在玩 | 11 | 正在做实验 |

**② 工作 → 描述（用官方 `@GET_JOBNAME`，**不要按職種猜**）**：

```erb
	LLM_ACT = @"正在%LLM_ACT%"
```

`@GET_JOBNAME(角色)` 定义在 `JOB_仕事内容.ERB:1249`，
是**游戏自己显示工作名用的接口** —— 官方那句
`PRINTFORMW %CALLNAME:ARG%的%GET_JOBNAME(ARG)%结束了。`（`:256`）就是这么用的。
它还支持 `CUSTOM_JOB_DESC` 自定义工作名。

> ### ⚠️ 为什么不能按職種翻译（这里踩过坑）
>
> `CFLAG:職種`（`JOB_*`）只是**粗分类**，同一个值涵盖**完全不同**的工作。
> 最典型的是 **`JOB_戦闘`(42)**：
>
> | 角色 | 实际工作 | 出处 |
> |---|---|---|
> | **美铃** | **门番（守门）** | `JOB_仕事内容.ERB:637` |
> | 魔理沙 | 训练 / 发掘作业 | `:1277-1281` |
> | 萃香 | 训练 / 喝酒 | `:1271-1276` |
>
> 我最初把它一律翻成「**正在练武**」—— 结果**美铃守门时，LLM 理解成"她在练拳"**，
> 台词就跟着跑偏了。
>
> **教训：涉及"游戏自己也有说法"的东西，先找官方接口，别自己造词。**

| 其它情况 | 注入的描述 |
|---|---|
| `CFLAG:睡眠` | 正在睡觉（刚被吵醒） |
| `BATHROOM(CFLAG:角色:現在位置)` | 正在浴室里（**地点判定**，见下） |
| `CFLAG:陪睡中` | 正躺着休息 |
| 其余（都为空闲） | **不注入这一行**（空着比写"闲着"好） |

##### 「今日作息」不是写死的表 —— 它读的是游戏实时值

注入内容形如：

```
【你今天的安排】今天是周三，你今天要从6时0分上到12时0分；你平时7时0分起床、23时0分睡觉
```

**每一项的来源都是"游戏已经算好的当前值"**，所以天然与日期/星期配套：

| 项 | 来源 | 为什么会跟着日期变 |
|---|---|---|
| **周几** | `@GET_DAY_CN()`（`日時天候管理.ERB:291`，返回"日/一/二…"） | 直接读 `DAY` |
| **上下班时段** | `TCVAR:工作開始`(325) / `工作結束`(326) | 由 `@仕事内容設定` 按**当天星期**重算（`JOB_仕事内容.ERB:32`，注释写着"MOVEMENT 每次调用时更新"） |
| **休息日** | `@CHARA_HOLIDAY(角色, 1)`（`JOB_仕事内容.ERB:9`） | 官方实时查询，**纯查询无副作用** |
| **起床/就寝** | `CFLAG:起床時間`(355) / `就寝時間`(354) | 角色固有属性，来自 CSV（`UPDATE_MAIN.ERB:447`） |

> ⚠️ **取不到的是「一周固定安排」**：它不是数据，而是**硬编码在
> `@仕事内容設定` 里的条件分支**（`YOUBI_MATCH(DAY, "月水")` 之类，上百处）。
> 要"预测明天"就得改 `DAY` 全局再还原一堆 `TCVAR`，风险不值当，所以没做。
>
> **但因为我们读的是"游戏已经按星期算好的结果"，实际效果和"读了排班表"是一样的** ——
> 不会出现"表里写周一、今天却是周三"。

**判定优先级**（越靠前越"当下"、越优先）：
```
睡眠 → 浴室 → 自由行动(Activity_Type) → 工作 → 陪睡
```

##### ⚠️⚠️ 两个"状态标志滞后"的坑

注入行动时必须看**真实进度**，不能只看状态标志 —— 因为游戏的状态标志**要等回合末才更新**：

| 标志 | 滞后的原因 | 正确判据 |
|---|---|---|
| `Activity_Type`（自由行动） | 行动跑完时 `Activity_Duration` 归零，但 `Type` 还留着 | **必须同时判 `Activity_Duration`** |
| `CFLAG:行動 == 5`（工作） | 工作量归零后要等 `@SLEEP`（`SLEEP.ERB:151-156`）或 `@JOB_仕事開始終了処理` 才清 | **必须同时判 `BASE:工作量 > 0`** |

**不特判的后果**：自由对话里我们已经推进时间、把工作量扣到 0，
但 `CFLAG:行動` 还是 5 → 注入给模型的是「你现在正在做的事：**正在门番**」→
模型继续演"我还在守门"，而玩家看到活已经干完了。**实测就是这个症状。**

修法（工作那一路）：

```erb
IF BASE:(LLM_CID):工作量 <= 0
	LLM_ACT = "刚把手头的活干完，正在收拾东西"
ELSE
	LLM_ACT = %GET_JOBNAME(LLM_CID)%
	...
ENDIF
```

**浴室那一项用游戏自己的地点判定** `@BATHROOM`（`PLACE_拠点共通.ERB:333`）：

- ⚠️ **必须显式传角色的位置**。`BATHROOM()` **不带参数时默认取
  `CFLAG:MASTER:現在位置`**（`同文件:337-338`）—— 那是**主角**的位置，
  直接写 `BATHROOM()` 会误判成"你在浴室"
- 它内部还带 `IN_HOME` 检查，所以**只有据点内的浴室**才算 —— 直接信它
- 之所以放在"自由行动"**之前**：地点比行动更具体。
  她在浴室时也可能有 `Activity_Type`（浴室在据点内、满足 `AT_HOME`），
  但"在浴室"显然更能说明此刻的状态

> ⚠️ **本作没有现成的"职业名"接口**：`DIM.ERH` 里虽然声明了 `JOB_NAME`，
> 但**全项目没有任何地方使用或填充它**（是旧补丁的遗留）；
> `COMF304 仕事を手伝う.ERB` 里也是硬编码的 `CASE JOB_*` 文本。
> 所以職種那张表是自己写的 —— 反正只有 17 项。
> 自由行动的编号含义则来自各 `FREE_ACT_*.ERB` 的头注释。

**prompt 里的呈现**：

```
【现在所在的地方】博麗神社的xxx
【同一个房间里还有】魔理沙、咲夜
【你现在正在做的事】正在读书学习
（可以自然地提到所处环境、手头的事、以及房间里的其他人 ——
  有人在场时可以因此收敛一点；但只准演你自己，
  不要替别人说话、也不要编造她们的台词或反应。
  另外不要生硬地报地名或汇报日程。）
（如果这是对话的第一句，最好就用你手头正在做的事当话题开头。）
```

最后那句是**特意为开场白加的** —— 否则她每次开场都只会干巴巴地说"有事吗"。

#### 同场角色是怎么取到的

做法照抄口上作者的标准套路（`M_KOJO_K73_1_函数.ERB:65-72` 的 `@K73_BESTIE_AROUND`）：

```erb
FOR LOCAL, 1, CHARANUM
	SIF LOCAL == LLM_CID
		CONTINUE                                   ; 排除自己
	SIF CFLAG:(LLM_CID):現在位置 != CFLAG:LOCAL:現在位置
		CONTINUE                                   ; 只留同房间的
	...
	LLM_OTHERS += %CALLNAME:LOCAL%
NEXT
```

三个要点：

1. **`FOR LOCAL`** —— `LOCAL` 是本作到处在用的**引擎内建局部变量**，不会和 `LLM_` 前缀的
   自定义局部冲突（但用之前要确认本函数别处没占用 `LOCAL`）
2. **从 1 开始遍历，不是 0** —— **0 是 MASTER（玩家）**，不该出现在"其他角色"里
3. **最多列 4 个** —— prompt 不必点名一屋子人，也免得串太长

**同时加了一条约束**（很重要）：

> 但**只准演你自己** —— 不要替别人说话、不要编造她们的台词或反应。

否则模型看到"房间里还有魔理沙"，很可能会**替魔理沙也写一句台词**，
那就变成一个 LLM 在演两个角色了。

> ⚠️ `#LOCALSSIZE` 因此从 10 提到 **14**（字符串局部已有 11 个）。

#### 日程感：她知道"自己快没空了"

游戏里每个角色都有自己的作息，不说的话她会陪你聊到天亮。
数据都是现成的（逐角色在 CSV 与 `@JOB_仕事内容` 里定义）：

| 变量 | 含义 |
|---|---|
| `CFLAG:角色:就寝時間` / `起床時間` | 作息（分钟制 0~1440） |
| `TCVAR:角色:工作開始` / `工作結束` | 工作时段；**`-1` 表示今天休息** |
| `TIME`（= `TIME:0`） | 当前时间 |

判据照抄官方的通用搭话逻辑（`ANOTHER_TALK.ERB:36-44`）—— 它会给
"30 分钟内要上班 / 要睡觉"分别走不同台词分支。**我们放宽到 60 分钟**：

```erb
; ① 马上要上班（休息日不算）
IF TCVAR:(CID):工作開始 >= 0 && TCVAR:(CID):工作開始 - TIME > 0 && TCVAR:(CID):工作開始 - TIME <= 60
	LLM_SCHED = "你马上就要去上班了"
; ② 马上要睡觉
ELSEIF CFLAG:(CID):就寝時間 - TIME > 0 && CFLAG:(CID):就寝時間 - TIME <= 60
	LLM_SCHED = "你马上就要到睡觉时间了，已经开始犯困"
; ③ 已经过了就寝时间（她还醒着 = 被你拖住的）
ELSEIF CFLAG:(CID):就寝時間 > 0 && (TIME > CFLAG:(CID):就寝時間 || TIME < CFLAG:(CID):起床時間)
	LLM_SCHED = "现在已经过了你平时的睡觉时间，你很困，只是还没走"
ENDIF
```

**为什么放宽到 60 分钟而不是官方的 30**：因为**聊一轮就过去 3 分钟**（见 §5.6），
随便聊十几轮就是半小时以上 —— "还有一小时"才是真正需要提醒玩家的提前量。

> ⚠️ 条件 ③ 特意加了 `就寝時間 > 0` 保护：万一该字段是 0（调试重置等），
> `TIME > 0` 会**恒真**，变成每轮都在喊"你该睡了"。
> （这类"阈值恒成立"的坑本项目已经踩过三次，见 §8.1 与 §10.2.1。）

**prompt 里这样呈现**：

```
【时间上的事】你马上就要到睡觉时间了，已经开始犯困
（⚠️ 如果上面出现了【时间上的事】，说明你手头的时间确实不多了 ——
  可以自然地带一句（例如「我该去睡了」「等下还得去干活」），
  或者显得心不在焉；但不必每句都提，也别把时间说得很精确。）
```

**刻意不强制结束对话** —— 官方 `ANOTHER_TALK` 到点时也只是**换台词**，
不是赶人走。她"真的去睡了"由游戏自己的作息系统处理
（`CFLAG:睡眠` 一置位，下次搭话就会被 `@LLM_REFUSE_REASON` 挡下，机制自然闭环）。

### 10.2 情绪：把数值转成语义描述，而不是喂数字

模型看不懂「`BASE:情緒=1200`」是什么意思，但看得懂「心情很好，兴致很高」。
所以 `@LLM_BUILD_SYSTEM_PROMPT` 里把各项数值**分档转换成描述**再注入：

| 条件 | 描述 |
|---|---|
| `情緒 >= MAXBASE*7/10` | 心情很好，兴致很高 |
| `情緒` 在 `MAXBASE/3 ~ MAXBASE*7/10` | 心情还算不错 |
| `理性 <= MAXBASE/10` | 有些心不在焉 |
| `憤怒 >= 300`（未到 500） | 有点烦躁，耐心不多 |
| `憤怒 >= 500` | 正在气头上，随时会发火 |
| `TCVAR:烂醉` / `睡眠` / `発情` / `媚薬` | 醉醺醺的 / 睡着的 / 情动难耐 / 被媚药影响 |
| **其余情况** | **「平静」** —— 不注入任何负面描述 |

**顺序即优先级**（靠后的覆盖靠前的，越"强势"的状态越靠后）。

> 为什么给描述而不是数字：数值对模型无意义，而且容易被角色"报出来"
> （她会说"我的好感度是 3000"这种 OOC 台词）。

#### ⚠️ 10.2.1 情绪档**只做加分项，不做减分项** —— 这是踩过坑的

原来这里有一条：

```erb
SIF BASE:(LLM_CID):情緒 <= MAXBASE:(LLM_CID):情緒 / 5     ; = 300
	LLM_MOOD = "情绪低落，提不起劲"
```

结果**几乎每轮都命中**，她句句都没精神，看起来像坏了。

**原因：`BASE:情緒` 的基线极低。**

| 事实 | 出处 |
|---|---|
| `BASE:情緒` **根本没有初始化**（默认 0） | 全项目搜不到初始化赋值 |
| 自然衰减**每次行动掉 40~120** | `BASE自然変動.ERB:21` |
| 一次会话才涨 30~200 | `TRACHECK_好感度上昇処理.ERB:224` |
| 官方唯一的"保底"写法是 `MAX(BASE:情緒, 300)` | `情事発覚.ERB:392` |

**⇒ 300 在作者眼里已经算"不低"了。** 拿它当"低落"的门槛，
等于给所有角色永久贴了个"没精神"的标签。

**两条规则**（同样适用于本项目其他按 `MAXBASE` 比例设阈值的地方）：

1. **情绪档只做加分项** —— 高了才描述"心情好"，低了**保持中性**。
   "真的不想说话"由 `@LLM_REFUSE_REASON` 那个独立机制去管，
   **不该靠一个形容词让模型自己演"没精神"**。
2. **设阈值前先查该变量的实际分布**，别假设"满值的一半就是中等"。
   本作很多 BASE 值长期在低位（衰减快、增长慢）。

**同一个坑还出现在 `CFLAG:態度`（见下）和 `@LLM_REFUSE_REASON`（见 §8.1）。**

#### ⚠️ 10.2.2 `CFLAG:態度` 不是"她对你这个人的态度"

`CFLAG:角色:6`（`CFLAG_態度`）的来源是 `ATTITUDE.ERB:85-94`：

```
合意判定 >= 500 → 3    >= 300 → 2    >= 150 → 1    否则 → 0
```

而 `合意判定` 是**用于性行为指令成否**的累积值。
所以这个字段实际是「**性方面的合意程度**」，跟日常聊天毫无关系。

原来把它写成「冷淡 / 勉强接受 / 愿意配合 / 主动迎合」——
**0 档叫"冷淡"是语义错误**：模型会理解成"她对这个玩家很冷淡"，
于是句句端着（这是"角色没精神"的第二个来源）。

现在改成准确的措辞，并在 prompt 里说明它只管亲密那一块：

```
【对亲密举动的接受程度】对你还没有那方面的意思
（这一项只管亲密 / 身体接触那一块，不代表你对玩家的整体态度；
  就算这里是「还没有那方面的意思」，日常闲聊也该照常自然，不要因此变得冷淡。）
```

### 10.3 语气约束：让 LLM 说话像那个角色

**问题**：光靠 persona（剧本名 + 说明文字）**约束不住语气** ——
模型看不到那个角色"实际怎么说话"，只会输出中性的通用 AI 腔。

**解法：把游戏自己的两个语气维度翻译成人话注入。**

游戏一直为每个角色维护着这两项（`CSV\Chara\Chara*.csv` 里逐角色设置）：

| 变量 | 编号 | 含义 |
|---|---|---|
| `CFLAG:角色:口調` | **391** | 句尾风格（6 种） |
| `CFLAG:角色:性格傾向` | **560** | 2=強気系（强势）/ 4=真面目系（认真） |

`口調` 的取值与用途见 `COMF484 スイカ割り.ERB:893-912` 的 `SELECTCASE`
（角色 CSV 里也直接写了注释，如 `2;～だよ系`）：

| 值 | 风格 | 注入的描述 | 例子（该角色） |
|---|---|---|---|
| 0 | `～のよ`系 | 女性化的口语腔，句尾带「～哦/～呢/～啦」 | **灵梦**、紫、幽香、辉夜 |
| 1 | `～です`系 | 礼貌的敬体，但不卑不亢 | 咲夜、妖梦、早苗、永琳 |
| 2 | `～だよ`系 | 直率的常体，不用敬语 | 琪露诺、橙、小伞 |
| 3 | `～だぞ`系 | 粗犷豪爽，带江湖气 | 萃香、蓝、妹红、勇仪 |
| 4 | `～のじゃ`系 | 老人口吻 | 隐岐山、紫（部分） |
| 5 | 無口系 | 沉默寡言，短句 + 省略号 | 小兎姫、Sagume |

`性格傾向` 目前只确证了 `2`（强势）和 `4`（认真）两个取值，
其余**不加描述**（宁缺勿错）。

**实现**：抽成 `@LLM_TONE_OF(角色, REF_TONE)`，**主 prompt 与拒绝 prompt 共用** ——
否则她拒绝时会突然变回中性的 AI 腔。

**同时在 prompt 里加了具体的风格禁令**（比"请符合角色性格"有效得多）：

```
3. ⚠️ 说话方式必须严格照上面【说话方式】那一行来。
   · 用口语短句，不要书面语、不要新闻腔或说明书式的长句。
   · 带语气词（哦/呢/啦/嘛/哼/啧…），该省略主语就省略。
   · 可以用省略号、破折号、反问来表达情绪。
   · 绝对不要「您好」「有什么可以帮您」「很高兴为您服务」这类客服腔。
   · 不要堆砌成语或华丽辞藻 —— 日常对话里没人那样说话。
   · 宁可口气夸张一点，也不要写成中性的通用回答。
```

**另一个杠杆：`temperature`**

`apis.txt` 里已从 `0.8` 调到 **`0.65`**（降低随机性 → 更贴角色）。
这是**限制语气发散最直接的手段**，但别调太低（低于 0.5 会变得呆板重复）。
想更自由就调回去，范围建议 `0.6 ~ 0.9`。

> ⚠️ 改 `apis.txt` 后**不用重启游戏** —— 在菜单里点 `[1] 接口列表 / 重载 apis.txt` 即可生效。

## 11. 排错手册

### 11.1 先做这两件事

1. **点 `[5] 自检`** —— 14 项 `EXISTFUNCTION`，哪项显示"缺失"就是它没被注册
2. **看日志**：
   - `plugins/LLMBridge/debug.log` —— 请求/响应（`CHAT-SEND` / `CHAT-OK` / `CHAT-FAIL`）
   - 根目录 `debug_log.log` —— 引擎捕获的异常（**只有真出错时才生成**）

### 11.2 症状 → 原因对照表

| 症状 | 最可能的原因 | 去哪看 |
|---|---|---|
| 点 `[4]` 没反应、什么都没打印 | `SIF` 后跟了多行（后面几行无条件执行 → 菜单直接退出） | 避坑清单 **5j** |
| 点 `[4]` 无输出但**函数自检是 OK** | 同上；`TRYCALLFORM` 会吞掉异常，所以没有报错 | 避坑清单 5j |
| 台词显示成 `REPLACE(REF_TEXT, "  ", " ")` | 字符串函数裸写在 `=` 右侧 | 避坑清单 **5e** |
| 模型拿到的是 `" + 灵梦 + "` | 变量当独立 `+` 项拼接 | 避坑清单 **5f** |
| 所有角色 OOC / 自称别的角色 | 同上（persona 没正确送进 prompt） | 避坑清单 5f |
| **秒超时** | `REF` 缺失（状态码传不回来） | 避坑清单 **5b** |
| 一直"接口返回了空内容" | 模型的思考模式把 `content` 挤空 | 插件侧已强制 `thinking: disabled` |
| `No native method LLM_* found` | DLL 被残留的游戏实例锁住 | 插件 README §8 |
| `无法解析的标识符"XXX"` | ① 本作没有这个函数（如 `TRIM`→`TRIM_STRING`）② 变量没 `#DIM` | 避坑清单 **5g / 5h** |
| 参数位置报"标识符"错 | 裸文本当参数（必须加引号） | 避坑清单 **5i** |
| 立绘不显示 | 游戏设置里「显示立绘」或「对话或事件中的配图」关着 | 游戏内设置 |
| 看得到台词但没数值提示 | 模型没给结算块，或给了全 0 | §5.3 的三种显示 |
| 加载时有 Lv1/Lv2 警告 | 逐个按避坑清单对号 | 避坑清单 §0 |

### 11.3 改完 ERB 必做的自查

`LLM_ERB语法避坑.md` 的 §0 列了完整流程，核心是四条：

1. `erb_check.py`（**注意：对含多函数块的文件会误报，不能当唯一判据**）
2. **跨行字符串扫描**（引号奇偶）—— 跨物理行的 `@"…"` 会让**整个游戏停止运行**
3. **`SIF` 多行扫描** —— 这一条最容易漏
4. **旧式拼接扫描**（`+ %变量%`）

## 14. 数值与开发备忘

- **判定"改动是否生效"**：看菜单标题的 `[build N]`
- **插件的 DLL 必须直接在 `plugins/` 根目录**（`LoadPlugins` 不递归）
- **改完插件要重新编译**：`powershell -ExecutionPolicy Bypass -File plugins\LLMBridge\src\build.ps1`
  （数值/对话功能**不需要**改插件）
- **`plugins/` 下的数据文件**（`tw_csv_chs.xml`、`tw_taste_chs.xml`、`bbas_dataset.xml`、
  `schema.xml`、`qol_data.db`）是 mod 依赖，**不可删除**
- **密钥安全**：`apis.txt` 含明文密钥，不要分享/提交到公开仓库；
  一旦泄露请到服务商后台轮换
