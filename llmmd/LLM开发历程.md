## 7. 请求失败的处理策略（★ 已改进）

**状态**：✅ **已实现**（2026-09）—— 之前是"一次失败就退出对话"，现在会**自动重试**

### 起因：一次实际故障

玩家和美铃聊「一起站岗」时**对话突然被弹出**。查 `debug.log`：

```
23:37:43  CHAT-SEND id=3
23:38:02  CHAT-FAIL id=3  网络错误：An error occurred while sending the request.
              ex=System.Net.Http.HttpRequestException
```

**间隔 19 秒** ⇒ **不是超时**（插件 HTTP 超时 60 秒、轮询上限 90 秒都够），
是**连接被中断**（服务端掐断 / 网络抖动）。

**而当时的处理是**：

```erb
IF LLM_STATE != 1
	PRINTFORML 　[出错] %LLM_OUT%
	CALL LLM_SHOW_API_HINT
	BREAK                       ← 一次网络抖动就把整场对话踢掉
ENDIF
```

⇒ **策略太脆** —— 瞬时故障不该让玩家丢掉整段对话。

### 改法：带自动重试

```erb
LLM_SEND_OK = 0
FOR LLM_TRY, 1, 4               ; 首次 + 2 次重试
	CALLSHARP LLM_CHAT_SEND(...)
	SIF TOINT(LLM_TMP) <= 0
		CONTINUE
	CALL LLM_POLL(...)
	SIF LLM_STATE == 1
		LLM_SEND_OK = 1
	SIF LLM_SEND_OK
		BREAK
	SIF LLM_STATE == 0          ; 超时 → 不重试
		BREAK
	SIF LLM_TRY < 3
		PRINTFORML 　（连接抖了一下，正在重试 %LLM_TRY%／2 ……）
NEXT
```

**三个刻意的设计选择**：

1. **只重试「网络/接口错误」，不重试「超时」** ——
   超时的含义是"服务器半天不回"，再发一次只会等更久。
2. **重试不记入对话历史**（`recordHistory` 传 0）——
   失败的那次没有台词，不该污染上下文。
3. **最多 3 次**（首次 + 2 次重试）——
   如果 3 次都不行，那就是真的有问题（网络断了/配置错了），
   这时候**明确报错并提示检查配置**，比无休止重试好。

### 第二次故障：**HTTP 503 `overloaded_error`**（同一问题的另一面）

重试改好后又碰到一次，这次日志给出的是：

```
00:04:04  CHAT-SEND id=68
00:04:05  CHAT-FAIL id=68
          HTTP 503 Service Unavailable
          {"error":{"message":"Upstream model provider is temporarily unavailable.
                              Please try again in a moment.",
                    "type":"overloaded_error","code":"INTERNAL_SERVER_ERROR"}}
```

**⇒ 这是上游服务商过载**，错误信息自己就写着 "Please try again in a moment"。

**⚠️ 而且它暴露了重试改动的两个点**：

1. **改动需要重启游戏才生效** —— 这次日志里 `id=68` 只出现一次，
   说明**重试根本没跑**（当时游戏还是旧版本）。
2. **重试之间要"等一下"** —— 对 `overloaded_error` 来说，
   立刻重发很容易再撞上；所以补了 `AWAIT 800`（让出式等待，不卡游戏），
   并把提示改成「接口那边忙不过来，等一下再试 N／2 ……」。

**最终形态**：

```erb
FOR LLM_TRY, 1, 4
	CALLSHARP LLM_CHAT_SEND(...)
	CALL LLM_POLL(...)
	SIF LLM_STATE == 1
		LLM_SEND_OK = 1
	SIF LLM_SEND_OK
		BREAK
	SIF LLM_STATE == 0            ; 超时不重试
		BREAK
	IF LLM_TRY < 3
		PRINTFORML 　（接口那边忙不过来，等一下再试 %LLM_TRY%／2 ……）
		AWAIT 800                 ; ← 让出式等待，给服务端缓一下
	ENDIF
NEXT
```

### 第三次故障：**请求超时 60 秒**（表现为"进对话前死机"）

```
00:25:47  CHAT-SEND id=121  name=魔理沙      ← 进对话的第一步（开场白）
00:26:47  CHAT-FAIL id=121  请求超时（超过 60 秒）
00:27:42  CHAT-SEND id=122  name=帕露西      ← 换了个角色
```

**排查过程**：

- **不是 prompt 太大** —— 对比各次 `sysLen`：魔理沙那次 **6137**，
  而当时平均值 **6082**、最大也就 6137。**没有异常。**
- **是服务端那一瞬间卡住了**（插件 `HttpClient` 的超时上限 **60 秒**）。

**⇒ 根因我们无法修复**（服务端的问题），但**"死机感"是我们要负责的**：
那 60 秒里画面上只有一行静止的「正在思考……」，玩家当然以为游戏卡死了。

### 改法：让等待**可见**

`@LLM_POLL` 的轮询循环里，每约 5 秒把那行更新一次：

```erb
IF LLM_WAIT >= LLM_NEXT_TIP
	LLM_NEXT_TIP += 5000
	CLEARLINE 1
	PRINTFORML 　.....正在思考（已等待 %LLM_WAIT / 1000% 秒）.....
ENDIF
```

**⚠️ 两个细节**：

1. **用「下次更新时间」而不是取模 `%`** ——
   `%` 在 ERB 里既能当**插值分隔符**又能当**取模运算符**，
   写在一起容易看错（自查脚本也会误报）。
2. **超时仍然不重试** —— 这是刻意的：每次超时要等 60 秒，
   重试就变成 **120 秒无响应**，比现在更糟。
   **要缩短等待，应该去改插件的超时（见下）。**

### 如果超时频繁发生，两个可选方案

| 方案 | 做法 | 代价 |
|---|---|---|
| **缩短超时** | 把 `LlmClient.cs` 的 `HttpTimeoutSeconds` 从 **60** 改小（如 30）| **需要重编译插件**（且编译前要先关游戏）|
| **换服务商** | 在 `apis.txt` 里加第二条 API，菜单里切换 | 需要另一个 key |

### 仍然存在的风险 / 可继续改进

- **`@LLM_TOGETHER_TALK`（陪伴后的追加台词）也有同样的失败分支**，
  但它失败**不影响对话**（只是少一句），所以暂未加重试。
- **如果重试仍然频繁失败**，可以考虑：
  - 把 `max_tokens` 调小（**回复生成时间**是超时的主要来源）
  - 或让玩家在菜单里看到"最近失败次数"

## 8. ★ 两个"实机才暴露"的感知错误（✅ 已修）

这两个都是**玩家实测**发现的 —— 共同点是：**游戏事实与注入给模型的描述不一致**。

### 8.1 开场白没进上下文 → 她"前后矛盾"

**症状**：开场白说「今天天晴」，后面几轮却一直讲「还在阴天」。

**根因**：开场白那次请求传的 `recordHistory = 0`（**不记入历史**）：

```erb
; 旧代码，`@LLM_CHAT_LOOP` 开场白
CALLSHARP LLM_CHAT_SEND(TARGET, LLM_SYS,
    "（现在开始自由对话，请你先开口。…）", 0, LLM_TMP)
                                            ↑ 不记
```

**后果**：**她完全不记得自己开场说过什么** —— 那第一句在她眼里根本不存在，
只能靠 system prompt 里的【外面的天气】重新"猜"，猜出来自然前后矛盾。

**当初为什么传 0**：怕把"请开始对话"这种**指令性文本**留在上下文里。

**修法**：**改为记录**（传 1），并把 `userText` 换成**场景旁白**而不是指令：

```erb
CALLSHARP LLM_CHAT_SEND(TARGET, LLM_SYS,
    "（你走到她面前，想和她说说话。）", 1, LLM_TMP)
```

⇒ **宁可历史里留一句自然旁白，也不能让她失忆。**

> ⚠️ **`@LLM_REFUSE_TALK` 那边仍然传 0**，那是对的 ——
> **拒绝不算"聊过"**，不该进上下文。

### 8.2 工作结束的判据少了一种 → 她"还在守门"

**症状**：美铃站岗 6–12 点，玩家帮忙让活提前干完（比如 10 点就完事），
但 LLM 还一直在说工作相关的话。

**根因**：游戏的「工作结束」有**三条路**，我们只判了第一条：

| 情况 | 判据 | 原来判了吗 |
|---|---|---|
| ① 活干完了 | `BASE:工作量 <= 0` | ✅ |
| ② **到点下班了** | `TIME > TCVAR:工作結束` | ❌ **漏了** |
| ③ 今天本来休息 | `TCVAR:工作開始 == -1` | ❌ 漏了 |

**②的后果最明显**：`工作量` 还留着零头、但时间已过下班点 ⇒
**游戏认为她下班了，我们还在注入「正在门番」**，模型自然继续演"我还在守门"。

**修法**：**改用官方现成函数** `@CHARA_HOLIDAY(角色, 0)`
（`JOB_仕事内容.ERB:9-25`，内部就是这三条）：

```erb
IF CHARA_HOLIDAY(LLM_CID, 0)
	IF BASE:(LLM_CID):工作量 <= 0
		LLM_ACT = "刚把手头的活干完，正在收拾东西"
	ELSE
		LLM_ACT = "今天的班已经下完了，正在歇口气"
	ENDIF
ELSE
	LLM_ACT = %GET_JOBNAME(LLM_CID)%   …
ENDIF
```

**⚠️ 同一个漏判有**两处**，都改了**：

1. `@LLM_BUILD_SYSTEM_PROMPT` 的 `LLM_ACT` 构建（注入"她现在在做什么"）
2. **`@LLM_APPLY_DELTA` 的"陪她工作"分支** ——
   漏判的后果更严重：**会继续帮她干活**（而活已经不存在）

**⚠️ 修 2 的时候还踩了一次 `SIF` + `ELSE`** ⇒ 报 `Extra closing tag 'ENDIF'`，
已改成 `IF … ELSE … ENDIF`（避坑清单第 1、2 条，本项目栽过最多的坑）。

### 8.3 工作进度**不告诉她**，导致她只能说"还没呢"（✅ 已修）

**症状**：玩家问「工作结束了吗」，美铃答「还没呢，我这一班得到中午才换」，
但玩家觉得活已经干完了。

**排查**（看日志 `id=18` 那轮）：她报的**时间信息是对的**
（「现在才十点多一点」「到中午才换」），所以问题只可能在 `工作量` 上。

**根因**：原来的注入只有一句 `正在门番` ——
**模型完全不知道进度还剩多少**，被问到只能含含糊糊答"还没呢"。
而且玩家**也无从判断**她说的对不对。

**修法**：把**进度百分比**一起注入：

```erb
LLM_TOGP = BASE:(LLM_CID):工作量 * 100 / MAXBASE:(LLM_CID):工作量
IF LLM_TOGP <= 0      → 「（马上就要收尾了）」
ELSEIF LLM_TOGP < 5   → 「（快干完了，就剩一点尾巴）」
ELSEIF LLM_TOGP < 30  → 「（已经干得差不多了，还剩大约 N％）」
ELSEIF LLM_TOGP < 70  → 「（干了一半上下，还剩大约 N％）」
ELSE       → 「（才刚开始没多久，还剩大约 N％）」
```

**⚠️ 为什么给百分比而不是绝对数字**：门番总工作量 3600，
光说"还剩 600"模型判断不出是多还是少；而"**还剩约 17％**"
它立刻知道"快完了、可以催一下"。

**⚠️ 门槛刻意做成**分档描述**而不是直接报数** ——
"剩 3%"这种精度没有意义，不如说"就剩一点尾巴"。

**⇒ 副作用（好的）**：玩家现在**能直接听出她的进度对不对**，
以后再有"对不上"的问题，一问就知道是哪边的问题。

### 教训（值得记）

> **凡是"游戏怎么判定某件事"的逻辑，优先找官方现成函数，不要自己写。**
> `@CHARA_HOLIDAY` 就是典型 —— 它的三条判据我是看源码才知道的，
> 自己写必然漏（这次就漏了一条，而且**两处都漏**）。

## 9. ★ "劝你去休息"现在会**说出口**并**被记住**（✅ 已实现）

**原来的问题**：玩家体力/气力见底时，系统只是打一句**第三人称旁白**：

```
　你连站都快站不稳了，实在没力气聊天。先去休息吧。
```

**两个毛病**：

1. **她本人一句话都没说** —— 玩家感觉是"**系统在挡我**"，而不是"她在关心我"。
2. **什么都不会留下** —— 下次再来，她**完全不记得你曾在她面前累趴过**。

**⇒ 一句话：那只是"过了一次检定"，没有变成"发生过的事"。**

### 改法：统一走 `@LLM_TOO_TIRED_TALK`

```erb
@LLM_TOO_TIRED_TALK(LLM_CID, LLM_KIND)
IF LLM_KIND == 1
	PRINTFORML 「……你先去歇着吧。站都站不稳了，还硬撑着聊什么。」
	LLM_MEMO_TXT = "他上次在我面前累得站都站不稳，被我赶去休息了"
ELSE
	PRINTFORML 「……你都说不出话了。先去休息，我在这儿等着你。」
	LLM_MEMO_TXT = "他累到连话都说不利索，我让他先去休息了"
ENDIF
CALL LLM_MEMO_ADD(LLM_CID, LLM_MEMO_TXT)
RETURN
```

**四个调用点全部统一**（原来只有第 3 处是"她的口吻"，其余是旁白或静默）：

| # | 位置 | 原来 |
|---|---|---|
| 1 | `@LLM_CHAT_LOOP` 入口（进对话就被拦）| 第三人称旁白 |
| 2 | `@LLM_CHAT_LOOP` 循环末尾（聊到一半累趴）| 第三人称旁白 |
| 3 | `@LLM_REFUSE_TALK` | 有她的口吻，**但没记忆** |
| 4 | `@LLM_TOGETHER_TALK` | **静默 RETURN**（连话都没有）|

### 三个刻意的设计选择

1. **不发请求，用固定台词** ——
   这一幕本来就该**快**（玩家已经很累了，还要等模型几秒钟很荒唐），
   而且"关心一句"的措辞不依赖上下文，**固化反而更稳**。
2. **记忆写成"她看到的第一人称视角"**，不是系统报告 ——
   `"他上次在我面前累得站都站不稳"` 读起来才是**她自己的回忆**。
3. **记忆走 `@LLM_MEMO_ADD`**（按好感度掷骰 + 自带去重）——
   所以**多处调用也安全**，而且"记不记得住"仍然跟着关系走。

### ★ 后续补强：**演出要贴角色 + 跟关系走**（2026-09 追加）

第一版改完还不够 —— 有两个毛病：

1. **`@LLM_TOO_TIRED_TALK` 用的是两句固定台词** ⇒
   **所有角色、所有关系说同一句话**，既不贴性格，也违背"亲密度决定对话内容"的前提。
2. **`LLM_TIRED_TH` 那段婉拒的 prompt 也是一刀切的** ⇒
   刚认识的人和恋人会用同一种口吻关心你。
3. **更根本的时序问题**：`@LLM_APPLY_DELTA`（发现你累 → 婉拒）是在
   **模型回复之后**才跑的 —— 那时她的话**已经说出口了**。
   模型不知道你累，很可能刚说完「好啊，我陪你」，系统再补一句"她让你去歇会儿"，
   **自相矛盾**。

**⇒ 三处一起改：**

#### ① 提前把"他撑不住了"写进 prompt（解决时序）

在 `@LLM_BUILD_SYSTEM_PROMPT` 里注入（阈值与 `LLM_TIRED_TH` 同源）：

```
【他的状态（很重要）】玩家看上去已经快撑不住了 ——
⚠️ 这种情况下你该做的是：
   · 主动劝他去休息，而不是继续拉着他陪你做事
   · 如果他提要陪你 / 帮你干活，你要拒绝
   · 也别每句都提 —— 提一次、态度明确就够
```

**⇒ 让她自己开口劝，而不是事后由系统打旁白。**

#### ② 关心程度**按关系分三档**

| 关系 | 该怎么关心 |
|---|---|
| **恋慕 / 恋人 / 爱欲** | **心疼，甚至有点生气**（气他不爱惜自己），可以有私心（「你倒下了谁陪我」）|
| **思慕 / 炮友** | 真心实意地劝，但**还没到心疼**的程度 |
| **关系还浅** | 只是出于**基本分寸**劝一句，**不必格外上心**，不要流露亲近感 |

**⚠️ 每一档都强调「表达方式仍是你的风格」** ——
嘴硬的先骂再关心、冷淡的皱着眉命令、随性的拿玩笑掩饰担心。**别变成温柔模板。**

#### ③ 固定台词改成走 persona

`@LLM_TOO_TIRED_TALK` 现在会**发一次请求**，用
`@LLM_BUILD_TIRED_PROMPT`（与 `@LLM_BUILD_REFUSE_PROMPT` 同一套骨架：
persona + 语气 + 关系 + 硬性要求）生成**符合她本人性格**的关心。

```erb
CALL LLM_BUILD_TIRED_PROMPT(LLM_CID, LLM_KIND, LLM_SYS)
CALLSHARP LLM_CHAT_SEND(LLM_CID, LLM_SYS, "（他刚才还硬撑着…现在明显到极限了。）", 1, LLM_TMP)
…失败 / 超时 → CALL LLM_TIRED_FALLBACK(LLM_CID, LLM_KIND)
CALL LLM_MEMO_ADD(LLM_CID, LLM_MEMO_TXT)
```

**⚠️ 保底台词 `@LLM_TIRED_FALLBACK` 也按关系分两档** ——
即使请求失败，也不能让她在这种时刻哑掉，更不能所有关系统一腔调。

**⚠️ 关系判据与主 prompt 用同一套写法**（`面識 → 思慕 → 恋慕 → 恋人 → 炮友 → 爱欲`，
后写的覆盖前面的），否则会出现"平时她当我是恋人、这一刻却按陌生人对待"的错位。

### 顺带

这条也印证了一个通用原则：

> **凡是"玩家经历过的事"，都该同时产出「她的台词」和「她的记忆」，
> 而不是只产出一条系统提示。**
> 只过检定的东西，玩家感受不到它真的发生过。

## 10. ★ 陪伴 / 帮忙 / 一起做事 也进持久记忆（✅ 已实现）

**需求**：帮她干活、陪她一起看书这类**一起做过的事**，也该被她记住。

### 现在的记忆来源汇总（共 7 个写入点）

| # | 来源 | 内容示例 | 谁触发 |
|---|---|---|---|
| 1-2 | **模型自己写的 `###MEMO###`** | 「他答应下次陪我去看樱花」 | 模型判断（约定/私事/称呼/共同经历）|
| 3-4 | **累趴**（`@LLM_TOO_TIRED_TALK` 成功/失败两条路径）| 「他上次在我面前累得站都站不稳」 | 体力/气力见底 |
| 5 | **帮忙干活** | 「他帮我干过门番」 | 玩家说「我来帮你」并成功推进 |
| 6 | **陪她一起做事** | 「有一次他陪我一起看书」 | 玩家说「我陪你」并建立陪伴模式 |
| 7 | **硬撑着陪你**（婉拒）| 「有一次他累得快撑不住了还想陪我」 | 你太累还想陪、被她拦下 |

### 为什么不会把 4 个槽位挤爆

**两个原因叠加**：

1. **事由是固定字符串** —— 工作名来自 `@GET_JOBNAME`（「门番」），
   陪伴事由来自 `@FreeAct_Name`（「看书」/「钓鱼」/「打扫」…）。
   所以**同一件事反复做，产出的记忆文本一模一样**。
2. **`@LLM_MEMO_ADD` 自带去重** —— 逐条比对，已存在的直接跳过。

**⇒ "一起看书"做一百次也只占 **1 个**槽位。**

### 措辞：写成**她自己的回忆**，不是系统日志

```erb
LLM_MEMO_TXT = @"他帮我干过%LLM_FANAME%"          ; 「他帮我干过门番」
LLM_MEMO_TXT = @"有一次他陪我一起%LLM_FANAME%"     ; 「有一次他陪我一起看书」
```

**⚠️ 这个区别很重要** —— 这些文本会被注入到
`【你还记得关于他的事】` 里，用第一人称回忆的口吻读起来才像"她记得"；
写成"玩家曾协助角色完成工作"那种公文腔，模型会演得像在读档案。

### ⚠️ 踩到的坑

写"帮工"那处时用了 `SIF LLM_FANAME != ""` 带**两行**（赋值 + `CALL`）——
`SIF` 只绑紧随的一行，`CALL` 会**无条件执行**，
于是工作名为空时会记进一条「他帮我干过」这种没头没尾的记忆。
已改成 `IF … ENDIF`（**又是这个坑，第 N 次了**）。

## 11. ★ 开场白要先"交代处境"（✅ 已实现）

**需求**：开场白生成时，让她先看看自己现在的状态 ——
在做什么（有没有在上班）、在哪儿、天气如何 —— 再开口。

### 澄清：状态**本来就注入了**

`@LLM_BUILD_SYSTEM_PROMPT` 每次组装 prompt 时都会**重新取一遍快照**，
所以开场白轮次拿到的就是当下的真实状态：

| 你说的 | 对应注入项 |
|---|---|
| 有没有在工作 | 【你现在正在做的事】（含工作名 + **进度百分比**）|
| 现在什么位置 | 【现在所在的地方】（大地图 + 房间）|
| 当前天气 | 【外面的天气】 |
| 还有 | 【现在几点】【你今天的安排】【同一个房间里还有】… |

**⚠️ 问题在于：模型完全可以不理这些，直接来一句「有事吗？」** ——
状态是"给它了"，但它不一定会**用**。

### 改法：加"开场白专属要求"

给 `@LLM_BUILD_SYSTEM_PROMPT` 加第 4 个参数 `LLM_OPENING`
（开场白传 `1`、普通轮次传 `0`），在 prompt 末尾追加：

```
【这是你这一场对话的第一句话】
⚠️ 玩家刚走到你面前。开口之前，先让这句话落进你此刻的处境里 ——
   · 你手上正在做什么（看【你现在正在做的事】）
   · 你在哪儿（看【现在所在的地方】）
   · 或者此刻的天气 / 时间（看【外面的天气】【现在几点】）
⚠️ 挑一两样自然地带进去就行，别像报流水账一样全念一遍。
⚠️ 而且要从你自己的视角说 ——
   「这太阳晒得人直发困」比「现在是晴天」自然得多。
⚠️ 如果此刻确实没什么可说的（比如你正睡着、正忙着），那就照实说，不用硬凑。
```

### 三个刻意的约束

1. **「挑一两样」** —— 不加这句，模型会把她知道的全念出来：
   「现在是晴天，我在红魔馆正门，我是个门卫，现在十点」——**像在读状态栏**。
2. **「从你自己的视角说」** —— 给了正反例（「太阳晒得人发困」 vs 「现在是晴天」），
   这是让开场白有**画面感**而不是**报数据**的关键。
3. **「没可说的就照实说」** —— 她正睡着的时候硬要她描述天气反而怪。
   **给模型留一个"可以不提"的出口**，否则它会为了满足要求而生造。

## 12. ★ 跨地点的"说错地方"与玩家自报身份（✅ 已实现）

### 12.1 「站在 A 房间说 B 房间的事」

**根因**：对话历史是**按角色**存在插件内存里的（最多 12 条 = 6 轮），
而且**从来没清过** —— 你在 A 房间聊完走到 B 房间再开口，
A 房间的话还在上下文里，模型顺着它说。

**⚠️ 试过"换地点就清历史"这个方案，但被否掉了**（用户判断，我同意）：

- **同一地点、同一天的连续对话本来该有上下文** —— 那是"刚才聊到一半"，
  清了反而变成答非所问；
- **清历史是破坏性的**，代价大、不可逆。

**⇒ 最终方案：提高「当前状态」的优先级，而不是删历史。**

在 prompt 靠后位置（越靠后影响力越强）加一段：

```
【当前的事实（优先级最高）】
上面那些【现在所在的地方】【现在几点】【外面的天气】
【你现在正在做什么】【同一个房间里还有】——
都是此时此刻的准确信息。
⚠️⚠️ 它们的优先级高于你们之前的对话记录：
   如果两者对不上（比如早先聊到过另一个地方、另一种天气），
   一律以上面这些为准，不要顺着旧话题继续。
⚠️ 尤其是地点 —— 别把之前待过的地方当成现在所在的地方。
```

**`@LLM_HISTORY_CHECK` 保留但**只记录位置/日期**，不再清历史**
（代码注释里明确写了"别再加回去"）。

### 12.2 玩家自报的身份 / 称呼

**需求**：玩家说「我是红魔馆的佣人」这类话时，她该记住，
**免得下一轮又把他当陌生客人**。

**⚠️⚠️ 它和普通持久记忆的性质**完全不同****——三点都相反：

| | 普通持久记忆 `LLM_MEMO` | **身份记忆 `LLM_ADDRESS`** |
|---|---|---|
| 是否掷骰 | 按好感度（15% / 40% / 80%）| **不掷骰** —— 与好感度无关 |
| 占几个槽位 | 4 个，满了淘汰最旧 | **完全独立**，不占 |
| 注入优先级 | 正常 | **刻意放低** |

**实现**：模型用 `###ADDR###` 输出（与 `###MEMO###` 分开，互不干扰）：

```erb
###ADDR###他说自己是红魔馆的佣人
```

**⚠️ prompt 里写清楚了两件事**：

1. **只有玩家真的自报身份时才写** —— 否则每轮都冒出来。
2. **⚠️⚠️「这不是你该怎么称呼他的规则」** ——
   关系深了以后**照样叫名字、叫朋友、用自己习惯的叫法**，
   它只用来**维护对话的一致性**（别刚听他说完又当陌生客人）。

**注入形态**：

```
【他告诉过你他的身份】他说自己是红魔馆的佣人
（⚠️ 这只是为了让你别前后矛盾 —— 别刚听他说完又把他当陌生客人。
  它不是你该怎么称呼他的规则：关系深了以后你照样可以叫名字、
  叫朋友、用你自己习惯的叫法。别因此把称呼变得生分。）
```

> **⚠️ 为什么优先级必须低**（用户明确要求）：
> 当成硬规则的话，**恋人档还一口一个"佣人先生"**就非常怪。
> 它的定位是**一致性锚点**，不是称呼规则。

## 13. ★ 以「开场白」为分界线的双层记忆（✅ 已实现，含插件改动）

**需求（用户设计）**：
- 每次开场白是一道**分界线**；
- **开场白以上**（上一场对话）→ 降级成**低优先级的补充记忆**；
- **开场白以下**（本次对话）→ 正常的当前对话记忆；
- 同时把插件的历史上限**扩到 30 条**。

### 为什么这个方案比"清历史"好

前面试过"换地点就清历史"，被否掉了 —— 那会让她**完全忘记**上一次聊过什么。
**降级成"低优先级参考"才是对的**：话题和印象保留，但**过时的地点/天气/时间不许再当现状用**。

### 改了插件（这次必须改）

ERB 侧拿不到历史内容，就没法把它降级 —— 所以给插件加了一个接口：

| 改动 | 位置 |
|---|---|
| **`MaxHistoryMessages`: 12 → 30**（6 轮 → 15 轮）| `LlmClient.cs:28` |
| **新增 `DumpHistory(charIndex, maxTurns)`** —— 导出历史为纯文本 | `LlmClient.cs` |
| **注册 `LLM_HISTORY_DUMP`**（参数：角色索引, 最多轮数, 结果变量）| `PluginManifest.cs` |

**⚠️ 踩到的坑**：我加了个 `ArgInt(args, n, def)` 辅助方法，
结果**基类里本来就有个 `ArgInt(args, i)`**（第 672 行）——
同名把已有的 4 处调用全打乱了，编译报 CS7036。
**改名成 `ArgIntDef` 才通过。**（教训：加辅助方法前先搜基类。）

**编译结果**：`0 警告 0 错误`，DLL 已部署（49664 字节），契约程序集引用正常。

### ERB 侧：`@LLM_PREV_CAPTURE`

开场白时调用一次（在 `BUILD_SYSTEM_PROMPT` **之前**）：

```erb
; ① 导出旧历史（最多 8 轮）→ 存进 LLM_PREV（按角色、进存档）
CALLSHARP LLM_HISTORY_COUNT(LLM_CID, LLM_TMP)
SIF TOINT(LLM_TMP) <= 0
	RETURN                          ; 第一次和她说话，不用做
CALLSHARP LLM_HISTORY_DUMP(LLM_CID, 8, LLM_TMP)
LLM_PREV:(LLM_CID) = %LLM_TMP%
; ② 清空插件历史 → 之后累积的就是"本次会话"
CALLSHARP LLM_HISTORY_CLEAR(LLM_CID, LLM_TMP)
```

**为什么只导 8 轮**：再往前的内容价值递减，而 token 是实打实的成本。

### 注入：位置和措辞都在强调"优先级低"

**放在 persona 之后、状态项之前** —— prompt 里**越靠后越有影响力**，
所以"仅供参考"的东西必须放前面：

```
【你们上一次交谈的片段（仅供参考 · 优先级低）】
玩家：…
你：…
（⚠️⚠️ 这是之前那一次聊天的记录，只是让你和他之间有个连贯印象：
   里面的地点、天气、时间都已经过时了，不要当成现在的情况。
   聊到相关话题时可以自然接上（「你上次说的那个…」），
   但如果它和下面的【当前的事实】冲突，一律以下面为准。）
```

### 两层记忆的完整分工

| 层 | 内容 | 优先级 | 存哪 |
|---|---|---|---|
| **当前对话** | 本次开场白之后的对话 | 最高（正常历史）| 插件内存（最多 30 条）|
| **上次对话** | 上一场的片段 | **低**（明说会过时）| `LLM_PREV`（存档）|
| **持久记忆** | 约定/私事/共同经历 | 中 | `LLM_MEMO`（4 槽，按好感度掷骰）|
| **身份设定** | 他自报的身份 | **刻意低**（不是称呼规则）| `LLM_ADDRESS`（独立，不掷骰）|
| **当前事实** | 位置/时间/天气/在做什么 | **最高**（压过所有历史）| 每轮实时计算 |

## 14. ★ "陪着做事永远做不完"（✅ 已修 —— 是我们的 bug，不是游戏设计）

### 症状

玩家陪着角色**一起运动**，但她**永远在运动**，陪不到结束。

### 排查结论：**是我们的 bug**

**运动的时长**（`FREE_ACT_5.ERB:48`）：

```erb
RETURN 60 + RAND:60        ; 即 60~119 分钟
```

**而我们的陪伴推进了多少时间**：

| 时机 | 推进 |
|---|---|
| 建立陪伴那一次（`t=3` / `t=4`）| +15 / +30 分钟 ✓ |
| **陪伴的后续轮次 · 工作分支** | **+15 分钟** ✓ |
| **陪伴的后续轮次 · 自由行动分支** | **只有 ④b 的 +3 分钟** ⚠️ |

**⇒ 自由行动分支漏了时间推进** —— 陪 4~8 轮也才攒 12~24 分钟，
而运动要 60~119 分钟，**玩家永远陪不到结束**。
（工作分支早就写了，只有自由行动这边漏了 —— 典型的"两个分支只改了一个"。）

### 修法

在自由行动分支补上与工作分支一致的推进：

```erb
IF Activity_Duration:(LLM_CID)
	…更新模式名…
	LLM_ELAPSE = 15
	TIME += MAX(LLM_ELAPSE - 3, 0)     ; ④b 已加过 3，这里补差额
	LLM_MSG += @"（你陪着她一起%LLM_FANAME%）"
```

**⚠️ 三个刻意的不做**：

1. **不在这里扣体力/气力** —— 陪着 ≠ 一起干，消耗只在建立陪伴那一次（⓪b）结算过；
   每轮再扣会变成无底洞（而且实测玩家会一路陪到昏过去）。
2. **不重复跑 `"ソース"`** —— 那会连刷好感度（见该分支上方的说明）。
3. **不改 `Activity_Duration` 本身** —— 交给 `@自由行動処理` 按时间自己递减
   （`MOVEMENT_自由行動.ERB:13`），手动再减一次就成了双重递减。

### 顺带：游戏的"中断"条件（供参考）

即使时间够，她的行动也可能**被游戏自己中断**（`@自由行動条件`，
`MOVEMENT_自由行動.ERB:79-108`）：离开据点 / 状態异常 / 进入诶嘿嘿 /
开始工作 / 延迟中 / 同行中 / **移动了位置** / 天气伤害 / 妊娠。
**这些是游戏设计，不该绕过** —— 我们只补自己漏掉的那部分。

## 16. ★ 帮忙干活走「失败 / 成功 / 大成功」（✅ 已实现）

**需求**：照官方那套走，而且数值**温柔一些** —— 成功也该有回报，但比大成功少。

### 掷骰（照抄官方 `COMF304:288-334`）

```erb
LLM_RATE = RAND:100
LLM_RATE_LOW  = 9      ; <= 9  → 大成功
LLM_RATE_HIGH = 90     ; >= 90 → 失败
```

结果码写进 **`TFLAG:193`**（官方用的就是这个位置）：`1` 大成功 / `0` 成功 / `-1` 失败。

**⚠️ 一个替代**：官方原式是 `90 + GET_SUCCESS_RATE() / 5`，
但 `@GET_SUCCESS_RATE` 在本作里**搜不到定义**（可能被 mod 删了/改名了），
所以用**固定档位**代替（9% / 10%，与官方量级一致）。
**等哪天找到那个函数，把 `LLM_RATE` 那两行换掉即可。**

### 三档数值（用户要求"温柔一些"）

| 档位 | 工作量 | 信赖度 | 好感源（随口 / 认真）|
|---|---|---|---|
| **大成功** | **×1.5** | **+3** | **450 / 600** |
| **成功** | 正常 | **+1** ← **新加的** | **300 / 450** |
| **失败** | 只剩随机量 | **−1** | **150 / 225** |

**⚠️ 成功原来是"什么都不给"** —— 结果"帮她干完活"和"没帮"几乎没差别，
玩家白忙一场。现在三档都有份，只是**量递减**。

**⚠️ 失败减半而不是归零** —— 毕竟花了时间（官方也只是 `WorkP = 0`，
随机量那部分还在）。

**⚠️ 两个维度是独立的**：
投入程度决定**基数**（随口 300 / 认真 450），掷骰结果决定**浮动**（+150 / 减半）。

### 结果会告诉模型 —— 这才是"对话更丰富"的关键

**⚠️ 时序问题**：`TFLAG:193` 是**当轮**的，而 prompt 是**下一轮**才组装的。
所以存进跨轮变量 `LLM_LAST_RESULT`（`@LLM_WORK_DO` 的两个调用点都写）。

**⚠️⚠️ 哨兵值**：`LLM_LAST_RESULT` 默认 0 会**和"成功"撞车** ——
不加处理的话，你这场对话里**还没帮她干过任何活**，她就会说「刚才那活干得挺顺」。
⇒ 在 `@LLM_CHAT_LOOP` 开场白时初始化为 **9**（= 还没帮过）。

**注入形态**：

```
【你刚帮他干的活】做得非常漂亮 —— 连你自己都有点得意。
（可以自然地表露出来：得意、邀功、或者嘴硬地说「这不算什么」。不要生硬地报「大成功」。）
```
```
【你刚帮他干的活】搞砸了 —— 手忙脚乱，还给他添了麻烦。
（可以自然地表露出来：懊恼、找借口、嘴硬、或者不好意思。不要生硬地报「失败」。）
```

**⚠️ 每一档都写了「不要生硬地报「大成功」/「失败」」** ——
否则她会直接念出结果码，那比不说还糟。

**⚠️ 成功那档写的是「不用特意提，正常聊就行」** ——
每轮都强调"我干得不错"会很烦。

## 17. ★ "嘴上答应、系统却判婉拒"（✅ 已修 —— 判定与台词的时序错位）

### 症状（截图实证）

屏幕上同时出现三行**互相矛盾**的内容：

```
「嗯，就这样。轻拿轻放，别急。」        ← 她说"答应了"（模型生成）
（她没答应，让你先去歇会儿）             ← 系统判"婉拒"
（她自己推进+30 时间－3）               ← 工作量**真的推进了**
```

### 根因：两套判定用了**两个不同时刻**的体力值

| 时刻 | 玩家体力 | 结果 |
|---|---|---|
| **组装 prompt 时** | 还够 | 注入里没强调"他快撑不住了" → 她**顺着对话历史**（上一轮刚答应过）继续说"好" |
| **本轮结算时** | 已被扣 150 → 低于阈值 | `LLM_TIRED = 1` → 判婉拒 + 清掉陪伴 |

**⇒ 她的台词和系统的判定必然打架。**

### ⚠️ 我第一版的修法**是错的**（记下来避免重犯）

我想改成"她这一轮已经答应了（`REF_TOGETHER` 非空）就不拦"，
但**那个分支的进入条件本身就是 `LLM_TGKIND != ""`**（已在陪伴中）——
写进去会让 `LLM_TIRED` **永远为 0**，**婉拒彻底失效**。
**已撤销。**

### 正确修法：把「他累了」放进**优先级最高**那一段

**根本问题是"她那句话的效力来源"错了**：
prompt 里确实有【他的状态】，但它在**靠前**位置，
而模型更信**靠后的内容**和**对话历史** —— 于是"上一轮答应过"压过了"他现在累了"。

**⇒ 把同一条信息**再写进【当前的事实（优先级最高）】**那一段：**

```
⚠️⚠️ 另外：玩家现在已经快撑不住了（体力/气力很低）。
   这一条同样压过对话记录 —— 就算你上一轮答应过要陪他 / 让他帮忙，
   现在也该改口：让他先去休息，别再让他继续。
   别顺着「刚才还答应过」往下说 —— 情况变了。
```

**⚠️ 关键是那句「**就算你上一轮答应过…现在也该改口**」** ——
它直接点名了冲突的来源（对话历史），而不是泛泛地说"他累了"。

**⚠️ 婉拒判定本身保持原样**（该拦就拦）——
它是对的，只是**台词要跟上**。

## 18. ★ 改成「先判、再让她说」（✅ 已实现 —— 根治 §17）

### 用户的要求

> 能不能把判断逻辑改成 **先判断、再出现对话** 呢

**对 —— 这才是根治。** §17 那些补丁（把"他累了"写进优先级最高段）只是
**让模型更可能遵守**，但根子还在：**她先说、系统后判**，两个结果就可能打架。

### 实现：判定前置 + 整轮共用同一个值

```
① 组装 prompt 之前（@LLM_BUILD_SYSTEM_PROMPT 里）
     算出"他累不累" → 写进文件级变量 LLM_PTIRED_LOCK
     同时据此告诉她该拒绝（靠前 + 靠后两处都写）
② 结算时（@LLM_APPLY_DELTA）
     LLM_TIRED = LLM_PTIRED_LOCK        ← **复用，不再重算**
```

**⇒ 她这句台词和系统的判定用的是**同一时刻的体力****，从根上不会再自相矛盾。

### ⚠️ 关键：`LLM_PTIRED` 必须是**文件级变量**

它原来只是 `@LLM_BUILD_SYSTEM_PROMPT` 的**局部变量**，结算那边根本取不到 ——
所以两边只能各算各的，必然错位。

**改动**（`LLM_KOJO.ERH`）：

```erb
#DIM LLM_PTIRED_LOCK       ; 9 = 本场还没判定过（哨兵）；0 = 不累；1 = 累
#DIM LLM_PTIRED_LOCK_TH    ; 配套阈值，保证两边判据完全同源
```

**⚠️ 阈值也一起锁** —— 只锁"累不累"而阈值各算各的，
万一 `MAXBASE` 在期间变了（换装/升级），两边还是会错开。

### ⚠️ 补完：**建立陪伴时那处婉拒也改成复用锁定值**

第一版只改了"陪伴中"那处（`LLM_TIRED = LLM_PTIRED_LOCK`），
**漏了"建立陪伴时"那处** —— 它仍然在结算里**自己重算了一遍阈值**：

```erb
; ❌ 旧代码（@LLM_APPLY_DELTA，建立陪伴分支）
LLM_TIRED_TH = 800
SIF MAXBASE:MASTER:体力 / 5 > LLM_TIRED_TH
	LLM_TIRED_TH = MAXBASE:MASTER:体力 / 5
…
ELSEIF BASE:MASTER:体力 <= LLM_TIRED_TH || BASE:MASTER:気力 <= LLM_TIRED_TH
```

**⇒ 同一个 bug 的第二次出现**（"写了判定，但没走统一入口"）。
现已改成：

```erb
ELSEIF LLM_PTIRED_LOCK        ; ← 直接用组装 prompt 时锁下来的判定
```

**并把 `LLM_TIRED_TH` 这个本函数专用阈值**整个删掉**（连声明一起）——
留着两份阈值只会让人误以为"这里可以重算"，而重算正是那个 bug 的来源。**
阈值现在只有一份：`LLM_PTIRED_LOCK_TH`。

### 完整的判定顺序（现在）

| 时机 | 顺序 |
|---|---|
| **开场白** | `HISTORY_CHECK` → `PREV_CAPTURE` → 哨兵 → **`BUILD_SYSTEM_PROMPT`（全部状态判定）** → 发请求 |
| **每轮** | **`BUILD_SYSTEM_PROMPT`（判定）** → 发请求 → `APPLY_DELTA`（**复用锁定值**）|

**⇒ 无论开场白还是后续轮次，模型拿到的都是"判定完成之后"的状态**：
有没有在上班、天气如何、在哪个房间、玩家累不累 —— 全部在它开口**之前**就定好了。
结算侧不再有任何"事后推翻她台词"的重算。

### 顺带保留的两层防护

| 层 | 作用 |
|---|---|
| **`LLM_PTIRED_LOCK`** | **温和的婉拒**：她还愿意陪，但会劝你去休息 |
| **`@LLM_TOO_TIRED`** | **硬刹车**：体力/气力**见底**时直接拦，安全网 |

**两者职责不同，别混在一起。**

## 19. ★ "活干完了"传不到模型 —— 是**两条注入互相打架**（✅ 已修）

### 症状（截图实证）

```
（活干完了，她可以歇口气了）        ← 系统判定：收工
「啊？还早着呢，我这班要守到十二点才换人。」  ← 她却按"排班表"说话
```

### 根因：prompt 里塞了**两条冲突的信息**

| 注入项 | 内容 | 对不对 |
|---|---|---|
| `LLM_ACT`（你现在正在做的事）| 「刚把手头的活干完」| ✅ **对** |
| **`LLM_ROUTINE`（你今天的安排）** | 「你今天要从6时0分**上到12时0分**」| ⚠️ **过时了** |

**`LLM_ROUTINE` 只按 `TCVAR:工作開始/結束` 拼（那是**排班表**），
完全没看"活是不是已经干完"。** 而模型面对冲突时，
**更信"日程表"那种像计划的东西** —— 于是照它说「还早着呢」。

### 修法（两处）

**① `LLM_ROUTINE` 里明说收工**（判据与 `LLM_ACT` **同源**）：

```erb
IF CHARA_HOLIDAY(LLM_CID, 0)
	IF BASE:(LLM_CID):工作量 <= 0
		LLM_ROUTINE += "，**不过活已经干完了，你现在已经收工**"
	ELSE
		LLM_ROUTINE += "，**不过时间到了，你已经下班了**"
	ENDIF
ENDIF
```

**⇒ 排班表和实际状态在同一条信息里就自洽了**，不再是两个打架的句子。

**② 注入处加"交叉一致性规则"**：

```
【你今天的安排】…
（⚠️ 这是**原定的作息表**。如果它和【你现在正在做什么】对不上 ——
  比如表上写着你今天要上到 12 点，但你**现在已经收工了** ——
  **一律以【你现在正在做什么】为准**，别说「我还得守到几点」。）
```

### 教训（这是同一类问题的**第四次**了）

| # | 冲突对 | 谁是对的 |
|---|---|---|
| 1 | `LLM_ACT` vs **对话历史**（换地点后）| `LLM_ACT` |
| 2 | 她的台词 vs **结算侧重算的判定** | 组装时的判定 |
| 3 | `LLM_ACT` vs `LLM_ROUTINE`（活干完了）| `LLM_ACT` |
| 4 | **prompt 靠前的内容 vs 靠后的内容** | 靠后的 |

**共同点：同一个事实被**两条路径**分别表达，而它们没有共享同一个判据。**

⇒ **规矩**：**凡是同一件事出现在多处（天/地/工作/累不累），
必须(a)判据同源、(b)冲突时明说以谁为准。** 光注入事实不够 ——
模型不负责帮你调和矛盾。

## 20. ★ "对话里的工作量和实际不一致"（✅ 已修 —— 钳位值被当成实际值）

### 症状

> 自由对话中的工作量部分好像与实际工作量不一致，
> 但**重新进入自由对话又能让他变得一致**，莫名其妙的。

**"退出重进就一致"是最关键的线索** —— 它说明**数值本身是对的**，
只是**某一侧拿的是另一个值**。（重进时会从真实字段重算，所以对上了。）

### 根因：把"**想扣多少**"当成了"**实际扣了多少**"

`@LLM_WORK_DO` 结尾：

```erb
LLM_TG = MAX(LLM_TG * LLM_STEP / 10, 1)
BASE:(LLM_CID):工作量 = MAX(BASE:(LLM_CID):工作量 - LLM_TG, 0)   ; ← 会被钳到 0
…
RETURN LLM_TG     ; ← 返回的却是**未钳位**的意愿值
```

**剩余工作量只有 100、而要推进 1500 时**：
- **实际只减了 100**（`MAX(..., 0)` 钳位）
- **但返回并显示的却是 1500**

⇒ 明细打出「工作量＋1500」，实际只减了 100 —— 玩家怎么算都对不上。

### 修法：用**前后差值**当结果

```erb
LLM_TG_BEFORE = BASE:(LLM_CID):工作量
BASE:(LLM_CID):工作量 = MAX(BASE:(LLM_CID):工作量 - LLM_TG, 0)
LLM_TG = LLM_TG_BEFORE - BASE:(LLM_CID):工作量     ; ★ 实际推进量
```

**⇒ 显示、进度、返回值三者永远一致。**

**⚠️ 对照**：同样在算"她自己推进"的 ④c **本来就是对的** ——
它写的是 `LLM_SELF = MIN(LLM_DT * 10, 工作量)`（先取 min 再扣），
所以那个值从一开始就是实际量。**同一个文件里两种写法，只有一种对** ——
这也是为什么这个 bug 藏了这么久。

### ⚠️ 同一个模式在**体力/气力**那边也有（**这次故意不改**）

```erb
DOWNBASE:MASTER:体力 += LLM_COST_T      ; 意愿量
CALL SOURCE_DOWNBASE(MASTER)            ; ← 内部 LIMIT(..., 0, MAX) 会钳位
CALL LLM_GAIN_COST(LLM_GAIN, "体力", LLM_COST_T)   ; ← 显示的是意愿量
```

**理论上会显示"体力−150"而实际只扣了 80。**

**但当前**触发不到**，所以不改**：
- 婉拒阈值是 **800**，而单次最大消耗是 **250**（认真帮忙）——
  800 − 250 = 550 > 0，**到不了钳位那条线**
- 陪伴模式每轮 150：进对话时 ≥800，扣一轮到 650，**下一轮就会被婉拒**，也不会继续扣

**⇒ 记在这里**：哪天动了阈值（调低）或加了更贵的动作，
这条就会变成真 bug，那时按 `LLM_TG_BEFORE` 那套前后差值改即可。

## 21. ★ 明细里显示玩家当前的体力 / 气力（✅ 已实现）

**需求**：*"能不能在「时间－3」那一行同时显示玩家的当前气力和当前体力，
方便玩家更好的进行体力管理。"*

### 实现

**新增 `@LLM_GAIN_CUR(明细串, 标签, 当前值, 上限)`** —— 在明细行追加一项
**当前值**：

```
（时间－3　体力 350/2000　气力 200/800）
```

**⚠️ 为什么是"当前/上限"而不是只给当前值** ——
光看「体力 350」判断不出还剩多少余量（上限因人而异，2000 和 1000 差一倍）；
写成 `350/2000` 一眼就知道还剩约 **18%**。

**⚠️ 为什么这一项"0 也要显示"**（和上面那些"0 就跳过"的项目相反）——
体力管理的**前提就是随时可见**，只在变动时才显示等于没显示。
所以它是**无条件追加**的，于是每轮明细都会带上余额。

**⚠️ 放在最末尾** —— 前面是"这一轮变动的增减"（`体力－150` 这种），
这里是"变动之后的余额"，视觉上分得开，不会看混。

**⚠️ 值取自**结算之后**（④e 官方结算已跑完）—— 所以是真正的最新余额，
不是"扣减前的旧数"。

### ⚠️ 顺手抓到一个自己的错

`@LLM_GAIN_CUR` 第一版写成：

```erb
SIF LLM_MAX > 0
	REF_TEXT += @"%TOSTR(LLM_VAL)%/%TOSTR(LLM_MAX)%"
	RETURN                    ; ← 这行会**无条件执行**
REF_TEXT += @"%TOSTR(LLM_VAL)%"   ; ← 于是兜底成了死代码
```

**`SIF` 只绑紧随的一行** —— 所以上限为 0 时反而**什么都不显示**。
已改成 `IF … ENDIF`。**（这个坑在本项目已经踩了 N 次，自查脚本每次都抓到。）**

## 22. ★ 技能经验**现在有数值反馈了**（✅ 已补）

**用户反馈**：*"陪伴干活增长对应技能经验值的内容做了吗？我没有在自由对话这边看到数值反馈。"*

### 查明：**经验确实在涨，但看不见**

- 经验成长（`@LLM_WORK_EXP`）**早在 §15 就实现了** —— 数值是真的在涨
- **但明细里一个字都没显示** ⇒ 玩家完全不知道自己练到了什么

**⇒ 玩家看不到 = 等于没做。** 这一条本身就是教训。

### 改了四处

**① `@LLM_WORK_EXP` 改成用 REF 参数带回结果**（顺带补上"大成功 +1"）

```erb
@LLM_WORK_EXP(LLM_JOB, REF_AMT, REF_LABEL)
```

普通函数只能 `RETURN` 一个数，**带不回"涨的是哪一项"** —— 所以用 REF 参数。

**② 补上「大成功 +1」**（§15 里留的那句"等哪天补掷骰再加"）

我们**现在会掷骰了**（§16），所以这里**忠实照抄官方的两段判定**：

| 職種 | 官方规则 |
|---|---|
| 清掃 / 会話 / 戦闘 / 教養 | 大成功 +1、`!RAND:4` +1 |
| 料理 / 音楽 / 採集 / 釣り / 調合 | **无条件 +1**、大成功再 +1 |

**③ 经验名用中文**（「清扫经验」「战斗经验」…），与明细里其它项风格一致。

**④ 明细里显示出来**（两个调用点各补一处）：

```erb
SIF LLM_LAST_EXP > 0
	CALL LLM_GAIN_GET(LLM_GAIN, LLM_LAST_EXP_NAME, LLM_LAST_EXP)
```

**效果**：

```
（你帮她门番，进度 13％　体力－150　气力－30　工作量＋375　信赖度＋1　战斗经验＋1　时间－15　体力 1500/2000　气力 600/800）
```

### ⚠️ 中间踩到的两个坑

**① `SIF` 两行 —— 又是它**

```erb
SIF TFLAG:193 == 1
	EXP:MASTER:清掃経験 ++
	REF_AMT += 1          ; ← 这行会**无条件执行**
```

想"判定一次、做两件事"时**很容易顺手写成 `SIF` 两行**。必须 `IF … ENDIF`。

**② 随机数会被掷两次**

反过来，"让随机数只掷一次"时也不能这么写：

```erb
; ❌ `RAND:4` 掷了两次，可能"经验涨了但计数没加"
SIF !RAND:4
	EXP:MASTER:清掃経験 ++
SIF !RAND:4
	REF_AMT += 1
```

**⚠️ 但**这里我故意保留了这种写法** —— 因为它和官方**逐行对应**，
而且"重新掷一次"在概率上**恰好等价**（都是 25%），
只是**计数偶尔会与实际涨的经验差 1**（都是 +1 的场合）。

**⇒ 权衡后决定：可读性优先**（和官方源码一一对应，以后核对不会错）。
**若哪天发现"经验涨了但没显示"，就是这里的概率性偏差，不是 bug。**

### ③ 每轮兜底清零

`@LLM_WORK_DO` 有**提前 RETURN** 的路径（活干完了 / 这两种職種不适用），
那时走不到发布经验那一步 → **值会残留上一轮的**，显示成"这轮也涨了"。

## 23. ★ 数值改成「进度条」显示（✅ 已实现）

**用户需求**：*"能使用像官方方案的那个进度条一样的显示模式吗"*

### 先查了官方有没有能复用的

| 函数 | 位置 | 能用吗 |
|---|---|---|
| `@PRINT_COLORBAR` | `PANIMATION.ERB:102` | ❌ **直接 PRINT**，不返回字符串 |
| `@COLOR_BAR` | `魔改内容\PRINT系\UI_Components_&_Tables.ERB:1190` | ❌ 同上 |
| `@HTML_COLORBAR` | `PANIMATION.ERB:142`（`#FUNCTIONS`）| ❌ 返回的是 **HTML**，我们走 `PRINTFORML` 纯文本，标签会原样显示 |
| `@PRINTTHRESHOLDBAR` / `@Print_Bar` / `@FREEBAR` | 各处 | ❌ 都是"打印"型 |

**⇒ 我们的明细是"先把整串在变量里拼好、最后一次打印"** ——
中间**插不进"打印"动作**（`CALL` 进去会把条打到别的行上）。
所以只能自己写一个**返回字符串**的版本。

### 字符选型：`■` / `□`

**用这两个是因为**官方自己的界面就在用**，字体一定支持、不会出豆腐块：
- `PRINT_STATE2.ERB:131` → `PRINTL 自宅位置：■■■■■ 【 ■■■■■ 】`
- `PRINT_STATE.ERB:13` → `PRINT ■`

（官方状态栏那条用的是 `▅`（U+2585），也能用；方块更"进度条"一些。）

### 实现：`@LLM_BARSTR(百分比, 长度)` —— `#FUNCTIONS`

```erb
@LLM_BARSTR(LLM_PCT, LLM_LEN)
#FUNCTIONS
…
LLM_FILL = LIMIT(LLM_PCT * LLM_LEN / 100, 0, LLM_LEN)
LLM_A = %SUBSTRING(LLM_FULL, 0, LLM_FILL)%
LLM_B = %SUBSTRING(LLM_EMPTY, 0, LLM_LEN - LLM_FILL)%
RETURNF @"%LLM_A%%LLM_B%"        ; ⚠️ 不能用 A + B
```

**⚠️ 三个坑都避开了**：
1. **必须 `#FUNCTIONS`** —— 普通函数返回不了字符串，嵌不进 `@"…%…%"`。
2. **`LIMIT` 两端都钳** —— 百分比可能超 100（上限变动时）或为负。
3. **拼接用 `@"…%变量%…"`，不能写 `A + B`** ——
   后者会拼进字面的 `" + "`（避坑清单第 4 条，本项目栽过）。

### 显示效果

```
（你帮她门番 ■□□□□□□□□□ 13％　体力－150　气力－30　工作量＋375
  信赖度＋1　战斗经验＋1　时间－15　体力 ■■□□□□□□□□ 350　气力 ■□□□□□□□□□ 200）
```

**⚠️ 体力/气力为什么"条 + 绝对值"两个都留**：
- **条**回答"还剩几成"（一眼看懂）
- **绝对值**回答"够不够" —— 婉拒线是 **800**，那是个**绝对数**，光看条判断不出来

**⇒ 所以形式是 `■■□□□□□□□□ 350`，而不是单纯的条。**

**用户需求**：*"某项技能距离下一级的进度能否也能用进度条表示，
这样可以直观地看到经验增加后距离技能升级还有多少进度。"*

### 关键：**升级公式不自己算，复用官方的**

查到官方状态界面画技能进度条用的就是这个链条：

```
@Qol_SkillProgressBar(nChara, nExp)      QoL_Misc.ERB:686
   → @Qol_PrintBar(nSkill, nSkillLv, nXp)   :716
      → CALLF @Qol_XpProgressToNextLevel    :722 / 定义 :730（#FUNCTION）
      → @PRINTLEVELBAR(Lv3 ▅▅▅…▅ Lv4)        UI_Components:1229
```

**`@Qol_XpProgressToNextLevel` 是 `#FUNCTION`，通过 `RESULT:0/1/2` 返回：**

| | 含义 |
|---|---|
| `RESULT:0` | **本级已积累**多少 |
| `RESULT:1` | **本级升满需要**多少 |
| `RESULT:2` | 到下一级为止的总需求 |

**⇒ 进度 = `RESULT:0 / RESULT:1`，直接拿来用。**

**⚠️ 为什么不照抄 EXPLV 公式**：那套公式**按技能分成两类，还有 Lv0/Lv1 的特例**
（`QoL_Misc.ERB:735-760`），自己抄一遍迟早和官方对不上。
**复用官方函数 ⇒ 玩家在状态界面看到的进度，和对话里看到的一定一致。**

**⚠️ 必须用 `CALLF`** —— `#FUNCTION` 标记的函数不能用 `CALL`
（官方 `@Qol_PrintBar:722` 用的也是 `CALLF`）。

### 实现：`@LLM_SKILL_BAR(職種, REF_OUT)`

输出形如 `Lv2 ■■□□□□□□□□ 4/10`，**在经验涨过之后**调用（否则显示的是涨之前的进度）。

|---|---|---|

| 41 会話 / 47 商売 / 52 お酒 | `ABL:話術技能` | 会話経験 |
| 42 戦闘 | `ABL:戦闘能力` | 戦闘経験 |
| 43 教養 | `ABL:教養` | 学習経験 |
| 44 料理 | `ABL:料理技能` | 料理経験 |
| 45 音楽 | `ABL:音楽技能` | **演奏/歌唱/舞踏取最大**（官方 `:704`）|
| 54 採集 / 55 釣り / 56 調合 / 53 家事 | `TALENT:*Lv` | 採集/釣り/調合経験 |

### ⚠️ 三个边界都处理了

1. **满级**（Lv6 以上）→ 官方状态界面就不画这条（`:720`），我们写「已满级」
2. **除以 0 保护** —— `RESULT:1` 万一为 0 不能崩
3. **未匹配職種** → 整项不显示，别让明细出现半截内容

### 合成**一项**显示，而不是两条

**⚠️ 拆开会变成**：`战斗经验＋1　战斗经验 Lv2 ■■…` —— 同一个技能名出现两遍。

⇒ 新增 `@LLM_GAIN_EXP(明细串)` 把三段**合成一条**：

```
战斗经验＋1 Lv2 ■■■■□□□□□□ 4/10
```

**⚠️ 而且"没涨经验的那一次也显示进度条"** ——
多数職種是 25% 才涨，只在涨时才显示的话，玩家几乎看不到进度。
（此时省掉「＋1」，只留 `战斗经验 Lv2 ■■…`。）

### ⚠️ 又差点踩"数值写进 `%…%`"的老坑

```erb
;            ^^^^^^^^ 数值用 {}        ^^^ 返回字符串的函数用 %%    ^^^^^^^^ 数值用 {}
```

**⇒ 判断规则：`%…%` 只给"字符串 / 返回字符串的函数"，`{…}` 给数值。**
已在自查脚本里加了**专项扫描**（自动识别数值变量被写进 `%…%`），本次扫描结果 0。

## 25. ★ 「少女思考中 / 少女重连中（X/3）」+ 20 秒超时重试（✅ 已实现）

**用户需求**：*"把正在思考的字样改为 `少女思考中……`；
请求超过 20 秒未响应自动重试，显示 `少女重连中（X/3）`；重试三次之后弹失败。"*

### 改动一：文案

| 原来 | 现在 |
|---|---|
| `.....%CALLNAME:TARGET%正在思考.....` | `.....少女思考中……` |
| `.....正在思考（已等待 N 秒）.....` | `.....少女思考中（已等待 N 秒）……` |

**5 处全部统一**（开场白 / 主循环 / 累趴台词 / 拒绝台词 / 陪伴台词）。

**⚠️ 秒数保留** —— 原来加它是因为"画面静止会让玩家以为死机"。
现在虽然 20 秒就会重发，但保留秒数能让"它还在跑"这件事可见。

### 改动二：等待上限 90 秒 → **20 秒**

`@LLM_POLL` 里：

```erb
SIF LLM_WAIT >= 20000
	BREAK
```

**⚠️ 这里只是"停止等待"，并没有真的取消请求** ——
取消由调用方做（`LLM_CHAT_CANCEL`），因为**"要不要重试"是调用方的决定**。

### 改动三：**超时也重试**（这是行为上的关键变化）

**原设计是"超时不重试、直接放弃"**，理由写着"服务器半天不回，重发只会等更久"。
**实测证明这个理由是错的**：服务端卡住时，"等"没有意义 ——
隔一会儿重发基本都能成，而干等 90 秒玩家只会以为死机。

**⇒ 现在统一成：只要没成功就重发，最多 4 次尝试（首次 + 重试 3 次）。**

```erb
FOR LLM_TRY, 1, 5              ; 1..4 = 4 次尝试
	…发请求…
	IF LLM_TRY == 1
		PRINTFORML 　.....少女思考中……
	ELSE
		PRINTFORML 　.....少女重连中（{LLM_TRY - 1}／3）……
	ENDIF
	CALL LLM_POLL(LLM_REQ, LLM_STATE, LLM_OUT)
	…
	; ⚠️ 重试前**必须取消**挂起的那次，否则它会叠成并发请求
	SIF LLM_STATE == 0
		CALLSHARP LLM_CHAT_CANCEL(LLM_REQ, LLM_TMP)
	SIF LLM_TRY < 4
		AWAIT 800
NEXT
```

**失败提示**（重试 3 次之后）：

```
[连接失败] 重试 3 次仍然没有回应
[无法发起请求] 检查一下接口配置        ← 一次都没发出去时（配置问题）
```

**`LLM_REQ == 0` 用来区分这两种** —— 发不出去是配置问题，发出去了没回应是网络/服务端问题。

**⚠️ 主循环失败后是 `CONTINUE` 而不是 `BREAK`** ——
**留在对话里**让玩家可以再试一次，比原来直接踢出对话友好得多
（超时那种情况服务端往往马上就恢复了）。

### 改动四：插件 HTTP 超时 60 秒 → **25 秒**

**⚠️ 这个必须跟着改**：ERB 侧 20 秒就放弃并重发，但底层请求还在跑 ——
如果插件仍是 60 秒，被放弃的那次会继续挂 40 秒，
**而且它一旦返回，token 照样计费**（我们只是把结果丢掉 = 白花钱）。
⇒ 收紧到 25 秒（比 20 秒大 5 秒，给"刚好在边缘成功"留点余量）。

**被占用**（游戏开着），复制那一步失败。
**⇒ 需要关掉游戏后重新跑一次 `plugins\LLMBridge\src\build.ps1`。**

## 26. ★ "陪着运动进不了陪伴状态" —— 分支被抢走了（✅ 已修）

### 症状（截图实证）

```
第1轮：（陪她一起做运动，过了 15 分钟）…     ← 陪伴建立成功
第2轮：（时间－3　体力 …）                    ← 什么都没有！
```

**第 2 轮既没有时间推进、也没有「（你陪着她…）」、连消耗都没有。**

### 根因：**"建立陪伴"分支每轮都被抢走，而它在已陪伴时什么都不做**

外层条件（`@LLM_APPLY_DELTA` ⓪b 开头）：

```erb
IF (LLM_D4 == 3 || LLM_D4 == 4) && (Activity_Duration || CFLAG:行動 == 5)
```

**⚠️⚠️ 模型每一轮看到"我正在陪着他"，都会再判一次 `t=3/4`**（"陪你"）——
这是**很自然的输出**，因为它的 prompt 里就写着【你们正在一起做的事】。

于是这个分支每轮都命中。而它内部那段是 `IF LLM_TGKIND == ""` 保护的：

```erb
IF LLM_TGKIND == ""          ; ← 已在陪伴时为假
	…跑官方 "ソース"、推时间、一次性加成、打消息…
ENDIF                        ; ← 整段被跳过 ⇒ **什么都不做**
```

**⇒ 又因为外层 `IF` 已经命中，下面的 `ELSEIF LLM_TGKIND != ""`（"陪伴继续"）
永远轮不到** —— 那一轮就成了空转。

### 修法：**给外层条件加 `LLM_TGKIND == ""`**

```erb
IF (LLM_D4 == 3 || LLM_D4 == 4) && LLM_TGKIND == "" && (Activity_Duration || CFLAG:行動 == 5)
```

**⇒ "已在陪伴中"会自然落到下面的继续分支统一处理，不需要在这里再抄一份继续逻辑。**

**⚠️ 顺带确认了两件事没被破坏**：
- **关系门槛（`LLM_TG_GATE`）婉拒**只在**首次建立**时判 ✓（本来就不该每轮重判）
- **"太累"婉拒**在继续分支里有**自己的一份**（`LLM_TIRED = LLM_PTIRED_LOCK`）✓ 仍然生效

### ⚠️ 顺带修掉一个文案重复

继续分支原来写的是：

```erb
LLM_MSG += @"（你陪着她一起%LLM_FANAME%）"
```

但 **`@FreeAct_Name` 对运动返回的本来就带"一起"**（"一起做运动"，`FREE_ACT_5.ERB:16`）——
于是显示成「你陪着她**一起一起**做运动」。已去掉多余的那个。

### 教训（这类"分支被抢走"是新的坑型）

前面几次的坑都是"**两个地方各判一次、判据不同源**"，
**这次的坑是"两个分支抢同一个条件、而其中一个在特定状态下是空操作"。**

**⇒ 规律**：**带"一次性动作"的分支，条件里必须包含"它确实是第一次"的判据。**
否则那个分支会一直吞掉事件，而真正该处理它的分支永远进不去。

## 28. ★ 能拿到活动的「结束时间」吗？—— 能，但**不能直接用 `Activity_Duration`**（✅ 已实现）

**用户提问**：*"做运动之类的这些活动，我们的自由对话模式能拿到对应的结束时间吗？"*

### 先答问题：能，但有个**大坑**

### 坑在哪：递减发生在**回合末**，而自由对话**不是一个回合**

```erb
; MOVEMENT.ERB:118（@CHARA_MOVEMENT 里，对每个角色）
CALL 自由行動処理(LOCAL)

; MOVEMENT_自由行動.ERB:13
Activity_Duration:ARG = MAX(Activity_Duration:ARG - TIME_PROGRESS(TIME:1), 0)
```

**`@CHARA_MOVEMENT` 是"一条指令结束后"才跑的** ——
而自由对话**整场都在一条指令里面**。

**⇒ 结论：**
| | |
|---|---|
| **能读到剩余分钟吗** | ✅ `Activity_Duration:(角色)` |
| **能算出结束时刻吗** | ✅ `TIME + Activity_Duration`（用 `@時刻表示` 格式化）|
| **⚠️ 它在对话中会减少吗** | ❌ **不会** —— 我们在对话里推进的 `TIME` 要等**退出对话后的那一回合**才被一次性补扣 |

**⇒ 直接用它，会得到"陪了 8 轮、她还剩 60 分钟"这种**永远不结束**的假象。**

**⚠️ 这才是"陪着运动陪不到结束"的**真根因** ——
比"自由行动分支漏写时间推进"更根本**（§14 修的是表，这里修的是里）。

### 修法：引入「有效剩余时间」

**① `LLM_SESSION_T0`**（`LLM_KOJO.ERH`）—— 开场白时记下**本场对话的起始绝对分钟数**：

```erb
LLM_SESSION_T0 = TIME + DAY * 1440      ; ⚠️ 用绝对值，跨天时 TIME 会回绕
```

**② `@LLM_ACT_REMAIN(角色)`（`#FUNCTION`）—— 实际还剩几分钟：**

```erb
LLM_LEFT = Activity_Duration:(LLM_CID)
LLM_LEFT -= MAX(TIME + DAY * 1440 - LLM_SESSION_T0, 0)   ; 扣掉本场已推进的
RETURNF MAX(LLM_LEFT, 0)
```

**③ 三处改用它：**

| 位置 | 原来 | 现在 |
|---|---|---|
| **`LLM_ACT`**（给模型的状态）| 只有「正在运动」| **追加「还剩大约 15 分钟，大约 10时30分结束」** |
| **陪伴继续的结束判定** | `IF Activity_Duration` ← **永远为真** | `IF LLM_ACT_REMAIN(...) > 0` |
| **每轮推进量** | 固定 15 | `MIN(15, LLM_ALEFT)`（**别陪过头**）|

**④ 到点时把帐面也清零：**

```erb
Activity_Duration:(LLM_CID) = 0
```

**⚠️ 为什么必须清零**：不清的话会出现"**认知不一致**" ——
我们已经打了「（一起做运动结束了）」，但 prompt 里的
【你现在正在做什么】仍然写着"正在运动"，她会继续演下去。

清零之后游戏那边也**一致**：回合末 `MAX(0 - N, 0)` 仍是 0，
并会正常触发官方 `"完了"` 分支 ✓

### 附带好处：她终于能"说得出"时间

prompt 里现在会给她：

```
【你现在正在做什么】正在运动（还剩大约 15 分钟，大约 10时30分结束）
```

**⇒ 她可以说「我再练一刻钟就回去」**，而不是笼统的"还在练" ——
这也把 §8.3 那个"工作进度说不清"的教训推广到了**所有自由行动**。

**⚠️ 跨天处理**：`時刻表示` 只认 `0~1439`，
所以 `LLM_AEND >= 1440` 时先 `-= 1440` 再格式化。

### ★ 全量覆盖审计（用户追问："其他陪伴相关的功能也附加了吗"）

把**所有**用到 `Activity_Duration` 的地方列出来逐个判，结果发现**还漏了 3 处**，已补齐：

| # | 位置 | 原来 | 问题 | 现在 |
|---|---|---|---|---|
| 1 | **`LLM_ACT`**（给模型的状态）| 只有「正在运动」| — | ✅ 已加剩余+结束时刻 |
| 2 | **建立陪伴的条件** | `(Activity_Duration \|\| 行動==5)` | ⚠️ **有效剩余已 0 也能"陪"** | ✅ `LLM_ACT_REMAIN(...) > 0` |
| 3 | **发呆的推进量** | `MIN(Activity_Duration, 30)` | ⚠️ **会陪过头** | ✅ `MIN(LLM_ACT_REMAIN(...), 30)` |
| 4 | **自由行动建立的推进量** | `MIN(LLM_ELAPSE, Activity_Duration)` | ⚠️ **同上** | ✅ `MIN(LLM_ELAPSE, LLM_ACT_REMAIN(...))` |
| 5 | **陪伴继续的结束判定** | `IF Activity_Duration` ← **永远为真** | ⚠️ 「结束了」永不触发 | ✅ 已改 |
| 6 | **陪伴继续的每轮推进量** | 固定 15 | ⚠️ 会超过实际剩余 | ✅ `MIN(15, LLM_ALEFT)` |
| 7 | **`@LLM_BUILD_TOGETHER_PROMPT`**（陪伴建立的追加台词）| 完全没提时间 | ⚠️ 她会说「那咱们接着练吧」，而其实只剩 3 分钟 | ✅ 已加 |
| 8 | **到点时清零 `Activity_Duration`** | 没清 | ⚠️ 界面说"结束了"、prompt 还说"正在运动" | ✅ 已加 |

**现在只剩 3 处直接用 `Activity_Duration`，且都合理：**

| 行 | 用途 | 为什么可以 |
|---|---|---|
| `LLM_ACT` 的分支条件 | 判断"要不要走自由行动分支" | 分支内部立刻用 `LLM_ACT_REMAIN` 判，到点会打「其实已经到点了」✓ |
| 到点清零 ×2 | 写操作 | 就是要写它 ✓ |
| `@LLM_ACT_REMAIN` 内部 ×2 | 读原始值 | 它就是为处理这个而生的 ✓ |

**⇒ 结论：陪伴相关的 8 个点全部覆盖。**（这也是"**同一类判断在所有入口都要同源**"
这条规律的第 N 次应用 —— 和前面 `LLM_PTIRED_LOCK`、`工作进度` 是同一个道理。）

## 29. ★ 「结束后模型知不知道」—— 差点又变成"明明结束了还说没结束"（✅ 已修）

**用户追问**：*"结束之后 llm 能知道该状态结束了吗？有没有可能像之前一样
明明工作或者运动已经结束，却还回复没结束的情况？"*

### 查证结果：**会，而且原因和 §19 一模一样**

我们在结算里把 `Activity_Duration` 清零之后，下一轮组 prompt 时：

```erb
LLM_ACT = ""
IF CFLAG:睡眠              → 不成立
ELSEIF BATHROOM(...)       → 不成立
ELSEIF Activity_Duration:(LLM_CID)   → ★ **刚被清零，不成立**
ELSEIF CFLAG:行動 == 5     → 不成立（没在上班）
ELSEIF CFLAG:陪睡中        → 不成立
ENDIF
; ⇒ LLM_ACT 仍然是 ""
```

而注入那边是：

```erb
SIF LLM_ACT != ""
	REF_PROMPT += @"\n【你现在正在做什么】%LLM_ACT%"
```

**⇒ 空串 ⇒ 整行都不注入 ⇒ 模型拿不到任何"她现在在做什么"的信息 ⇒
只能从对话历史里编 ⇒**玩家问"结束了吗"，它答「还没呢」。**

**这和 §19「工作结束传不到模型」是**同一个病**：
不是信息错了，而是**信息压根没送到**。**

### 修法：三层

**① 记下"刚结束"并保留一轮**（`LLM_JUST_ENDED`，`LLM_KOJO.ERH`）

在两个"清零点"各写一次：

```erb
LLM_JUST_ENDED = %LLM_FANAME%     ; 或 %LLM_TGKIND%
```

**② 在 `@LLM_BUILD_SYSTEM_PROMPT` 的分支链**之后**消费它**：

```erb
IF LLM_ACT == "" && LLM_JUST_ENDED != ""
	LLM_ACT = @"刚把「%LLM_JUST_ENDED%」做完，正在歇口气"
ENDIF
```

**③ 兜底：`LLM_ACT` 永远不为空**

```erb
SIF LLM_ACT == ""
	LLM_ACT = "手头没什么事，正闲着"
LLM_JUST_ENDED = ""      ; 用完就清（无论有没有用到）
```

**⇒ 这一步才是治本**：即使没有"刚结束"这件事，
【你现在正在做什么】**也不会凭空消失** —— 她闲着就照实说"闲着"。
（**"让一项信息消失"永远比"给一项信息"危险**：消失时模型不会觉得缺了什么，
它会**用历史去补**，而补出来的往往是错的。）

### ⚠️ 工作那一侧**本来就覆盖了**（不需要额外改）

| 机制 | 内容 |
|---|---|
| **`LLM_ACT`** | `CFLAG:行動 == 5` 仍成立时 → 「刚把手头的活干完，正在收拾东西」|
| **`LLM_ROUTINE`**（§19 修的）| 「…你今天要从6时0分上到12时0分，**不过活已经干完了，你现在已经收工**」|

**⇒ 两条独立路径都在说"已收工"**，而且 §19 加过交叉一致性规则
（冲突时以【你现在正在做什么】为准）✓

**⚠️ 为什么不给工作也加 `LLM_JUST_ENDED`**：
那是**第三份**同样的信息，只会增加"三处不同源"的风险（本项目栽过两次）。
工作侧已经有两处**判据同源**的表达，够了。

### 📌 这一节的规律

> **"结束一件事"要同时做两件事：**
> **① 改状态（`Activity_Duration = 0`）**
> **② 确保这件事在下一轮的 prompt 里**仍然被表达**（哪怕只是"刚做完"）**
>
> 只做 ① 会留下一个**沉默的空洞**，而模型面对空洞会**用历史去填** ——
> 填出来的正是"还没呢"。

`LLM_JUST_ENDED`，**工作相关的 3 处"结束"全漏了**：

|---|---|---|

### 二、模块化：`@LLM_MARK_END` —— **唯一登记入口**

```erb
@LLM_MARK_END(REF_MSG, LLM_WHAT, LLM_TEXT)
;  REF_MSG  —— 追加到哪（传 LLM_MSG）
;  LLM_WHAT —— 那件事的名字；**空串 = 这不是"结束"，不登记**
```

1. **所有"结束"都必须经过这里** —— 否则 `LLM_JUST_ENDED` 不会写，
   下一轮 prompt 里"她刚做完"这件事会**凭空消失**，模型只能从历史里编
   ⇒ 回一句「还没呢」（§29）。
2. **"被拒绝"不是"结束"** —— 关系不够 / 太累婉拒时，那件事**还在继续**，
   她下一轮仍然"正在运动"。这种传空 `LLM_WHAT`，只显示提示、**不登记**。

**⚠️ 为什么它刻意不碰 `REF_TOGETHER`**：那是 `@LLM_APPLY_DELTA` 的引用参数，
把引用参数再传给另一个函数的引用参数**不可靠**（本项目踩过）。
调用方自己清（就一行，而且清得明白）。

## 32. ★ 开场白不接上次的话题了（✅ 已修 —— 是"优先级"那道防线写得太宽）

| # | 位置 | 原来写的 | 问题 |
|---|---|---|---|
| ① | **`LLM_PREV` 注入标题** | 【你们上一次交谈的片段（**仅供参考 · 优先级低**）】| 标题就写着"优先级低、仅供参考"，模型直接忽略 |
| ② | **【当前的事实】规则** | 「…**一律以上面这些为准，不要顺着旧话题继续**」| ★★ **最要命的一句** —— 把**话题**也一起否掉了 |
| ③ | **开场白要求** | 只写"落进你此刻的处境"（做什么/在哪/天气）| 完全没提"上次聊过什么" |

**⚠️ ②是真正的祸首**：那句话的**本意**只是压住"别把旧地点/旧天气当现状"（§12/§19），
但"**不要顺着旧话题继续**"这半句**范围太宽** ——
"话题"和"事实"是两回事，它把两者一起禁掉了。

**⇒ 结果**：开场白退化成"只会描述天气"，玩家觉得"她怎么像不认识我"。

### 修法：把「事实」和「话题」**明确划开**

**②【当前的事实】—— 收窄到四类事实：**

```
⚠️⚠️ 它们压过对话记录里的「事实」——
   也就是地点、天气、时间、你现在在做什么这四类；
   两者对不上时，一律以上面这些为准。
⚠️ 但只限「事实」—— 你们聊过的话题、约定、心事并不过时，
   可以放心接着聊。别因为「情况变了」就把之前说过的话全丢掉。
```

**①`LLM_PREV` —— 标题去掉"优先级低"，并明说"话题没过时"：**

```
【你们上一次交谈的片段】
…
（⚠️⚠️ 这是上一次聊天，目的是让你和他之间有个连贯印象：
   · 里面的地点、天气、时间都已经过时 —— 别当成现在的情况。
   · 但话题、约定、心事并没有过时 —— 可以自然地接着聊
     （「你上次说的那个，后来怎么样了」）。这正是「熟人」该有的样子。
   · 万一和下面的【当前的事实】冲突，以【当前的事实】为准
     （冲突只可能出在「事实」上，比如地点 —— 话题不会有冲突）。)
```

**③开场白要求 —— 把"接上次"列为**第一优先**，处境退为"同时"：**

```
⚠️ 玩家刚走到你面前。开口之前，先看【你们上一次交谈的片段】——
   · 上面有内容时，优先接它：一句「上次你说的那个…」「后来怎么样了」
     比描述天气更像「见到熟人」，也最能体现你们之间的关系。
   · 接上之后，这句话仍然要落到此刻（看下面的处境项）——
     光接旧话题会显得你在背台词，「上次的事 + 现在的样子」才自然。
   · 上次没聊过什么（那个片段是空的）就只用处境开场，不用硬凑。
```

**⚠️ 关键是最后那条**："光接旧话题会显得你在背台词" ——
**只接话题会走向另一个极端**（像在念记录），所以要求**两者结合**。
这也和 §31 那条"回忆不能当谈资"呼应：**回忆要落到当下才算活的**。

## 33. ★ PALAM（调教参数）是什么 + 我们接了没有（调研结论）

**用户提问**：*"这些数值有什么用？以及我们的自由对话系统有没有调用这些数值增减的可能性？"*
（附截图：`恭顺 135 + 9 = 144` / `情欲 322 + 20 = 342` / `咲夜：好意 +222 / 优越 +780` 这类）

### ① 截图那两栏是什么

**是游戏自己的 PALAM 变化报告** —— `SOURCE.ERB:1080-1105`（在 `@SOURCE_CHECK` 里）：

```erb
FOR LOCAL:1,0,CHARANUM
	FOR LOCAL,0,100
		SIF CUP:(LOCAL:1):LOCAL - CDOWN:(LOCAL:1):LOCAL == 0
			CONTINUE
		SIF CFLAG:(LOCAL:1):現在位置 == CFLAG:MASTER:現在位置
			PRINTFORML %PALAM_TR(PALAMNAME:LOCAL)% {PALAM:…} + {CUP:…} = {PALAM:… + CUP:…}
		PALAM:(LOCAL:1):LOCAL += CUP:(LOCAL:1):LOCAL - CDOWN:(LOCAL:1):LOCAL
		CUP/CDOWN = 0
	NEXT
NEXT
```

- **格式**：`名称  当前值 + 增量 = 新值` —— 和截图一模一样
- **时机**：**回合末**（`@SOURCE_CHECK`）
- **范围**：**只显示和玩家在同一地点的角色**（`:1092 / :1098`）

**⇒ 所以这不是什么调试面板，是正常的回合结算报告。**
**⇒ 也再次印证：对话里写的 `SOURCE`，要等**退出对话那一回合**才结算成 PALAM。**

### ② 这些值各有什么用

| PALAM | 由哪个 `SOURCE` 来 | 作用（都能在代码里查到）|
|---|---|---|
| **恭順(10)** | `SOURCE:恭順` | → `ABL:従順` / `ABL:奉仕精神`（`TRACHECK_好感度上昇処理.ERB:440-444`）；指令成功率 |
| **欲情(11)** | `SOURCE:欲情` | 发情 / 性行为可否；**欲求不满度**（`SOURCE.ERB:1175-1206`）|
| **屈服(12)** | `SOURCE:屈従` | 与恭順取 max → `ABL:従順` |
| **好意(20)** | `SOURCE:受動` | → `ABL:親密`（`:434`）；各角色事件阈值（1500 / 2500 之类）|
| **優越(21)** | `SOURCE:征服` | 角色事件（如輝夜 `:637`）；性行为中"支配"走向 |

**⚠️ 还有一个隐藏的倍率杠杆**：`@YUKIZURI_BONUS` 里

```erb
TFLAG:97 *= 10                     ; ← 好感度 ×10
LOCAL = GETPALAMLV(PALAM:好意,10) - 1      → ABL:親密
LOCAL = GETPALAMLV(PALAM:恭順,3) - 1       → ABL:奉仕精神
LOCAL = MAX(GETPALAMLV(恭順,3), GETPALAMLV(屈服,3))  → ABL:従順
```

**⇒ 恭順 / 屈服 / 好意 实际上决定"**好感度获取效率**"和几个 ABL 的档位。**
这也是为什么它们看着不起眼、实际很重要。

### ③ 我们的系统接了没有 —— **✅ 已经接了，而且是自动的**

**因为我们照抄了官方的 `"ソース"` 分支**：

```erb
TRYCALLFORM 自由行動内容_{Activity_Type}(角色, "ソース", 倍率)
```

**以运动为例**（`FREE_ACT_5.ERB:90-99`），这一调就自动写入：

```erb
DOWNBASE:MASTER:体力 += 40 * 時間係数      ; 双方体力气力
DOWNBASE:CHARA:体力  += 20 * 時間係数
SOURCE:CHARA:歓楽 = (150 + ((ABL:親密 + ABL:MASTER:戦闘能力) * 50)) * 時間係数
SOURCE:CHARA:受動 = (100 + ((ABL:従順 + ABL:MASTER:戦闘能力) * 50)) * 時間係数
SOURCE:CHARA:征服 = (100 + ((ABL:施虐属性 + ABL:CHARA:戦闘能力) * 100)) * 時間係数  ; ★ 喂给 優越
TFLAG:信頼度管理 = 2
EXP:MASTER:戦闘経験 ++
```

**⇒ 所以"陪着运动"其实**已经在加** `SOURCE:征服`（→ 優越）了** ——
玩家截图里那个 `优越 +780` **很可能就是它**。

**⚠️ 顺带发现**：官方这条 `"ソース"` 自己也加了 `EXP:MASTER:戦闘経験 ++` ——
好在我们**只在"帮忙干活"那条路**（`@LLM_WORK_EXP`）另加经验，
陪伴这条路不碰，所以**没有双重计数** ✓

**我们**额外手写**的只有两处**：

| 位置 | 写了什么 | 为什么必须手写 |
|---|---|---|
| 帮忙干活（`@LLM_WORK_DO`）| `SOURCE:歓楽` / `SOURCE:受動` | 这条路**不走** `"ソース"`，所以照抄 `COMF304` 自己写 |
| "性骚扰"那一档 | `PALAM:欲情 += PALAMLV:3` | 对话里没有对应的官方指令 |

### ④ 要不要再额外补别的？—— **建议不要**，三条理由

1. **现在的做法**天然正确**：自由对话的数值 = **对应官方指令的数值**。
   我们不需要判断"该给什么" —— **照抄那条指令的 `"ソース"` 就行**。
2. **直接写 `PALAM:*` 会绕开 `SOURCE → CUP/CDOWN → PALAM` 那条链** ——
   那条链带 `TFLAG:102` 闸门、上下限、角色修正；
   绕过去容易失控（本项目已经在"未结算 / 钳位"上栽过好几次，见 §20）。
3. **这些是**调教参数**（身体 / 服从关系）** ——
   **纯聊天推进它在语义上是错的**，会让玩家"多聊几次就攻略完成"，
   把整个游戏的调教线架空。

**⇒ 以后若要给对话加新数值，正确做法是：
找到**语义等价的那个官方指令**，走它的 `"ソース"` 分支 —— 而不是自己写 `PALAM`。**

### 📌 这条结论值得单独记

> **自由对话的数值效果，应当在**官方指令的通道**里完成，
> 而不是在我们自己的代码里另算一份。**
>
> 这样做的三个好处：
> · **判据同源** —— 官方改平衡，我们自动跟着改
> · **不会漏结算** —— `DOWNBASE`/`SOURCE`/`TFLAG:信頼度管理` 的结算链由游戏负责
> · **语义正确** —— 官方那条 `"ソース"` 已经写好了"这件事该给什么"

```
67: 相性,31,80;早苗                    ← 人际关系（RELATION）
68: 相性,55,150;白莲
73: CSTR,工作情報,保姆　周二、五　20时～24时
74: CSTR,職場,命莲寺（二）·寺子屋（五）

83: CSTR,18,变成像嗜虐的、倒错的折磨。
```

### 二、我们目前的缺口（实测统计）

```
CSTR:        0 处    ← ★★ 角色介绍文完全没读
RELATION:    0 处    ← ★★ 人际关系完全没读
PERSONALITY: 0 处    ←    性格没读
GET_MAPNAME: 2 处    ✓    地点已有
```

**⚠️ 而且我们现有的三张表是**手写的**：**

| 函数 | 覆盖 | 问题 |
|---|---|---|
| `@LLM_CHARA_TRAIT` | 48 人 | 手写 |
| `@LLM_CHARA_FEATURE` | 16 人 | 手写 |
| `@LLM_CHARA_LIKES` | 31 人 | 手写 |

**⇒ 官方**本来就有**这些信息**（`CSTR` + `PERSONALITY_TYPE` + `RELATION`），
手写表应当**退化为补充**，主体改用官方数据源。**

### 三、可行性：✅ 完全可行，价值很高

**技术上一件事都不难** —— 全部是"读一个变量"：
`CSTR:(角色):10` / `RELATION:(角色):(对方)` / `PERSONALITY_TYPE(角色)`。

**⚠️ 唯一要照抄官方顺序的**：角色介绍**可能被口上覆盖**
（`PRINT_STATE2.ERB:167-175`：先 `CALL KOJO_ACTIVE_INFO` + `TRYCCALLFORM CHARA_INFO_KOJO*`，
`RESULT` 非 0 才用口上版，否则遍历 `CSVCSTR(NO, 10..19)`）。

### 四、建议的注入方案（按价值排序）

**① ★★ 角色介绍文 →【她是什么样的人】**
- 这是**人设的灵魂**：种族 / 能力 / 性格 / 行为倾向
- **⚠️ 和现有的 persona 不是一回事**：我们现在注入的是**口上剧本标识**
  （`@KOJO_ACTIVE_INFO` 的 `RESULTS`），那是"她怎么说话"；
  **`CSTR:10~18` 才是"她是什么人"** ✓ 互补，不重复
- ⚠️ 长度 ~9 行，是 token 大头 —— **但值**

**② ★★ 人际关系 →【她和其他人的关系】**
- **这是"活人感"最大的一块** ——
  现在她提到别的角色**只能靠模型自带的东方知识**，完全不知道"她自己跟谁好"
- **⚠️ 只给偏离 100 的**（100 = 普通，没有信息量）⇒ 建议**前 5 名 + 后 3 名**
- **✅ 语义分档官方已经有现成的**（`QoL_ShowRelation.ERB:41-54`，配色就是分档）：

  | 值 | 含义 |
  |---|---|
  | `< 60` | 关系很差 |
  | `< 100` | 有点疏远 |
  | `= 100` | 普通 |
  | `< 130` | 还不错 |
  | `< 200` | 很好 |
  | `>= 200` | 非常好 |

**⇒ 不用自己编语义，直接照这套说。**

**③ 性格**（`PERSONALITY_TYPE`）→ 一行，但能定性

**④ 工作情报 / 工作地点**（`CSTR:工作情報` / `職場`）→ 补进现有的 `LLM_ROUTINE`
- ⚠️ 现在 `LLM_ROUTINE` 只有「周几 + 时段」，**没有工作名**（如"保姆"）

**⑤ 常去区域 / 自宅位置** → 可以自然聊到"我常去哪""我住哪"

**⑥ 弹幕技能** → ⚠️ 战斗相关，日常对话价值低，**建议跳过**

### 五、注意事项

| # | 注意点 |
|---|---|
| 1 | **prompt 长度**：角色介绍 9 行 + 人际关系 8 项是一笔开销 ⇒ **介绍全给、关系只给偏离的** |
| 2 | **口上覆盖优先** —— 照抄官方顺序（见上）|
| 3 | **关系是单向的**：`RELATION:A:B` = "**A 对 B**"；我们要的是 `RELATION:(她):(别人)` |
| 4 | **路人角色**走另一套（`RANDOM_CHARANUM`）—— 我们的 TARGET 是固定角色，但可加保护 |
| 5 | **别让模型念数据** —— 注入时照 §31 的写法说明"这是背景，不是话题" |

### 六、优先级判断

**这个（§35）应优先于技能等级（§34）。**
理由：技能等级回答"她**擅长什么**"，
而角色介绍 + 人际关系回答"**她是谁、她跟谁有关系**" —— **后者对"活人感"的作用大得多**。
两者可以一起做，但先做这个见效更快。

| | 平均角色 | 小傘这类（最长）|
|---|---|---|

### 三、★ 顺手发现一个**双赢**的优化

**⚠️ 关键背景**：DeepSeek 一类的 API 有**上下文缓存（Context Caching）** ——
**重复的前缀**按更低价计费（约 1/10）。

**但我们的 prompt 每轮都在变**（时间、状态、工作进度、体力…）⇒ **前缀不稳定、缓存难命中。**

**⇒ 建议：把"固定不变的内容"放在 prompt **最前面**，把"每轮变的"放后面。**

而**角色介绍 / 人际关系 / 性格**恰好是**逐角色固定**的（一个月都不会变）✓

**⚠️ 而且这和"该不该放前面"的直觉**刚好一致**：**
这两个功能**本来就该是"背景"**（§31 的教训：回忆不能当谈资；
§35 也强调"这是背景不是话题"）—— **背景就该弱影响、不该抢注意力** ✓

**⇒ 放前面 = 定位正确 + 缓存友好，双赢。**
（对比：§19 那些"当前事实"是**必须抢注意力**的，所以它们留在靠后位置 ✓ 不冲突。）

|---|---|---|
| **人际关系只给**偏离 100 的**前 5 + 后 3**（本来就这么设计）| 已在估算内 | 无 |
| **跳过弹幕技能** | — | 战斗相关，日常用不上 |
| **控制在 8 条关系以内** | 小 | 无 |
| **不加"注入说明"文字** | 省 ~150 字 | ⚠️ **不建议** —— 说明是防止模型念数据的关键，砍了反而浪费前面所有 token |

## 37. ★★★ 已实现：官方「角色介绍 / 性格 / 人际关系 / 工作情报」（与手写表**并存**）

因为有些官方的内容写的很少，我感觉不足以支撑 llm 的语言。"*

### 一、设计原则：**两组并存，官方打底 + 手写补细节**

| | 官方数据 | 手写表 |
|---|---|---|
| 内容 | 她是**什么人**（种族/能力/背景/社会关系）| 她**怎么说话、在意什么** |
| 覆盖 | 全角色 ✓ | 48 / 16 / 31 人 |
| 缺点 | **有的角色写得很少**（多数只有一行 26~34 字）| 需要人工维护 |
| **⇒ 结论** | **都注入，互补** | |

### 二、新增的 4 个函数

| 函数 | 作用 | 数据源 |
|---|---|---|
| `@LLM_CHARA_INTRO(角色, REF_OUT)` | 角色介绍文 | `CSVCSTR(NO:角色, 10~18)` |
| `@LLM_CHARA_PERSONALITY(角色, REF_OUT)` | 性格类型 | `@PERSONALITY_TYPE`（`#FUNCTIONS`）|
| `@LLM_CHARA_RELATION(角色, REF_OUT)` | 人际关系 | `RELATION:(她):(别人)` |
| `@LLM_REL_WORD(值, REF_OUT)` | 值 → 中文措辞 | 分档**照抄官方配色阈值** |

**⚠️ 几个实现要点：**

1. **角色介绍用 `CSVCSTR(编号, 索引)` 而不是 `CSTR:角色:索引`** ——
   官方自己取介绍文用的就是 `CSVCSTR`（`PRINT_STATE2.ERB:171-174`），照抄最稳。
2. **性格是 `#FUNCTIONS`** ⇒ 只能用表达式调用（`REF_OUT = %PERSONALITY_TYPE(...)%`），不能 `CALL`。
3. **人际关系只给"最好 3 个 + 最差 3 个"** ——
   `RELATION` 是 N×N 表，全给会塞爆 prompt；而 `100`（普通）和 `0`（未设定）**没有信息量**。
4. **⚠️ `0` 必须排除** —— 它表示"没有这段关系"，**不是"关系极差"**。
5. **排序不用数组** —— 按 `(值降序, 索引升序)` 逐轮取"上一个之后的最大值"。
   （`#DIM` 数组要占 `#LOCALSIZE`，200 个槽位吃不消。）
6. **关系分档直接照抄官方**（`QoL_ShowRelation.ERB:41-54` 的配色阈值）：

   | 值 | 措辞 |
   |---|---|
   | `< 60` | 很不对付 |
   | `< 100` | 有点疏远 |
   | `< 130` | 还算亲近 |
   | `< 200` | 关系很好 |
   | `>= 200` | 非常亲近 |

## 38. ⚠️ 真 BUG：「我很困」跟作息对不上（✅ 已修 —— 影响 42% 的角色）

**用户实测**：*"我们现在的『我现在有些困』这个东西是怎么判断的？
我体感这个好像在 llm 中并没有随着作息输入，有些时候的开场白会冷不丁来一句。"*

**⇒ 用户体感完全正确，而且根因是一个真 bug。**

### 根因：`就寝時間` / `起床時間` 的"两种形态"只处理了一种

原判据（`@LLM_BUILD_SYSTEM_PROMPT` 的 `LLM_SCHED` 第 ③ 条）：

```erb
ELSEIF CFLAG:(LLM_CID):就寝時間 > 0 && (TIME > CFLAG:(LLM_CID):就寝時間 || TIME < CFLAG:(LLM_CID):起床時間)
	LLM_SCHED = "现在已经过了你平时的睡觉时间，你很困，只是还没走"
```

**两个值都是**当天分钟数**（0~1440），所以"她什么时候在睡"有**两种形态**：**

| 形态 | 例子 | 正确判据 |
|---|---|---|
| **跨夜型**（`就寝 > 起床`）| 23:00 睡、7:00 起（1380/420）| `TIME > 就寝 \|\| TIME < 起床` ← `\|\|` 对 |
| **同天内**（`就寝 < 起床`）| 1:00 睡、10:00 起（60/600）| `就寝 < TIME < 起床` ← **要用 `&&`** |

**⚠️ 原代码对第二种也用了 `||`** ⇒ 变成 `TIME > 60 || TIME < 600` ——
**除了 1:00 那一分钟，整天都成立！**

### 影响范围（量过全部 165 个有作息的角色）

| | 数量 | 旧判据 |
|---|---|---|
| 跨夜型 | 95 个 | ✅ 正确 |
| **同天内** | **70 个（42%）** | ❌ **覆盖 100% 的时间** |

**受影响的包括：萃香、魔理沙、露米娅、隐岐奈、美宵…**（全是"凌晨睡、白天起"型）
**⇒ 这 70 个角色**任何时间**都会被告知"你很困，只是还没走"。**

### 修法：拆出 `@LLM_IS_SLEEPTIME(角色)`

```erb
@LLM_IS_SLEEPTIME(LLM_CID)
#FUNCTION
…
SIF LLM_A <= 0 || LLM_B <= 0
	RETURNF 0
IF LLM_A > LLM_B
	SIF TIME > LLM_A || TIME < LLM_B      ; ① 跨夜
		LLM_R = 1
ELSE
	SIF TIME > LLM_A && TIME < LLM_B      ; ② 同天内
		LLM_R = 1
ENDIF
RETURNF LLM_R
```

**⇒ `LLM_SCHED` 第 ③ 条改成 `ELSEIF LLM_IS_SLEEPTIME(LLM_CID)`** ——
**判据只有一个来源**（又是那条规律：同一件事不能两处各判一次）。

### 修复前后模拟（一天 24 个整点里说"困"的次数）

| 角色 | 就寝/起床 | 类型 | 旧 | 新 |
|---|---|---|---|---|
| **多多良小伞**（玩家实测那位）| 01:00 / 10:00 | 同天内 | **24 次（整天）** | **8 次** ✅ |
| 博丽灵梦（对照组）| 23:00 / 07:00 | 跨夜型 | 7 次 | 7 次（不变）✅ |

### ★ 追加验证：反极性作息（蕾米莉亚那种"白天睡、晚上醒"）

**用户追问**：*"蕾米莉亚那种白天睡晚上醒的角色呢？"*

**⇒ 查证：已经被**天然覆盖**，不用额外处理。**

```
★ レミリア   就寝 06:00 / 起床 18:00  → 同天内(就寝<起床)
  00:00·醒 … 06:00·醒 07:00·困 … 17:00·困 18:00·醒 … 23:00·醒
```

**⚠️ 关键理解**：`同天内` 这个分支**天然涵盖两种相反的作息** ——

| 语义 | 例子 | 判据 |
|---|---|---|
| 凌晨睡、白天起 | 小伞 01:00~10:00 | `就寝 < TIME < 起床` |
| **白天睡、晚上醒** | **蕾米莉亚 06:00~18:00** | **同一条判据** |

**因为判据的本质就是"从**就寝**走到**起床**的那段区间"** —— 区间在哪一侧与代码无关 ✓

**四种代表性角色的最终判定表**（`困` = 会被告知在犯困）：

| 角色 | 就寝 / 起床 | 类型 | 困的时段 |
|---|---|---|---|
| **蕾米莉亚** | 06:00 / 18:00 | 同天内 | **07:00 ~ 17:00**（白天睡）✅ |
| 小伞 | 01:00 / 10:00 | 同天内 | 02:00 ~ 09:00 ✅ |
| 灵梦 | 23:00 / 06:00 | 跨夜 | 00:00 ~ 05:00 ✅ |
| 美铃 | **24:00** / 06:00 | 跨夜 | 00:00 ~ 05:00 ✅ |

**⚠️ 顺带覆盖到一个边界情况**：**18 个角色的 `就寝時間 = 1440`（24:00）**
（美铃、永琳、映姬、慧音…）——  它们走跨夜分支，`TIME > 1440` 恒假、
`TIME < 起床` 生效 ⇒ **判定正确** ✓（`TIME > 1440` 那半句是死代码，无害）

**（穷举验证时曾报 18 处"不一致"，查明是我的**验证脚本**瑕疵 ——
暴力法从 `1440` 出发先自增、漏测了 `00:00` 那一刻；**代码本身是对的**。）**

### ★ 顺带修掉另一处矛盾：她**真的在睡**时不该说"只是还没走"

第 ③ 条的措辞是「你很困，**只是还没走**」—— 它**假定她还醒着**。
可她要是**真的在睡**（`CFLAG:睡眠 = 1`，比如玩家去吵醒吸血鬼），
这句话就和 `LLM_ACT` 的「正在睡觉（刚被吵醒）」**直接打架**。

**⇒ 修法：加 `!CFLAG:(LLM_CID):睡眠` 条件** —— 睡着时不发这句
（"她在睡"这件事 `LLM_ACT` 已经说清楚了）。

```erb
ELSEIF !CFLAG:(LLM_CID):睡眠 && LLM_IS_SLEEPTIME(LLM_CID)
	LLM_SCHED = "现在已经过了你平时的睡觉时间，你很困，只是还没走"
```

**⚠️ 又是那条规律的又一例**：**同一个事实（"她现在该睡"）由两处表达时，
必须保证两处不说矛盾的话。**

### ★ 追加：`LLM_SCHED` 现在是**四档**（用户要求补"睡醒后 1 小时"）

**用户要求**：*"我想让其睡前的一小时说自己有些困意，
睡醒后的一小时说自己有些没睡醒，把这个需求也加上。"*

### 📌 教训（这次追问本身也是教训）

> **"我做了"和"我证明给你看了"是两回事。**
> 前一条我只给了**边界附近的几个采样点**，看起来像"只有睡后那段"；

> 如果你恰好用灵梦（跨夜型）试，一切正常；用小伞才发现。
> **⇒ 写这种判据时，两种形态要各找一个角色验。**（这次是量了全部 165 个才发现的。）

台词是模型按 persona/语气自己写的。所以"单调"的根子在
**注入措辞对谁都一样** —— 换个说法，模型产出的台词也就跟着变了。

```
② prompt 里按它注入：「你困得撑不住了，这一轮就打算收尾去睡」
③ 她说完 + 结算之后：按**同一个值** BREAK（真的结束对话）
```

**⇒ 两处用同一个判定 ⇒ 她的话和系统的动作必然一致** ✓
**⇒ 而且她有一轮机会把道别**说出口**，不是被系统硬掐断** ✓

| 其它（认识 / 陌生）| 80% |

**⚠️ 为什么用这几档而不是自造公式**：它们和游戏既有的关系分级**完全对齐**，
玩家一看就懂"为什么她今天没赶我走"。

**⚠️ 恋人档的刹车在哪**：`@LLM_TOO_TIRED`（玩家体力/气力见底时她心疼地让你去休息）——
那才是"熬到昏厥"的兜底 ✓ 和这个"温和的收尾"职责不同。

### 三、判据同源（又是那条老规矩）

`@LLM_IS_SLEEPY(角色)` = **睡前 1 小时 或 已到睡觉时段**，

## 40. ★★ 玩家说「再见」就真的结束 + 她会挽留或送别（✅ 已实现）

**用户要求**：*"玩家说结束语真的会结束 —— 比如「再见」「下次见」「好的 回头再见」
「晚安」「那我先走了」；角色判定是否接受玩家离开（越亲密越不想让玩家走）；
拒绝则说挽留的话、接受则说告别的话；而且这个话语最好和她之后一小时内要做的事挂钩。"*

### 一、⚠️ 先说一个必须先解决的**时序陷阱**

**本来想用模型的 `LLM_D4`（言论性质）来报"玩家在道别" —— 但行不通**：

```
玩家说话 → 组装 prompt → 她回复（内含 D4）→ 结算
                ↑
      要在这里决定"挽留还是送别"，可那时 D4 还没产生 ⚠️
```

**⇒ 只能在 **ERB 侧用关键词**判**（玩家输入在组装 prompt 之前就有）✓
**⇒ 这样才落回"先判、再让她说"（§18）** ✓

### 二、三个新函数

| 函数 | 作用 |
|---|---|
| `@LLM_IS_BYE(文本)` | 关键词判定（`#FUNCTION`）|
| `@LLM_NEXT_HOUR(角色, REF_OUT)` | "你接下来一小时内要做什么" |
| `@LLM_BYE_CHECK(角色, 输入)` | 判定接受 / 挽留 → `LLM_BYE_MODE` |

**道别关键词**（宁可误判也别漏判）：
`再见 / 拜拜 / 告辞 / 失陪 / 晚安 / 下次见 / 回头见 / 明天见 / 待会见 /
我走了 / 先走 / 该走 / 得走 / 不早了 / 时间不早`

### 三、`LLM_BYE_MODE` 三个值

| 值 | 含义 | 后续 |
|---|---|---|
| 0 | 玩家没在道别 | 什么都不做 |
| **1** | **接受**（她送他走）| 说完 → **BREAK**（真的结束）|
| **2** | **挽留**（不想让他走）| 说完 → 继续聊，并记一次 |

**挽留概率（越亲密越高 —— 用户明确要的方向）：**

| 关系 | 挽留率 |
|---|---|
| 恋人 / 爱欲 | **80%** |
| 恋慕 | 55% |
| 思慕 | 30% |
| 其它 | 10% |

**⚠️⚠️ 三个修正，全部把挽留压到 0：**

1. **她自己一小时内有事**（要上班 / 要睡）→ 不挽留，
   **反过来顺口说自己也要走了** —— 这正是用户要的"话语和接下来要做的事挂钩" ✓
2. **玩家快撑不住了**（`LLM_PTIRED_LOCK`）→ 心疼地放他走（和累趴那套同源）✓
3. **本场已经挽留过一次**（`LLM_BYE_KEPT`）→ 第二次不再留 ✓
   否则玩家说三次"真的得走了"她还三次挽留，就变成耍赖了

### 四、prompt 注入（两种）

**接受时**（`LLM_BYE_MODE == 1`）：
```
★★ 他刚才是在跟你道别，而你接受了 ——
   · 说一句送别的话，用你自己的口吻（别客套、别客服腔）。
   · ⚠️ 顺口提一句你自己接下来要做什么：你马上就要去上班了（6时0分）
     这正是你放他走的原因 —— 说出来比干巴巴的「再见」好得多。
   · 说完这句，这场对话就结束了 —— 别再抛新话题。
```

**挽留时**（`== 2`）：
```
★★ 他刚才是在跟你道别，但你不想让他走 ——
   · 说一句挽留的话，用你自己的口吻（撒娇 / 找借口 / 耍赖 / 装没听见…都行）。
   · 这不是客套，是你真的舍不得 —— 但也别写成苦情戏，短一点、像随口说的。
   · ⚠️ 别用「再坐一会儿」这种万能句，用和你自己有关的理由留他。
```

**⚠️ 两个"别"是刻意的**：
- **"别客套/别客服腔"** —— 否则会写成"感谢您的陪伴，期待下次光临"
- **"别用万能句"** —— 否则所有角色都挽留成同一句话（和 §39 那个"单调"是同一个教训）

## 43. ⚠️ 真事故：注释里误敲一个 `>` → **游戏拒绝启动**（✅ 已修 + lint 已补）

**用户报告**：游戏启动报
`警告Lv2:魔改内容\LLM_CONVERSATION.ERB:第1785行:使用不正确的文字作为行的开始`，
然后 `由于ERB脚本出现无法解释的行，Emuera停止运行`。

### 原因

写 `@LLM_HORNY_DESC` 的注释时，**想写 `;` 结果敲成了 `>`**（大概是脑子里在写 markdown 引用块）：

```erb
1784: ;     · **关系深**（= 2，恋慕 / 恋人 / 爱欲）⇒ 才会用眼神、小动作、
1785: >       半句话去撩他。          ← ★ 行的开头是 ">"，不是 ";"
```

**⇒ ERB 里这不是注释，是一个"以 `>` 开头的语句"** ⇒ 解释器无法解释 ⇒ 停止运行。

### ⚠️⚠️ 真正值得记的是：**`erb_check.py` 当时报的是 "All checks passed"**

因为 `erb_check.py` 是**缩进/配对**检查器 —— 它**根本不看"行的开头合不合法"**。
**⇒ 一个能让游戏完全起不来的错误，从它眼皮底下过去了。**

### 修法

**① 改掉那一行** ✓

**② 给 `erb_check.py` 补一条规则（`check_line_starts`）**，并且**分了级**：

| 级别 | 规则 | 依据 |
|---|---|---|
| **error** | 行首是 markdown 残留符号 `> \| \` ~ ^ * ?` | **任何情况下都不可能是合法语句** ⇒ 0 误报 |
| **warn** | 行首是中日韩文字 | ⚠️ **有两个合法来源**，只能提示 |

**⚠️ 那两个"合法来源"是实测扫全库（613 个文件）才发现的**，否则这条规则会天天误报：
1. **日文变量名赋值** —— era 系脚本大量这么写
   （`基礎攻撃力 = ABL:MASTER:戦闘能力 + 1`）
2. **`[SKIPSTART] … [SKIPEND]` 块内** —— 整段被解释器跳过
   （`NOUMIN.ERB` 开头整段中文说明）

**⇒ 所以 lint 里同时跳过 `[SKIPSTART]` 块** ✓

### 📌 教训

> **"工具说没问题"≠"没问题"。**
> `erb_check.py` 一直报 All checks passed，是因为它**只查它知道的那些事**。
> **⇒ 每次遇到一个工具没抓到的错，就当场把那条规则补进去** ——
> 这次补完，这类错误（漏分号、markdown 残留）就再也过不去了。
>
> **另一条**：写注释时**别让手指带着 markdown 习惯跑** ——
> 在 ERB 里 `>` `|` `` ` `` 开头都是硬错误。

## 44. ⚠️ 实测反馈：说「再见」时她**没道别就退出了对话**（✅ 已加防御）

**用户报告**：*"说再见的时候角色没有说出告别的话，而是直接退出自由对话模式了，
也许需要修改时序。"*

### 一、先排查时序 —— **时序本身是对的**

把主循环的调用顺序完整拉出来核对：

```
314: CALL LLM_BYE_CHECK(TARGET, LLM_INPUT)      ← 判定（玩家输入的关键词）
321: CALL LLM_BUILD_SYSTEM_PROMPT(...)          ← 内部：@LLM_DECIDE_ACTION → ACTION=3
                                                   → @LLM_ACTION_HINT CASE 3 注入送别提示
337: CALLSHARP LLM_CHAT_SEND(...)               ← 发请求
399: CALL LLM_PRINT_REPLY(TARGET, LLM_OUT)      ← ★ 她的回复在这里打印
431: IF LLM_BYE_MODE == 1 → BREAK               ← ★ 收尾在**她说完之后**
```

**⇒ 顺序正确：判定在前、注入在中、打印在前、收尾在后。**
（也核对过 `STRFIND` 在本作存在、`@LLM_IS_BYE` 的关键词包含"再见"。）

### 二、真正的可疑点：**她这一轮的回复被清空了**

主循环里有一条路径：

```erb
395: CALL LLM_SANITIZE_REPLY(LLM_OUT)
396: SIF LLM_OUT == ""
397:     CONTINUE          ← ★ 回复为空就**无声跳回输入框**
```

**⇒ 如果道别那一轮她的回复被清空**（例如 `###DELTA###` 解析把整段吃掉、
或模型没按格式给块），就会变成：

> **她什么都没说 → 回到输入框 → 玩家按回车 → `SIF LLM_INPUT == "" → BREAK` → 对话退出**

**⇒ 玩家看到的正是"没道别就退出了"** ✓ 与你描述的现象吻合。

**⚠️ 也检查了 `@LLM_PARSE_DELTA`**：它本身是**失败安全**的
（没有 `###DELTA###` 就原样返回；前半段为空就不抠）—— 所以不是它主动清空的，
但**它挡不住"模型这一轮就是没输出台词"**这种情况。

### 三、修法：**收尾轮不允许无声地过去**

把那条 `SIF LLM_OUT == "" / CONTINUE` 改成**分情况处理**：

```erb
IF LLM_OUT == ""
	; ★ 收尾轮：补一句旁白，把这一幕**演完**再结束
	IF LLM_BYE_MODE == 1
		CALL LLM_SHOW_FIGURE(TARGET)
		PRINTFORML 　（%CALLNAME:TARGET%朝你点了点头，算是道了别）
		LLM_TOGETHER = ""
		BREAK
	ELSEIF LLM_WANT_SLEEP
		CALL LLM_SHOW_FIGURE(TARGET)
		PRINTFORML 　（%CALLNAME:TARGET%打了个哈欠，转身去睡了）
		LLM_TOGETHER = ""
		BREAK
	ENDIF
	; ⚠️ 其它情况照旧：回到输入提示（空回复多半是网络抽风，不该踢出对话）
	CONTINUE
ENDIF
```

**⚠️ 两个设计要点**：
- **收尾轮必须演完**（道别/去睡不能无声过去）
- **非收尾轮仍然不踢出**（空回复多半是网络抽风，让玩家再说一次）

### 四、⚠️ 还没定位的（需要你再测一次）

**如果重启后她**说了一句但不是道别**（而不是"什么都没说"），那问题就在注入侧，
不在时序侧。**两种现象的排查方向完全不同**：

| 你看到的现象 | 说明问题在 |
|---|---|
| **她什么都不说，然后退出** | ✓ 已在本次修掉（空回复路径）|
| **她说了一句，但不是道别** | ⚠️ 注入侧 —— `LLM_ACTION` 没变成 3，或模型没follow |
| **她说了一句，但很敷衍** | ⚠️ 措辞侧 —— 提示不够强 |

**⇒ 麻烦重启后再试一次，把她的**原话**发我** —— 那样我能直接判断是哪一类。

## 48. ★★ 「她自己怎么看自己」—— 夸大型 + 谦虚型（✅ 已实现）

**用户要求**：
1. *"有些性格的角色还会夸大自己 —— 比如琪露诺会说自己很能打但实际很弱。你找一下还有没有其他适合这样性格的。"*

## 49. ★★ 「专长」层 —— 以及为什么"做饭"只有 2 个人值得写

**用户追问**：*"那做饭呢？或者其他的东西呢？"*

### 一、先看数据（扫全部 168 个角色）

| 料理等级 | 人数 |
|---|---|
| **ＥＸ** | **1**（美宵）|
| **Ｓ** | **1**（咲夜）|
| ≤ Ｄ | **135** |

**同理**：`音楽 <= 1` 有 142 个、`清掃 <= 1` 有 120 个、`話術 <= 1` 有 101 个。

### 二、⚠️⚠️ 由此得出的设计原则

> **给一半角色都写"她不擅长做饭"，等于什么都没说。**
>
> **真正值得写的，是"**稀有**"的那一端：她会，而别人不会。**

**⇒ 这也是为什么"专长"必须是**手写表**而不是按数值自动算** ——
数值高不等于"稀有"（`戦闘 >= 4` 有一大片），
而"这件事对她来说是**身份的一部分**"只有人知道。

### 三、实现：`@LLM_SKILL_PRIDE(角色, REF_OUT)`

| 角色 | 专长与态度 |
|---|---|
| **美宵** | 做饭是**看家本事**（全作唯一 EX）；有底气、乐意露一手；⚠️ 但**别主动吹** —— 开店的靠手艺说话 |
| **咲夜** | 家务厨艺是**专业**，完美到理所当然；**不特意炫耀**，被质疑时平静地证明；⚠️ 对「做得不够好」**容忍度极低** |
| **莉卡 / 梅露兰** | 演奏是**存在的意义**，不是爱好；外放，会主动想吹一段 |
| **露娜萨** | 同上，但**低调** —— 把话题引向姐妹而不是自己 |
| **弁弁 / 八桥** | 付丧神的演奏 —— **主动展示**，被夸会顺势抬自己 |
| **阿求** | 编书是使命；用「据我所知」的口气，**不是说教** |

### 四、三层结构（这是现在的完整形态）

```
【她擅长 / 不擅长的事】   ← ① **客观事实**（自动，只收有区分度的）
【她的专长】               ← ② **稀有强项**（手写，7 条）
【她怎么看自己】           ← ③ **自我认知**（手写，13 条，可与事实不符）
```

**三层各管一件事**：
- **①** 回答"她会什么"（数值）
- **②** 回答"她以什么为傲"（**稀有性**）
- **③** 回答"她怎么看自己"（**允许是错的**）

**⚠️ 表里没有的角色走通用规则**（"Ａ/Ｓ 谈起来有底气、Ｄ/Ｅ 心虚"）—— **已经够了，不必逐人写**。

### 五、用户的最终确认

> *"我觉得没问题 —— 让角色明白自己擅长什么不擅长什么就好。"*
>
> **⇒ 采纳。三层保持现状，不再加层。**
