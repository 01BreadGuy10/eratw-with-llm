### 3.3 ★ 本次定案：`CFLAG:態度` 不是 150/300/500

文档里有两套互斥的说法，**两份都只对了一半**：

```erb
; ERB\ステータス計算関連\ATTITUDE.ERB:83-94  （实测原文）
CFLAG:LOCAL:合意判定 = LOCAL:1
CFLAG:LOCAL:合意判定 += FLAG:催眠強度 * 4
SELECTCASE CFLAG:LOCAL:合意判定
    CASE IS >= 500
        CFLAG:LOCAL:態度 = 3
    CASE IS >= 300
        CFLAG:LOCAL:態度 = 2
    CASE IS >= 150
        CFLAG:LOCAL:態度 = 1
    CASEELSE
        CFLAG:LOCAL:態度 = 0
ENDSELECT
IF CFLAG:LOCAL:態度 < 2 && TALENT:LOCAL:合意誤認
    CFLAG:LOCAL:態度 = 2
    SIF CFLAG:LOCAL:合意判定 < 300
        CFLAG:LOCAL:合意判定 = 300
ENDIF
SIF CFLAG:LOCAL:ブチギレ && (!FLAG:70 || CFLAG:LOCAL:344 == 1)
    CFLAG:LOCAL:態度 = 0          ; ← 暴怒 / 睡着会强制归 0
SIF CFLAG:LOCAL:睡眠
    CFLAG:LOCAL:態度 = 0
```

| 量 | 编号 | 值域 | 阈值 |
|---|---|---|---|
| **`CFLAG:合意判定`** | **19** | 0~500+ | **150 / 300 / 500**（积分制） |
| **`CFLAG:態度`** | **6** | **0~3** | 由「合意判定」换算，**不是** 150/300/500 |

**⇒ 结论**：
- 代码里写 `CFLAG:態度 >= 3` 是**对的**（`LLM_CONVERSATION.ERB:4693` 就是这么写的，注释「官方 `CFLAG:態度 >= 3`」✓）。
- 想要**更细的接受度**用 `CFLAG:合意判定`（数值，比态度档位细）——**调研文档推荐的这个做法是对的**。
- **⚠️ 两者会不同步**：`合意判定 >= 500` 但 `背チギレ` 或被催眠/睡着时，`態度` 会被**强制归 0**。
  ⇒ **别用 `合意判定` 反推 `態度`**，直接读 `態度`。

## 4. 架构与机制（骨架）

### 4.1 两阶段 + 结算（LLM项目总览 §3）

```
┌─ 判定阶段 ─────────────────────────────────────────┐
│  ① @LLM_SLEEP_CHECK   → 她要收尾去睡吗（按亲密概率）│
│  ② @LLM_BYE_CHECK     → 玩家在道别吗？接受还是挽留  │
│  ③ 体力阈值           → 他快撑不住了吗              │
│  ④ @LLM_DECIDE_ACTION → ★ 算出**唯一的** LLM_ACTION │
│  ⇒ 这些数值到此就用完了                             │
└────────────────────────────────────────────────────┘
                        ↓
┌─ 对话阶段 ─────────────────────────────────────────┐
│  ⑤ @LLM_ACTION_HINT → 把「结论 + 相关数值」合成一句话│
│  ⑥ 基础事实层照常注入（地点/时间/天气/关系/记忆…）  │
│  ⑦ 【最重要的表达规则】—— 状态不是清单              │
└────────────────────────────────────────────────────┘
                        ↓
┌─ 结算阶段 ─────────────────────────────────────────┐
│  ⑧ @LLM_PARSE_DELTA / _MEMO / _NOTE ⇒ @LLM_APPLY_DELTA │
│  ⑨ 按 LLM_ACTION 决定是否结束对话                   │
└────────────────────────────────────────────────────┘
```

**⚠️ 为什么这样分（踩坑换来的）**：
改之前是"**并行撒网**" —— 六个模块各自往 prompt 里塞一段带 ⚠️ 的指令，
一轮最多塞进 **5 条** ⇒ 模型只能**每条都回应一下** ⇒ 台词变成"**状态面板念了一遍**"。

**⇒ 现在的规则：`事实可以有很多条，行动只能有一个。`**

### 4.2 `@LLM_DECIDE_ACTION` 的优先级（第一个成立的赢）

| 码 | 行动 | 说明 |
|---|---|---|
| 2 | **挽留** | 玩家发起的，最该回应 |
| 3 | **送别** | 同上 |
| 4 | **心疼他** | 比"她自己的困"更紧急 |
| 5 | **收尾去睡** | — |
| 6 | **憋着**（想要但地方不对） | — |

## 7. ⚠️ ERB 语法铁律（踩过的，**写代码前必看**）

> 完整版在 `ERB\魔改内容\LLM_ERB语法避坑.md`（1263 行）。这里是高危摘要。

| 规则 | 说明 |
|---|---|
| **`SIF` 只绑紧随的一行** | **且不能配 `ELSE`/`ELSEIF`/`ENDIF`**（同缩进也不行）；**下一行也不能是 `SIF`** |
| **`CHARADATA` 变量自己占一层下标** | 最多写 `VAR:(角色):(下标)`（两层） |
| **跨函数共享的变量必须放 `.ERH`** | 写在 `.ERB` 文件级会报 Lv1「#行只能在函数声明后立刻使用」 |
| **`#LOCALSIZE` / `#LOCALSSIZE` 只分配槽位** | **变量仍要 `#DIM` 声明**；`#DIMS X, N` 占 **N 个**字符串槽 |
| **形参名不能叫内置名** | `CHARA` / `ARG` / `ARGS` / `TARGET` / `MASTER` / `LOCAL` / `TIME` / `DAY` / `RESULT`… 都不行 |
| **要写回调用方的形参必须 `#DIM REF 名`** | 形参名叫 `REF_XXX` **不等于**引用传递！`REF` 只负责"传得回来"，不负责"算得对" |
| **字符串拷贝用 `A = %B%`** | 裸写 `A = B` 得到字面量 `"B"`；本作 `'=` **不可用于普通字符串拷贝** |
| **`%…%` 只能装字符串** | **数值必须 `{…}`**（"花括号装数字，百分号装文字"） |
| **字符串函数只能写在 `%…%` 里** | `X = SUBSTRING(...)` 得到的是**表达式原文** ⇒ 静默失效 |
| **字符串拼接：变量必须写在引号内** | `X += @"…%变量%…"`；**`X = "文" + %变量%` 会把 `" + ` 一起拼进去** |
| **`@"…"` 里不能有裸 ASCII 双引号** | 用「」 |
| **绝不写跨物理行的 `@"…"`** | 会让**整个游戏停止运行**；`\n` 要在同一行 |
| **行首必须合法** | 注释必须 `;` 开头（**`>` 开头会让游戏拒绝启动**） |
| **`CALLNAME:xxx` 不能直接进 `%…%`** | 先用 `=` 接住 |
| **`CALLSHARP` 同步阻塞、只回填最后一个参数** | `"0"`=等 / `"1"+文本`=成功 / `"-1"+原因`=失败（状态码和文本**拼在同一个参数里**） |
| **`EXISTMETH` / `EXISTFUNCTION` 不认插件方法** | 要探测插件得真的 `CALLSHARP` 一次 |
| **`#FUNCTION` / `#FUNCTIONS` 只能表达式调用** | 不能 `CALL`；`#FUNCTIONS` 只能返回字符串 |
| **带表达式的下标别写**（尤其别写进 `@"…"` 插值） | 解析失败**静默变空、不报错** ⇒ 先赋值给临时变量 |
| **抄官方判定注意作用域** | `CFLAG:诶嘿嘿`（317）= **玩家**；`CFLAG:角色:诶嘿嘿` = 角色 |
| **调官方流程函数前先抄它的 `RETURN` 前置条件** | 如 `@被逆推` 开头 `IF FLAG:推倒 == 2 / RETURN`（**静默返回**） |
| **同一件事不能两处各判一次** | 统一入口；**本项目栽过 7 次** |

**⚠️ 一个最容易误判的组合坑**：`REF` 缺失 + 字符串函数裸写会**互相掩护** ——
两个错误都在时功能静默失效；只修 `REF` 会让错误的表达式**立刻生效**、把台词整个替换成表达式原文。

### 9.6 ⚠️⚠️ `SAVEDATA` 尺寸不能改（正式版后）

**Emuera 二进制存档里 `SAVEDATA` 变量按声明顺序连续排布** ——
一个变量尺寸变了 ⇒ **后面所有变量偏移移动** ⇒ 读旧档可能**错位**
（不只是"新变量为空"，**别的变量也可能读到垃圾值**）。

| 阶段 | 规矩 |
|---|---|
| **测试期（现在）** | ✅ 随便改（旧测试档废了没关系）。**该做相反的事：趁现在把可能需要的槽一次备齐** |
| **正式版之后** | ❌ **绝不能改尺寸**。只追加；真要扩容就**新建变量**（如 `LLM_MEMO2, 32`），读时**先新的、空了再旧的** |

**本次实际情况**：`LLM_MEMO` 从 **4 改成 32**（2026-09-16）。用户读旧档发现记忆为空 ——
可能是老档本来没这些字段（正常），也可能是偏移错位（不正常）⇒ **建议开新档验证**。

#### #4 的详细评估结论（★ 最有价值的一段）

**穷举六对组合**：
- **会同时且一致**：`他累了+时间上的事`、`他累了+送别`、`欲求不满+挽留`、`时间上的事+收尾去睡`、`送别+收尾去睡`
- **结构上不会同时**：`他累了+挽留`（挽留率已压 0）、`欲求不满+憋着`（已互斥）、`挽留+收尾去睡`
- **⚠️ 唯一没处理的是 `欲求不满 + 他累了`**（她很想要，但他撑不住）

**最坏情况**：恋慕 + 欲求 1000 + 深夜 + 玩家很累 + 说"我走了" ⇒ **5 个强信号**。
问题不是"矛盾"而是 **反高潮** 与 **"台词变成汇报"**："这不是『活人』，这是『状态面板念了一遍』"。

**四条判定**：
- 日常闲聊（1~2 信号，大多数）✅ 没问题
- 睡前/道别（3 信号，不少）⚠️ 偶尔啰嗦但看得下去
- **极端叠加（5 信号，少）❌ 会出现"念状态面板"**
- ⇒ **"不会天天坏，但会在你最想看到好戏的时候（道别、深夜、恋慕）坏"**

**建议（成本都很低）**：
① **收尾轮降级 `LLM_HORNY`**（`LLM_BYE_MODE == 1` 或 `LLM_WANT_SLEEP == 1` 时不注入"表现方式"）—— ⏸ **待用户定**
② 加一句"别念清单"的总规则 —— ✅ 已由【最重要的表达规则】实现；作者："**这一句可能是整套系统里性价比最高的一行文字**"

#### 校准文档的核心结论（原文）

> **"这套系统现在的问题不是『不够强』，而是『可能同时太强』。"**

### 9.8 项目法则（跨节复用的元规律，**改代码前先对照**）

| 坑型 | 法则 |
|---|---|
| **判据不同源**（出现在 §8.2/§17/§18/§19/§26/§28/§29/§30/§38/§41） | **凡同一件事出现在多处，必须 (a) 判据同源、(b) 冲突时明说以谁为准**。模型不负责帮你调和矛盾 |
| **信息消失 → 模型用历史去填**（§19/§29） | **"让一项信息消失"永远比"给一项信息"危险** |
| **分支被抢走**（§26） | **带"一次性动作"的分支，条件必须含"它确实是第一次"的判据** |
| **手写多份 ⇒ 必漏**（§28 漏 3、§29 漏 3、§30 又漏 3、§41 有 21 处） | **同一件事要记在多处时不要手写多份 —— 建一个入口** |
| **`SIF` 只绑紧随一行**（§10/§21/§22/§40…） | 要做两件事／"判定一次做多件事" ⇒ 一律 `IF…ENDIF`。**本项目栽过最多**的坑 |
| **`%…%` 装不了数值／又是取模** | 数值用 `{…}`；判"距下次更新"用累加变量而非取模 |
| **`BREAK` 返回 0 ⇒ 上层 `RELINE` 清屏**（§45/§46） | 要保住画面必须 `RETURN 1` |
| **`#DIM` 数组占 `#LOCALSIZE`**（§37/§41） | 用逐轮取最大值代替数组；新函数别忘 `#LOCALSIZE` |
| **"工具说没问题"≠"没问题"**（§43） | 遇到工具没抓到的错就**当场补规则**进 `tool\` |
| **"我做了"≠"我证明给你看了"**（§38） | 判定逻辑改动要**汇报完整判定表，不要抽样**；两种形态各找一个角色验 |
| **先看证据，再动代码**（§45/§46） | 先看 `debug.log` 有无 `CHAT-OK` + `reply` |
| **优先复用官方函数/通道**（§8/§24/§33/§38） | "凡是『游戏怎么判定某件事』的逻辑，优先找官方现成函数" |
| **示例/点名比规则更有说服力**（§31/§32） | 「别用『上次你…』开头」「就算你上一轮答应过…现在也该改口」 |
| **数值效果走官方指令通道**（§33） | 不自己另算一份（判据同源／不会漏结算／语义正确） |

## 15.10 ★★ 存档兼容性：怎么加变量才不让玩家重开档（2026-09-18）

**⇒ 用户问**："能不能让玩家在不重开存档的情况下得到这个改动呢？"

### 原理

Emuera 的存档是**按声明顺序排列的值序列** ——
读档时按**当前代码的声明顺序**去对应 ⇒ **顺序一变，后面全错位** ⚠️

| 做法 | 旧存档 |
|---|---|
| **★ 追加在所有 `SAVEDATA` 的最后** | ✅ **能用**（新变量读到默认值 0 / 空）|
| **❌ 插在中间** | ⚠️ **后面全部错位** ⇒ 灾难 |
| **❌ 改已有变量的尺寸**（`, 1` → `, 16`）| ⚠️ **错位**（**2026-09-18 我们改 11 个标量时就报废了旧档**）|
| **✅ 新增非 `SAVEDATA` 变量**（普通 `GLOBAL` / 函数局部）| ✅ **完全不影响存档** ✓ |

### 三条操作规范

**① 新增 `SAVEDATA` ⇒ 一律追加在 `.ERH` 里所有 `SAVEDATA` 声明的**最后****
```erb
; ── 已有的（别动顺序）──
#DIM CHARADATA SAVEDATA LLM_PREF, 16
; ── ★ 新增的放这里 ──
#DIM CHARADATA SAVEDATA LLM_NEWTHING, 1
```
**⚠️ 绝不能插在 `LLM_ADDRESS` 和 `LLM_MEMO` 之间** ⚠️

**② 新变量必须能**容忍空值**（旧档读进来是 0 / 空字符串）**
```erb
; ✅ 好：0 就当成"这个功能还没启用"
SIF LLM_NEWTHING:(cid):0 <= 0
	RETURN
; ❌ 坏：假定它一定有值
```

**③ 永远不要改已有变量的尺寸** ⇒ 那等于**报废所有旧档**
**⇒ 所以一开始就写对**：**标量一律 `, 1`**（见 §15.9）✓

### ⚠️ 唯一例外

**如果改动本身就是为了修"存不住"的 bug**（如 §15.9 的标量改数组）——
**⇒ 那没法避免一次重开档** ⚠️
**⇒ 但要**明确告诉玩家**："这次必须开新档" ✓
